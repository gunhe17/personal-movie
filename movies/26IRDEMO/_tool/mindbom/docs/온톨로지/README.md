## 30초 요약

운영 플랫폼과 검사 시스템을 잇는다. 상대가 「검사 축 온톨로지 초안」(AS-1~6)을 냈고,
우리는 **양쪽 코드와 규약 원문을 실측해** 검증·보완했다.

핵심 결론 다섯:

1. **마인드봄 `Examination` 1건 = 플랫폼 `assessment_task` 1건** — 우리는 개별 실시에 집중하고, 묶음(case)은 플랫폼이 갖는다
2. **플랫폼에 준동형 사상 기계가 이미 있다** (`app/ontology/common/homomorphism.py`) — 새로 발명할 게 아니라 검사 축을 얹는다
3. **전이 강제력은 우리만 있다** — 플랫폼은 사건(이벤트 10종), 우리는 규칙(전이 맵). 느슨한 쪽으로 통일하면 SaMD 요건이 무너진다
4. **검사 정의는 플랫폼 `assessments`가 정본** — "신설"이 아니라 AS-1·AS-2에 맞게 **개조**하는 일. 다만 투사검사는 `workflow_type` 2값 어디에도 안 들어가 개조가 선행돼야 등록 가능
5. **회의 대기 안건 9개** (A~I) — 런타임 분리 형태가 정해져야 풀리는 것이 많다

### 사상표에서 새로 드러난 것 (2026-08-18)

플랫폼 코드를 실측하며 문서와 어긋나는 점 두 가지를 찾았다.

1. **이벤트 10종 중 전이는 8종뿐이다.** `updated`·`deleted`는 status를
   바꾸지 않는 CRUD 이벤트다(`updated`는 changed dict만 싣고, `deleted`는
   soft delete). 구현방안 §2.2가 10종을 일괄로 "전이 표현"이라 부르는 것은
   부정확하다 — 사상의 정의역에서 빼야 한다.

2. **`reverted`·`cancel_reverted`는 정적 전이 맵으로 표현 불가능하다.**
   목적지가 고정값이 아니라 `process["previous_status"]`에 담긴 값이다
   (`revert_task.py:28`, `revert_cancel_task.py:24`). 우리
   `VALID_TRANSITIONS`는 정적 dict이므로 구조적으로 대응물이 없다.
   위 회의 안건 7번.

준동형 검증은 통과했다(위반 0건). 4구간 접기가 안전한 이유도 실증됐다 —
재분석 역전이 2개가 모두 접힘 안에 갇혀 플랫폼에서는 관측되지 않는다.
`ai_draft_ready`·`under_review`를 `submitted`로 접으면 위반 3건이 뜬다.

## 이 작업에서 배운 것

**소스 파싱은 리팩터링에 취약하다.** 기존 프론트-백엔드 대조가 정규식으로
`ExamType` 유니온을 읽었는데, 선언이 `keyof typeof MODULES`로 파생되며
비교할 리터럴이 사라져 **테스트가 조용히 깨진 채** 방치돼 있었다.
계약은 데이터라 그 문제가 없다.

**탐지 도구를 그대로 믿으면 안 된다.** knip 결과 17개 중 4개가 오탐이었다
(자기 파일 내부 사용). 각 항목의 참조를 직접 확인해야 한다.

**같은 판정을 두 곳에 적으면 언젠가 어긋난다.** SCT 화면이 술어를 인라인으로
재구현하며 `completed`를 빠뜨려 완료된 검사에 확정 버튼이 다시 뜬 적이 있고,
고친 뒤에도 로르샤하에 같은 코드가 남아 있었다. 한 팀·한 레포에서도 이렇다.
