검사 모듈화와 운영 플랫폼 연동

따로 만들던 검사 셋을 하나로 묶고, 그 위에 플랫폼 연동을 얹는 일

마인드봄 · 2026-08-18 기준

1.1문제 — 같은 일을 세 번 만들었다

HTP·로르샤하·SCT를 작업자 세 명이 하나씩 맡아 따로 만들었다.

검사는 셋이지만 화면이 하는 일은 대부분 같다. 검사를 열고, 왼쪽에 단계 목록을 보여주고, 지금 어디까지 왔는지 표시하고, 다음 단계로 넘긴다. 그런데 셋이 따로 만들어졌으니 이 공통된 일이 세 벌로 존재했다.

가장 상징적인 숫자가 두 번째다. HTP 껍데기(112줄)와 SCT 껍데기(112줄)를 나란히 놓고 비교하면 다른 곳이 딱 두 군데였다 — 주소에서 검사 번호를 읽는 이름이 examId냐 id냐, 그리고 검사 종류가 'htp'냐 'sct'냐. 나머지 110줄은 글자 하나까지 같았다.

왜 이게 문제인가

같은 규칙이 세 곳에 적혀 있으면 언젠가 어긋난다. 한 곳을 고칠 때 나머지 두 곳은 조용히 옛날 규칙으로 남는다. 아무도 에러를 보지 못하고, 그저 화면마다 동작이 조금씩 달라진다.

실제로 일어난 일: 같은 검사가 어떤 화면에선 '로르샤하', 어떤 화면에선 '로샤'로 표시됐다. 같은 상태가 'AI 초안'과 'AI 초안완료'로 갈렸고, 색깔도 주황과 보라가 공존했다. 셋 다 "누가 봐도 버그"는 아니어서 오래 남았다.

"SCT 결과 화면이 판정 규칙을 직접 베껴 적으면서 상태 하나를 빠뜨렸다. 그래서 이미 끝난 검사에 '검사 확정' 버튼이 다시 떴다. 고친 뒤에도 로르샤하에 같은 코드가 남아 있었다." core/status.ts:48-56 주석에 기록된 실제 사고

1.2해법 — 껍데기 하나 + 자기소개서 셋

공통된 일은 한 벌만 두고, 검사마다 다른 것만 따로 적는다.

자기소개서(module.ts)에 적는 것

각 검사는 화면 껍데기를 만들지 않는다. 자기가 어떤 검사인지만 적는다.

  • 이름과 짧은 이름 — '로르샤하' / '로샤'
  • 단계 목록 — SCT는 작성 → 검토 → 결과 3단계
  • 각 단계가 언제 열리는지 — "문항을 다 채우면 검토가 열린다"
  • 잠겨 있을 때 왜 잠겼는지 알려줄 문구

이게 전부라 파일 하나가 60~70줄이고, 그중 대부분이 주석(왜 이렇게 판정하는가)이다. 실제 선언은 20~30줄.

효과가 가장 잘 드러나는 곳: 검사 목록판에 한 줄 추가하면 주소 연결· 사이드바·필터·배지·아이콘이 전부 따라온다. 예전엔 새 검사를 붙이려면 11곳 이상을 손봐야 했다.

1.3규칙을 베껴 적지 못하게 막기

묶어놓아도, 나중에 누군가 또 베껴 적으면 원점으로 돌아간다.

그래서 테스트가 코드를 감시하게 했다. 프로젝트 전체 파일을 훑어서 "확정 여부 판정"을 직접 다시 계산하는 코드가 있으면 테스트가 실패한다.

테스트가 실패하면 이렇게 말한다 — "목록에 추가하지 말고 코드를 고쳐라."

구분이 섬세하다. 상태를 나열하는 것 자체는 막지 않는다. 타입 정의나 라벨 표는 나열이지 판정이 아니고, 그것까지 막으면 정의를 쓸 수 없다. 잡아야 하는 건 "이 상태들 중 하나인가"를 다시 계산하는 코드다.

테스트가 지키는 것

테스트개수지키는 것
gate.spec.ts 109 클릭한 단계가 항상 열려 있는가 — 7가지 결재상태 × 4가지 진행상태 × 3검사 전수
state-contract.spec.ts 21 프론트와 백엔드가 같은 상태 목록을 쓰는가

extensibility.spec.ts가 특히 재밌다. 존재하지 않는 검사 두 개 (MMPI-2, 웩슬러)를 가짜로 선언해놓고, 그것들이 코어를 안 건드리고 동작하는지 본다. 이 파일이 깨지면 "새 검사를 붙이려면 코어를 고쳐야 한다"는 뜻이다.

리팩터링 전에는 이 테스트조차 새 검사를 선언할 수 없어 기존 'htp'를 빌려 쓰고 있었다. 확장성 테스트가 확장 불가를 증언하던 자리였다.

2.1가장 어려웠던 문제

"다음 방에 들어가야 도장이 찍히는데, 도장이 없어서 못 들어간다"

검사 화면은 단계를 순서대로 밟는다. 그럼 "다음 단계에 들어가도 되는가"를 무엇으로 판단할까? 처음엔 자연스럽게 검사 상태로 판단했다.

그런데 실제 데이터를 보니 이랬다.

검사수집을 마쳐도상태는
로르샤하녹음 종료 시각만 기록검사 진행중 그대로
HTP그림 4장 업로드 완료아무 변화 없음
SCT문항 전부 제출검사 진행중 그대로

세 검사 모두 "수집이 끝났다"를 상태에 남기지 않는다. 그러니 상태로 단계를 막으면 순환에 빠진다 — 다음 화면에 들어가야 상태가 바뀌는데, 상태가 안 바뀌어서 못 들어간다.

병원 차트로 비유하면

칸이 하나일 때

"진료 단계"라는 칸 하나에 환자 진행과 의사 결재를 같이 적으려 한다. 환자가 검사를 다 받았는데 의사 도장이 없으면, 그 사실을 적을 칸이 없다.

칸을 둘로 나누면

진행: 환자가 어디까지 받았나 (검사 완료 ✓)
결재: 의사 검토가 어디까지 (아직 미검토)
두 사실이 동시에 기록되고, 다음 방 입장은 진행만 보면 된다.

2.2분리가 만든 것

이 분리는 화면 하나 고치는 수준이 아니라 시스템의 뼈대를 바꿨다.

① 상태 목록이 줄었다

ai_analyzing(AI 분석중)이 상태에서 빠졌다. 그건 상태가 아니라 작업이었기 때문이다 — 순간적이고, 여러 번 반복되고, 실패하고, 어떤 검사에는 아예 없다. 별도의 작업 기록표로 옮겼다.

앞으로 붙을 표준화 검사(MMPI·웩슬러)는 규준표 기반이라 AI 분석 단계가 아예 없다. 상태 목록에 그게 있으면 없는 단계를 억지로 통과해야 한다. 실제로 SCT가 그래서 상태 관리를 우회하고 있었다.

② 실데이터로 검증했다

실제 검사 40건에 새 판정을 적용했더니, 겉보기에 똑같이 검사 진행중이던 로르샤하 3건이 2건(기록 완료)과 1건(기록 중)으로 갈렸다. 상태만 보던 눈에는 보이지 않던 구분이다.

③ 우연히 안전하던 곳이 드러났다

진행 상황을 아직 모르는 동안 뒤 단계를 열면 안 된다는 규칙이 있다. 그런데 로르샤하 모듈만 그 방어를 자기 안에 갖고 있었다. HTP와 SCT가 안전했던 건 규칙을 지켜서가 아니라, 판정식이 마침 진행 상황을 참조해서 생긴 우연이었다.

지금은 코어가 보장한다. 모듈이 진행 상황을 안 봐도 코어가 막고, 가짜 모듈로 그걸 검증하는 테스트가 있다.

3.1연결해야 할 두 시스템

마인드봄은 검사를 하고, 마인드스코프는 센터 운영을 한다.

마인드봄 — 우리

검사 한 건을 실시하고 해석 초안을 만든다. "이 검사가 어디까지 진행됐나"를 규칙으로 관리한다.

마인드스코프 — 운영 플랫폼

내담자·케이스·배정·청구를 관리한다. 검사 진행을 사건(이벤트)으로 기록한다.

연결 지점은 명확하다. 마인드봄 검사 1건 = 플랫폼 검사과제 1건. 우리는 개별 실시에 집중하고, 여러 검사를 묶는 '케이스' 개념은 플랫폼이 갖는다.

어려운 점 — 같은 현실을 다른 어휘로 적는다

마인드봄플랫폼
표현 방식 규칙 — "이 상태에서 저 상태로만 갈 수 있다" 사건 — "시작됐다", "제출됐다"
강제력 있음 규칙 위반은 거부된다 없음 사건은 기록될 뿐
상태 개수 6종 6종 (이름과 의미가 다름)

느슨한 쪽으로 통일하면 안 된다. 우리는 SaMD 2등급 의료기기라 상태 전이를 엄격히 관리해야 하는 규제 요건이 있다. 플랫폼 방식에 맞추면 그 요건이 성립하지 않는다. 회의 안건

3.2사상표 — 무엇이 무엇에 대응하는가

"어떤 사건이 어떤 전이를 뜻하는가"를 표로 고정한다.

이걸 표로 못박지 않으면, 양쪽이 각자 알아서 해석하다가 어긋나도 아무도 모른다. 그래서 대응 관계를 코드로 적고, 양쪽 검증 장치가 같은 데이터를 읽게 했다.

왜 4구간을 하나로 접는가

AI 초안·검토·확인은 전부 우리 임상가 안에서 일어나는 일이고, 플랫폼 입장에선 아직 "제출 전"이다. 이걸 플랫폼의 '제출완료'로 보내면 안 된다 — 우리는 아직 재분석으로 되돌아갈 수 있기 때문이다.

검증으로 확인했다. 우리 되돌리기 전이 두 개가 접힘 안에 갇혀 있어 플랫폼에서는 아무 일도 없던 것처럼 보인다. 일부러 '제출완료'로 접어보면 위반 3건이 뜬다. 이 역테스트도 함께 고정해뒀다.

일부러 대응시키지 않은 것 — '완료'

양쪽에 완료라는 같은 이름이 있지만 다른 개념이다. 플랫폼의 완료는 담당자가 검수해야만 도달한다. 우리 '보고서 생성'을 거기에 자동 연결하면, 사람의 검수가 조용히 건너뛰어진다 — 감사추적 구멍이자 규제 위반이다.

그래서 우리 축은 '보고서 생성'에서 끝내고, 그 뒤는 플랫폼 소관으로 남긴다.

3.3실측하며 찾은 것

문서만 읽지 않고 플랫폼 코드를 직접 확인했더니 두 가지가 어긋나 있었다.

① "이벤트 10종"이 실은 8종이다

플랫폼 문서는 검사 이벤트 10종이 전부 진행 상태를 나타낸다고 적고 있다. 그런데 코드를 보면 수정과 삭제 두 개는 상태를 바꾸지 않는다. 단순 편집 기록일 뿐이다.

대응표를 만들 때 이 둘을 빼야 한다. 안 그러면 "대응되지 않는 항목"이 표에 섞여 들어가 나중에 혼선이 생긴다. 문서 정정 필요

② '되돌리기'는 표로 표현할 수 없다

플랫폼에는 완료를 취소하는 되돌리기 기능이 있다. 문제는 되돌아갈 목적지가 고정돼 있지 않다는 것 — 취소하기 직전 상태를 따로 저장해뒀다가 거기로 돌아간다.

우리 규칙표는 "A에서는 B로만 갈 수 있다"는 고정된 표라서, 목적지가 그때그때 달라지는 이 동작은 구조적으로 담을 수가 없다. 회의 안건 추가

4.14층 방어

"두 곳이 어긋나도 모르게 지나갈 수 있나"를 층층이 막는다.

층막는 것상태
1층 선언과 실제 구현이 다르면 서버가 안 뜬다 플랫폼 보유
2층 규칙을 베껴 적은 코드가 있으면 테스트 실패 완료
3층 프론트와 백엔드가 같은 표로 전수 대조 완료
4층 DB에 규칙 밖 값이 있으면 감사 로그에 기록 완료 미연결

1~3층은 코드가 규칙을 어기는 것을 막는다. 4층만 성격이 다르다 — 코드를 거치지 않고 들어온 값(과거 버전이 남긴 데이터, 외부 시스템 연동)을 읽는 시점에 발견한다.

4층은 차단하지 않고 기록만 한다. 규칙 밖 값을 만났다고 조회를 막으면 과거 데이터를 가진 검사는 열람 자체가 불가능해진다. 임상 기록 접근이 막히는 편이 값이 낡은 것보다 나쁘다.

원칙: 읽기는 관대하게, 쓰기는 엄격하게.

5검사 정의 개조 주체우리 3종 등록이 여기 막혀 있다
6PDF 저장·무결성저쪽엔 체크섬이 있고 우리는 비저장
7되돌리기 대응고정 표로 표현 불가능 이번에 발견

연동이 붙어야 의미가 생기는 것

4층 관측 모듈은 만들어뒀지만 아직 조회 경로에 연결하지 않았다. 지금 규칙 밖 값이 나올 수 있는 건 과거 completed 하나뿐이고, 그건 이미 알고 있는 사실이라 쿼리 한 번이면 확인된다. 4층이 진짜 필요해지는 건 외부 시스템이 우리 DB에 값을 넣기 시작할 때다.

연결 지점을 정하려면 회의 안건 1번(레포·런타임 분리 형태)이 먼저 정해져야 한다. 모듈은 호출부가 없어 아무 동작도 하지 않으므로 부담이 없다.

모듈화에 남은 기술 부채

  • 아이콘만 여전히 검사별 분기 — 해결됨. 임시 SVG를 옮기는 대신 아예 없애고, 검사 심볼 색을 모듈이 선언하게 했다. 프론트에 검사종류 하드코딩 분기가 남지 않았다.
  • 백엔드 진행 판정은 아직 손으로 분기 — 프론트는 목록판에서 파생되는데 백엔드는 대칭이 아니다
  • 진행 축이 두 개의 예/아니오뿐 — 웩슬러처럼 소검사 12개짜리는 담을 수 없다
  • HTP만 검토 단계가 없다 — 결과 화면에 검토가 섞여 있어 CDSS 원칙과 충돌
  • 로르샤하 자유반응·질문 미분리 — 표준 실시 절차는 2단계인데 하나로 합쳐져 있다
