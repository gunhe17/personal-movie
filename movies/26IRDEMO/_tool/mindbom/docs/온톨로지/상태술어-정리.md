> 배경 문서: [검사축-구현방안.md](검사축-구현방안.md) §4.2 (2층 — 리터럴 금지)

## 1. 무엇이 문제였나

### 한 줄 요약

**"임상가 확정 이후인가"라는 판정이 코드 9곳에 각각 손으로 적혀 있었다.**

`['confirmed', 'report_generated', 'completed']` — 이 배열이 술어 함수 안에만 있어야 하는데,
화면과 서비스가 저마다 다시 적고 있었다.

### 왜 위험한가

지금은 9곳의 값이 **우연히 모두 같아서** 아무 일도 안 일어난다.
문제는 상태가 하나 늘거나 줄 때다 — 정본을 고쳐도 나머지 8곳은 옛 값 그대로 남는다.
그리고 **아무도 모른다.** 타입 체크도 테스트도 "배열 리터럴이 서로 달라졌다"를 잡지 못한다.

### 이건 가정이 아니라 이미 겪은 사고다

`apps/web/src/lib/features/examination/core/status.ts` 주석에 경위가 남아 있다:

> 실제로 SCT 결과 화면이 이 목록을 인라인으로 재구현하면서 completed를 빠뜨려,
> **완료된 검사에 '검사 확정' 버튼이 다시 뜨는 회귀**가 있었다.
> (그 화면은 이 값을 "완료됐나" 판정으로도 재사용했다 — 두 개념은 다르다.)

`completed`는 `confirmed`보다 **더 진행된** 상태다. 목록에서 빠지면
"가장 끝난 검사만 기능이 막히는" 역전이 생긴다.

SCT는 그때 고쳤다. **그런데 로르샤하가 같은 코드를 그대로 갖고 있었다** — 이번에 발견한 것.

## 2. 무엇을 고쳤나

### 2.1 술어 함수를 정본으로 세웠다

각 상태 머신 옆에 집합과 술어를 두고, 나머지는 전부 그것을 호출한다.

| 위치 | 추가한 것 |
|---|---|
| `examination/common/state_machine.py` | `CONFIRMED_STATUSES` · `is_confirmed()` |
| `comprehensive_report/state_machine.py` | `CONFIRMED_STATUSES` · `is_confirmed()` |
| `examination/core/status.ts` (프론트) | `CONFIRMED_STATUSES` (기존 `isConfirmed` 내부로) |
| `features/report/constants.ts` (프론트) | `isReportConfirmed()` · `isReportFinalized()` |

### 2.2 검사와 종합보고서는 **별개**로 뒀다

값이 우연히 겹치지만 다른 상태 머신이다.

```
검사(examination)   : created · in_progress · ai_draft_ready · under_review
                      · confirmed · report_generated · completed        (7종)

종합보고서(report)  : draft · ai_generated · under_review
                      · confirmed · report_generated · completed        (6종)
```

`draft`·`ai_generated`는 검사에 없고, `created`·`in_progress`·`ai_draft_ready`는 보고서에 없다.
**한쪽을 고칠 때 다른 쪽이 따라가면 안 되므로 각자 정본을 갖는다.** 주석에 그 이유를 남겼다.

### 2.3 호출부 9곳을 술어로 교체

| # | 파일 | 이전 | 이후 |
|---|---|---|---|
| 1 | `rorschach/services.py:977` | `status not in ("confirmed", …)` | `not is_confirmed(...)` |
| 2 | `comprehensive_report/facade.py:373` | `status not in ("confirmed", …)` | `not is_confirmed(...)` |
| 3 | `examination/common/repository.py:240` | `status.in_(("confirmed", …))` | `status.in_(CONFIRMED_STATUSES)` |
| 4 | `examination/report/facade.py:37` | `_ELIGIBLE_STATUSES = {…}` | `= CONFIRMED_STATUSES` |
| 5 | `comprehensive_report/constants.py:11` | `SELECTABLE_STATUSES = {…}` | `= CONFIRMED_STATUSES` |
| 6 | `rorschach/steps/Results.svelte:47` | `[…].includes(e.status)` | `isConfirmed(layoutCtx.status)` |
| 7 | `rorschach/steps/Results.svelte:119` | `[…].includes(exam.status)` | `isConfirmed(layoutCtx.status)` |
| 8 | `reports/[reportId]/+page.svelte:29` | `[…].includes(report.status)` ×2 | `isReportConfirmed()` · `isReportFinalized()` |
| 9 | `examinations/+page.svelte:205` | `DONE_STATUSES = new Set([…])` | `isConfirmed()` |

### 2.4 술어가 `string`도 받게 넓혔다

`isConfirmed(status: ExamStatus)` → `isConfirmed(status: ExamStatus | string)`

**왜** — 목록 API 응답(`ExamItem.status`)은 서버에서 오므로 타입이 `string`이다.
좁힌 타입만 받으면 화면이 `as ExamStatus` 캐스팅을 피하려고 배열을 다시 적게 된다.
실제로 `examinations/+page.svelte`의 `DONE_STATUSES`가 그렇게 생겨난 것으로 보인다.

> **정본을 쓰는 쪽이 항상 더 쉬워야 한다.** 어렵게 만들면 우회가 생긴다.

## 3. 손대지 않은 것

| 대상 | 이유 |
|---|---|
| `htp/steps/Results.svelte`의 `NEXT_STEP_STATUSES` | `['ai_draft_ready', 'report_generated']` — 확정 술어의 재구현이 **아니다.** "다음 단계 버튼이 뜨는 상태"라는 독자적 개념이고, 파일 안에서 한 번만 쓰이며 주석에 근거가 달려 있다 |
| `EXAM_STATUS_VISUAL` 등 라벨·색 맵 | 상태를 **키로 쓰는** 것이지 술어가 아니다 |
| `VALID_TRANSITIONS` | 전이 규칙 자체 = 정본 |

**판정 기준**: 상태 문자열이 등장한다고 다 문제가 아니다.
**같은 판정을 다른 곳에서 다시 구현**하는 것이 문제다.

## 5. 이 작업의 의미

[검사축-구현방안.md](검사축-구현방안.md)가 제안한 **4층 방어** 중 2층의 선행 작업이다.

| 층 | 하는 일 | 상태 |
|---|---|---|
| 1층 | 로드 시점 선언·구현 대조 | 플랫폼 `homomorphism.py`에 이미 존재 |
| **2층** | **리터럴·재구현 금지** | **← 이번 작업이 정리 대상을 없앰. lint 도입은 다음** |
| 3층 | 적합성 표 49쌍 전수 대조 | 다음 작업 |
| 4층 | 런타임 관측 | 이후 |

이제 "상태 판정은 술어 함수로만" 규칙을 lint로 강제할 수 있다.
정리 전에 lint를 켰다면 9곳이 한꺼번에 빨간불이 되어 도입 자체가 막혔을 것이다.

### 남은 것 (참고)

`CONFIRMED_STATUSES`가 백엔드 2곳 + 프론트 2곳, 총 4곳에 각각 선언돼 있다.
지금은 **의도적**이다 — 검사와 종합보고서는 별개 상태 머신이고, 백엔드와 프론트는
언어가 다르다. 이 4곳을 하나로 묶는 것이 구현방안 §4.3의 **적합성 표**가 할 일이다.
