> 준거 규약: `.claude/api/{ontology,naming,application}.md` · `app/ontology/{CLAUDE,DECISIONS}.md`
> 작성 2026-08-18 · 양쪽 코드 + 규약 원문 실측

## 0. 이 문서가 따르는 원칙

### 0.1 연산이 먼저다 (CLAUDE.md §3.2)

> **기존 방식 (NOT)**: "이 객체는 어떤 필드를 갖는가?"부터 생각함
> **온톨로지 방식 (BUT)**: "이 세계에서 가능한 의미 있는 연산은 무엇인가?"부터 생각함
>
> 핵심: 객체의 의미는 데이터 형태가 아니라 **"무엇을 할 수 있는가(연산)"**에 의해 결정됩니다.

따라서 테이블·컬럼으로 시작하지 않는다. 검사 세계 $A_{검사} = (S, O)$의 연산 $O$를 먼저 세우고,
상태 $S$는 그 연산이 요구하는 만큼만 뒤따르게 한다.

### 0.2 어휘는 발명하지 않는다 (naming.md §2)

> 이 표에 없는 동사를 새 서비스·엔드포인트에 도입하려면 loop 결정 로그에 항목을 추가하고 이 표를 갱신한다
> — 어휘는 닫혀 있고, 확장은 기록을 남긴다.

**검사 축이 필요로 하는 동사는 이미 전부 통제어휘 안에 있다**(§1.2). 새 동사를 만들지 않는다.

### 0.3 필터·정렬·투영은 유도한다 (naming.md §2-A)

> 총체 쿼리의 **필터와 기본 출력**은 tool별 발명이 아니라 **모델 필드 아키타입에서 기계적으로 유도**한다
> (발명 여지 제거 = 어휘 드리프트·누락·환각 파라미터의 구조적 차단, lab 실측 59→78%).

슬롯을 손으로 고르지 않는다. 아키타입이 정한다(§3.3).

## 1. 검사 세계의 연산 $O_{검사}$

### 1.1 연산 목록 — 통제어휘 대조

naming.md §2-B(생명주기·상태전이)와 §2-A(CRUD)에 **이미 존재하는 동사만** 쓴다.

| 연산 | 통제어휘 | 한국어 | 소유 | 비고 |
|---|---|---|---|---|
| `create` | §2-A | 생성·등록 | 플랫폼 | 검사 배정 |
| `submit` | §2-B | 제출 | 마인드봄 | 반응 수집 완료 (반대어 `retract`) |
| `confirm` | §2-B | 확정 | 마인드봄 | **CDSS 핵심** — 임상가 확정 |
| `complete` | §2-B | 완료 | 플랫폼 | 진행이 끝남 — 검수 액션 |
| `cancel` | §2-B | 취소 | 플랫폼 | 예정된 것을 무름 (반대어 `revert`) |
| `refuse` | §2-B | 거부 | 내담자 | `accept`의 반대어로 등재됨 |
| `query` | §2-A | 유연 조회 | 양쪽 | 다중 필터·필드 선택형 |

**어휘 판정 근거** — naming.md §2-B는 "UI 버튼의 한국어가 판정 기준"이라고 못박는다.
마인드봄 UI의 '검사 확정' 버튼 → `confirm`. 통제어휘의 `confirm`("시스템·상대가 유효 확정")과
정확히 대응한다.

### 1.2 통제어휘에 없어서 상태로 두지 않는 것

| 후보 | 판정 | 근거 |
|---|---|---|
| `administer` (실시) | **동사 아님** | 통제어휘 미등재. 실체는 `submit`까지의 과정 — progress 축이 담당 |
| `score` (채점) | **동사 아님** | 통제어휘 미등재. AS-2 "채점 방식" 축은 **분류**이지 사건이 아니다 |
| `draft` (초안 생성) | **동사 아님** | §1.3 참조 — 사상 규칙 위반 |
| `publish` (보고서 발행) | **미정** | 통제어휘에 없다. `create_report`로 표현 가능한지 확인 필요(§6.2) |

> **규약 준수**: 위 넷을 동사로 쓰려면 loop 결정 로그 등재가 필요하다(naming.md §2 서문).
> 등재 없이 도입하지 않는다.

### 1.3 `ai_analyzing`이 상태가 아닌 이유 — 사상 규칙

CLAUDE.md §1.3:

> 정의역의 모든 원소는 반드시 **단 하나의 화살표만** 공역으로 보내야 합니다.

AI 초안 생성은 같은 검사에서 여러 번 일어난다(재분석·로르샤하 영역별). 상태로 두면
한 원소가 여러 화살표를 갖게 되어 **사상이 성립하지 않는다.** `ai_analysis_jobs`로 분리한 것은
우회가 아니라 사상 규칙을 지킨 결과다.

> **회의 정정**: 초안 §4.5는 마인드봄 상태를 8종(`ai_analyzing` 포함)으로 실측했으나
> 2026-08-18 현재 **7종**이다. 상태 사상표는 4구간 접힘으로 재작성해야 한다.

### 1.4 연산에서 유도된 상태

```
created ──submit──> in_progress ──(job)──> ai_draft_ready
        ──(review)──> under_review ──confirm──> confirmed
        ──(report)──> report_generated ──complete──> completed
```

**빠진 연산이 곧 빠진 상태다** — `refuse`/`cancel`에 대응하는 상태가 마인드봄에 없다는 것이
초안 §4.5 갭 ②의 정체다. 필드 누락이 아니라 **연산 미정의**다.

## 2. 준동형 조건 — 무엇이 보존되어야 하는가

CLAUDE.md §2.2:

$$f(\text{transition}(s, e)) = \text{publicTransition}(f(s), \text{publicEvent}(e))$$

- $S_{내부}$ = 마인드봄 7종 · $S_{외부}$ = 플랫폼 6종 · $f$ = 압축 사상

### 2.1 보존이 깨지는 지점 — `completed` 동명이의

| | 마인드봄 | 플랫폼 |
|---|---|---|
| `completed` 의미 | 최종 상태 (전이 없음) | **담당자 검수 액션의 결과** |

$f(\text{report\_generated} \xrightarrow{complete} \text{completed})$를 자동 매핑하면,
플랫폼에서 `complete`(검수)가 **일어나지 않았는데** `completed`에 도달한다.
좌변 ≠ 우변이므로 **준동형이 아니다.**

**해법**: $f$의 정의역을 `report_generated`까지로 제한한다. `complete`는 사상하지 않는다.
양쪽 `completed`는 동명이의이며 대응하지 않음을 계약에 명시한다.

### 2.2 비대칭 — 규칙을 표현하는 방식이 다르다

| 항목 | 마인드봄 | 플랫폼 |
|---|---|---|
| 전이 표현 | **선언** — `VALID_TRANSITIONS` 맵 | **사건** — `AssessmentTaskAtomic` 이벤트 10종 |
| 전이 강제 | `validate_transition()`이 불법 전이 차단 | 없음 — `status`는 `String(20)`, 어떤 값이든 대입 가능 |
| 종료 상태 | `completed` 단일 | `TERMINAL_TASK_STATUSES = {completed, refused, cancelled}` |
| 집계 | 없음 | `sync_case_status.py` — task 세어 case 상태 유도 |

> **정정(2026-08-18)**: 앞선 판단은 "플랫폼에 전이 규칙이 없다"였으나 부정확했다.
> **선언적 맵이 없을 뿐 사건은 정의돼 있다** — `assessment_task/events.py`가
> `created`·`started`·`submitted`·`completed`·`refused`·`cancelled`·`reverted`·
> `cancel_reverted`·`updated`·`deleted` 10종을 발행하고, 알림 핸들러가 이를 소비한다
> (`notify_assessment_task_submitted` 등).

**차이의 본질**: 플랫폼은 "무슨 일이 일어났는가"(사건)를, 마인드봄은 "무엇이 허용되는가"(규칙)를
표현한다. 둘 다 연산 구조이지만 **강제력이 있는 쪽은 마인드봄뿐**이다 —
플랫폼은 잘못된 전이를 사후에 기록할 수는 있어도 사전에 막지 못한다.

준동형 검증은 이 차이를 흡수할 수 있다. 플랫폼 이벤트 10종을 우리 상태 전이에 사상하면
"어떤 사건이 어떤 전이를 뜻하는가"가 표로 고정된다(§4.3 적합성 표의 확장).

> **회의 안건**: 전이 규칙 엄격함의 기준. 느슨한 쪽으로 통일하면 SaMD 2등급 요구사항
> ("상태 머신: 검사 상태 전이 엄격 관리")이 성립하지 않는다.
> 이벤트를 계약에 포함시켜 사상표를 만드는 것이 현실적 절충안이다.

from app.infrastructure.persistence.unit_of_work import UnitOfWork

반쪽 노출은 "슬롯 혼동 함정"으로 규약이 명시적으로 금지한다.

**커스텀 봉쇄(surjectivity) 준수** — 위 표 밖의 파라미터를 만들지 않는다.
`audit_query_filters.py`의 `custom_param_gaps`가 역검사한다.

### 3.4 정렬 — 사건축 완결 (naming.md §2-A)

시점 필터가 열린 축은 정렬도 열려야 한다("거를 수 있으면 정렬도 할 수 있어야 한다").

| 축 | 필터 | 정렬 값 |
|---|---|---|
| 대표(`created_at`) | `date_from/to` | `latest` · `oldest` (무표) |
| `scheduled` | `scheduled_from/to` | `scheduled_earliest` · `scheduled_latest` |
| `started` | `started_from/to` | `started_earliest` · `started_latest` |
| `completed` | `completed_from/to` | `completed_earliest` · `completed_latest` |

**대칭 요구**: 규약은 시점 필터와 사건축 정렬을 "완전 대칭"으로 못박는다 —
유도원이 하나이므로 **한쪽만 열면 비대칭**이 된다(거르는데 정렬 못 함 = 대표축 오용).
감사 `date_filter_completeness_gaps` + `sort_completeness_gaps`가 짝으로 검사한다.

#### 앵커 개념 제거 (2026-08-18 적용 완료)

작업 착수 시점의 `date_from/to`는 `created_at`이 아니라 **파생값**을 걸렀다:

```python
anchor = func.coalesce(Examination.scheduled_at, Examination.created_at)
```

이건 **"일정 미정"을 "등록한 날에 일정 있음"으로 위장**하는 것이었다.
검사일을 정하지 않고 등록한 검사가 타임라인에 '예정' 라벨을 달고 등록일에 떴다 —
잡은 적 없는 예정이다. 프론트에도 같은 규칙이 복제돼 있었다(`resolveAnchor`).

**적용한 결정: 일정이 없으면 없는 것으로 남긴다.** 억지로 날짜를 붙이지 않는다.

| 항목 | 이전 | 이후 |
|---|---|---|
| 서버 필터 | `coalesce(scheduled_at, created_at)` | `scheduled_at` (NULL은 비교에서 탈락) |
| 프론트 위치 | `scheduled_at ?? created_at` | `scheduled_at` (없으면 카드 없음) |
| "앵커" 개념 | `AnchorResult` 구조체 + `resolveAnchor()` | **소멸** — 고를 게 없으면 이름도 필요 없다 |

파생 컬럼이 사라지면서 `date_from/to`가 규약의 **대표 시간축**으로 정상화됐고,
`scheduled_at`은 온전한 사건축이 된다. 유도표(§3.3)와 정렬표가 그대로 성립한다.

> **일정 없는 검사는 왜 남는가** — 필수화로 없앨 수 없다. 플랫폼도 같은 구조다:
> `assessment_sessions.schedule_id`가 nullable이고(온라인 링크 발송 등 대면 일정
> 없는 검사), `schedules.start`는 not-null이다. "일정에 붙었나"와 "언제"가 분리돼 있다.
> 운영 플랫폼에서 등록해도 일정 없는 검사는 계속 들어온다.

배선 정본은 `infrastructure/persistence/agent_query.resolve_sort`.
SQL 어휘(`asc`/`desc`)는 표면 금지.

### 3.5 yaml 계약 (ontology.md §4)

```yaml
# app/ontology/handler/examination/query_examination.yaml
name: examinations.query

codomains:
  center_type:
    counseling:
      operation: app.application.handlers.examination.query_examination.query_examination_handler
      slots:
        - center_id
        - owner_scope
        - status
        - exam_type
        - client_id
        - client_ids
        - examiner_id
        - examiner_ids
        - battery_id
        - battery_ids
        - date_from
        - date_to
        - scheduled_from
        - scheduled_to
        - started_from
        - started_to
        - completed_from
        - completed_to
        - id
        - ids
        - sort
        - limit
        - fields
```

**§4 준수 확인**

| 규칙 | 준수 |
|---|---|
| `codomains` 밑의 키는 정확히 하나 | `center_type` 하나 |
| `slots`는 조회 축 **전부** (공통분 복제) | 20개 전부 나열 — 공유 선언 안 만듦 |
| `SERVER_SUPPLIED`(`uow`·`namespaced`)는 slots 밖 | 제외됨. 단 공역이 반드시 받아야 함 |
| `operation`은 전체 import 경로 | 명시 |
| 미등재 좌표 = `NotImplementedError` | school·military·hospital 선언 안 함 (D6 판단 계승) |

### 3.6 호출 방향 — 단방향 (ontology.md §2)

```
ontology handler  →  application handler  →  facade  →  service  →  repository
```

| 대상 | 판정 |
|---|---|
| application handler | 허용 |
| 모듈 루트 facade | 허용 |
| 모듈 handler · service · repository · model | **금지** |
| 다른 ontology handler | **금지** — 2단만, 체인 금지 |
| application → ontology (역방향) | **금지** |

**검사 축 적용**: 마인드봄 검사 조회는 `query_examination_handler`(application) →
`ExaminationFacade`로 내려간다. 온톨로지가 `ExaminationRepository`를 직접 부르지 않는다.

### 3.7 출력 — 네임스페이스 끄기 (ontology.md §6)

```
agent 표면 : {"examination.id": ..., "examination.status": ...}   접두 필요
ontology   : {"id": ...,             "status": ...}               접두 = 모듈 어휘 누수
```

공역이 `namespaced=False`를 **관통**시켜야 한다. 안 받으면 로드가 죽는다(§5).
봉투(`rows`·`aggregate`)는 손대지 않고 통과 — 돌아오는 사상은 항등이다.

### 3.8 상태 전이는 온톨로지에 두지 않는다

ontology.md §1은 "한 파일 = 한 정의역 연산"이라 `transition_examination`도 형태상 가능하다.
그러나 **두지 않는다.** 근거는 DECISIONS.md D5의 판정 기준이다:

> 판정 기준은 **하강 가능한가** 하나다.
>
> | 공유되는 것 | 처리 |
> | 한 모듈 안의 로직 | owning facade로 하강 — handler끼리 부르지 않는다 |
> | 크로스모듈 use-case | 정의상 단일 facade로 못 내려간다 → handler 호출 |

상태 전이는 **검사 모듈 안의 로직**이므로 owning facade로 하강 가능하다 →
`ExaminationFacade.confirm_examination()`이 정본. 온톨로지 표면이 아니다.

전이 URL도 naming.md §3이 정한 형태를 따른다:

```
POST /examinations/{id}/confirm      # 상태전이 = 동사 segment
```

> PATCH body의 status 값으로 위장하지 않는다(naming.md §3 명시 금지).

## 4. 어긋남 방지 — 4층

### 4.1 1층 — 로드 검사 (ontology.md §5, 이미 존재)

> `get_homomorphism`이 yaml을 읽을 때 셋을 본다. 하나라도 어긋나면 예외다.

| 검사 | 잡는 것 |
|---|---|
| 축이 `AXES`에 있나 | 축 이름 오타 |
| `operation` 경로가 import 되나 | 함수명 오타 · 리네임 잔재 |
| `slots` == 시그니처 − `SERVER_SUPPLIED` | **선언·구현 드리프트** |
| `SERVER_SUPPLIED`를 전부 받나 | 공역이 `namespaced`를 안 받으면 호출이 깨진다 |

> 셋째가 핵심이다. application에 필터가 추가되면 옛 형태는 **조용히 안 넘겼고**,
> 호출자는 걸렀다고 믿고 안 걸러진 행을 받았다.

**검사 축이 얻는 것**: 검사 조회에서 같은 사고가 원천 차단된다.

**못 잡는 것**: 정의를 **안 쓰고 인라인 재구현**하는 경우 → 2층

### 4.2 2층 — 리터럴 금지 (신설)

**근거는 추측이 아니라 실제 사고다.** 마인드봄 `apps/web/.../core/status.ts` 주석:

> 실제로 SCT 결과 화면이 이 목록을 인라인으로 재구현하면서 completed를 빠뜨려,
> 완료된 검사에 '검사 확정' 버튼이 다시 뜨는 회귀가 있었다.

한 팀·한 레포·한 언어에서 일어났다. 조직이 나뉘면 **발견되지 않는 쪽**으로 간다.

- 금지 1: 상태 문자열 리터럴 (`'confirmed'` 등) — 생성 파일 외
- 금지 2: 술어 배열 인라인 (`['confirmed','report_generated',…].includes(…)`)

**실측 규모**: 마인드봄 상태 문자열 산재 = 백엔드 112곳 + 프론트 83곳 = **195곳**.

### 4.3 3층 — 적합성 표 (핵심)

$f(a \cdot b) = f(a) * f(b)$를 **전수**로 검증한다.

```json
// conformance/transitions.json — 7×7 = 49쌍 전부
[
  {"from": "confirmed",      "to": "report_generated", "allowed": true},
  {"from": "confirmed",      "to": "completed",        "allowed": false},
  {"from": "ai_draft_ready", "to": "under_review",     "allowed": true},
  {"from": "ai_draft_ready", "to": "in_progress",      "allowed": true}
]
```

표본이 아니라 전수. 상태 축은 검사가 18종으로 늘어도 7종 그대로다(조합 폭발은 검사 종수가 아니라
상태 종수를 따른다).

**양쪽 스택이 같아 검증 코드를 한 벌만 쓴다** — 둘 다 FastAPI + SQLAlchemy 2.0 + Pydantic 2 + pytest.

### 4.4 4층 — 런타임 관측

- DB에 선언이 모르는 `status` 값이 있으면 **감사 로그에 경고**
- 전이 시 규칙과 대조해 위반이면 **차단이 아니라 기록**

CLAUDE.md §3.3이 요구하는 "실제 세계를 올바르게 투영하고 있는가"의 상시 점검.

### 4.5 기존 감사 스크립트와의 연결 (ontology.md §8)

> **배선 — 현재 미완**: agent 노출·감사가 이 경로를 아직 모른다. 노출 시 함께 갱신:
> - `core/tool_registry._iter_handler_modules` 스캔 루트에 추가
> - `scripts/audit_query_filters.py`의 tool→모듈 경로 매핑

검사 축을 붙일 때 이 둘을 함께 갱신해야 한다. 안 하면 `custom_param_gaps`·
`date_filter_completeness_gaps`·`sort_completeness_gaps` 감사가 검사 축을 못 본다.

## 5. 데이터 소유 — 무엇을 버리고 무엇을 지키는가

"연산을 소유한 쪽이 상태를 소유한다"로 판정한다(§0.1).

### 5.1 버린다 — 마인드봄 시연용 테이블

| 마인드봄 | 플랫폼 대응 | 근거 |
|---|---|---|
| `institutions` (6필드) | `center/center` + 운영시간·룸·프로그램 등 10개 서브모듈 | 기관 운영 연산이 플랫폼 소유 |
| `members` (6필드) | `center/member` + 근무시간·초대, 별도 `role/role_permission` | 멤버십 연산이 플랫폼 소유 |
| `clients` (11필드) | `client/profile` + 관계·형제·연동요청 등 7개 서브모듈 | 내담자 등록·연동 연산이 플랫폼 소유 |
| `accounts` | `person/person` + `person_profile` | 인증 연산이 플랫폼 소유 |
| **`examination_batteries`** | `assessment_cases` (+`sets`·`packages`) | 묶음 관리 연산이 플랫폼 소유 — **§5.5** |

플랫폼 `Client`에는 `person_id`가 있어 **한 사람이 여러 센터에 존재**하는 구조를 다룬다.
마인드봄에는 그 개념이 없다.

**ontology.md 안티패턴 준수**:

> 기관 종류별 handler·facade·테이블 분화(`query_student`·`SchoolFacade`·`students`)
> → 개념 하나로 흡수, 갈리는 건 선언 데이터

마인드봄이 `clients`를 따로 갖는 것이 이 안티패턴의 변형이다. 개념 하나로 흡수한다.

### 5.2 지킨다 — 검사 연산이 소유한 것

| 대상 | 근거 |
|---|---|
| `examinations`의 참조 컬럼 | 복사본이 아니라 **"이 검사가 누구 것인가"** 참조. 단 플랫폼 id 체계로 전환 |
| 상태 머신 (`VALID_TRANSITIONS`) | `confirm` 연산의 정본. CDSS 원칙의 실체 |
| progress 축 | `submit` 완료 판정. 데이터 구조를 뒤지는 로직이라 선언으로 못 내려감 |
| AI job 축 | §1.3의 사상 규칙이 요구한 분리 |
| 검사 접근 권한 판정 (`access.py`) | 기관 규칙이 아니라 **검사 도메인 규칙** |

역할은 플랫폼 `role_permission`에서 받되, **"그 역할이 이 검사에 접근 가능한가"의 판정은
마인드봄이 한다.** 넘기면 CDSS 원칙이 플랫폼 권한 시스템에 녹는다.

### 5.3 재작업 — 조인이 끊긴다

마인드봄 검사 조회는 현재 `Client`를 직접 조인한다:

```python
# common/repository.py:98-103
Client.name.label("client_name"),
Client.birth_date.label("client_birth_date"),
Client.gender.label("client_gender"),
.outerjoin(Client, Examination.client_id == Client.id)
```

`client_id` 참조는 검사 모듈에만 **101곳**. 생년월일·성별은 규준 적용에 쓰이는 임상 데이터다.

**다만 규약이 답을 일부 정해준다** — naming.md 참조 아키타입은 "포함 + name(D14)"과
"이름은 해당 query로 id 확인 후" 체이닝 gloss를 요구한다. 즉 **이름 필터는 금지, id 필터가 정본**이다.
현재 마인드봄의 `Client.name.ilike()` 검색은 이 규약과 어긋나므로, 런타임 분리 여부와 무관하게
**체이닝 방식으로 재설계**해야 한다.

| | 조회 경로 | 재작업 |
|---|---|---|
| 같은 런타임 | 플랫폼 handler 직접 호출 | 조인 유지 가능 |
| 분리 | ontology API | 조인 불가 — 이름 투영을 D14 방식으로 |

### 5.4 검사 정의 — 플랫폼 `assessments`가 정본 (2026-08-18 실측 정정)

**초안 §4.5와 본 문서 이전 판이 "카탈로그 신설"로 본 것은 부정확하다.**
플랫폼에 검사 정의 테이블이 이미 있고, 채택 구조와 채점 엔진 프로토콜까지 갖춰져 있다.

```python
# modules/assessment/assessment/models.py
class Assessment(BaseModel):
    __tablename__ = "assessments"
    code, version, kor_name, eng_name, assessment_type, description,
    duration, age, status, workflow_type, external_url, supports_online,
    definition: Mapped[dict] = mapped_column(JSONB, ...)
```

| 층위 | 상태 | 비고 |
|---|---|---|
| 테이블·스키마 | **있음** | `assessments` |
| 채택 | **있음** | `center_assessments` — `uq_center_assessment(center_id, assessment_id)` |
| 엔진 프로토콜 | **있음** | `AssessmentEngine` — `validate_responses`·`calculate_scores`·`interpret` |
| 엔진 구현체 | **2종** | `smartphone_addiction` · `smartphone_overdependence_adult` |
| `(code, version)` 복합 유일 | **없음** | AS-1 갭 — 아래 |
| 4축 | **없음** | AS-2 갭 — 아래 |
| 라이센스·판권 | **없음** | |
| 규준(norm) | **없음** | |

#### AS-1 갭 — 개정판 병존 불가 (코드 확인)

```python
Index("uq_assessments_code_active", "code", unique=True,
      postgresql_where=text("deleted_at IS NULL"))
```

`version` 컬럼은 **존재하나 유니크에 포함되지 않는다.** `code`만 활성 유일이라
같은 검사의 개정판이 동시에 존재할 수 없다 — 초안의 "표시 라벨뿐" 판정이 정확하다.

**소급 불변 요구**(AS-1): 규준 개정 시 정의 행을 고치지 않고 새 행을 만들어야
과거 실시가 옛 규준을 계속 가리킨다. 현재 구조로는 불가능하다.

#### AS-2 갭 — 축이 2값 + 불리언 하나

| 초안의 4축 | 현행 대응 | 판정 |
|---|---|---|
| 응답 주체 (본인·관찰자·검사자) | **없음** | 신설 |
| 실시 채널 (온라인·대면·외부) | `supports_online` 불리언 | 축 아님 |
| 채점 방식 (엔진·전문가·외부수신) | `workflow_type` 2값(`self_report`·`external_service`) | 압축됨 |
| 산출물 (점수·소견·PDF) | `workflow_type`에 뒤섞임 | 분리 필요 |

`workflow_type`을 4축의 압축 캐시로 취급한다는 초안 AS-2의 판단이 코드와 맞다.

#### "수백 종"의 정체 — 앞으로 등록될 목표치

**이관할 자산이 아니다.** 실제 등록된 것은 채점 엔진 2종이며, 시드 파일
(`scripts/seed/develop/assessment.py`)은 케이스·회기 픽스처지 검사 정의 시드가 아니다.

따라서 회의 안건은 "누가 카탈로그를 만드나"가 아니라 **"기존 `assessments`를
AS-1·AS-2에 맞게 개조하는 작업을 누가·언제 하나"**다.

#### 마인드봄이 해야 할 일

| 작업 | 내용 |
|---|---|
| `exam_type` → `assessment_id` 전환 | `String(20)` 평문 3값을 `assessments` 참조로. naming.md 참조 아키타입 적용 |
| 3종 등록 | HTP·Rorschach·SCT를 `assessments` 행으로. `assessment_type = projective` 이미 존재 |
| 산출물 축 분리 요구 | 투사검사는 `workflow_type`의 2값 어디에도 안 들어간다(자가응답 아니고 외부서비스도 아님) — 세 번째 값 또는 4축 분해가 선행돼야 등록 가능 |

**의존 관계**: 3종 등록은 AS-2 개조에 막혀 있다. 현행 `workflow_type` 2값 체계에서는
투사검사를 표현할 자리가 없다.

### 5.5 검사 묶음 — `examination_batteries` 폐기, 우리는 task 하나에 집중

#### 대응 관계

```
플랫폼  assessment_cases ──┬─→ task (HTP)       ──→ 마인드봄 Examination
        (묶음·배정·발송)     ├─→ task (Rorschach) ──→ 마인드봄 Examination
                            └─→ task (SCT)        ──→ 마인드봄 Examination
```

**마인드봄 `Examination` 1건 = 플랫폼 `assessment_task` 1건.**
초안 §1의 판단과 같다 — "개별 실시(Administration) … 실시·채점의 실체는 채널에 따라 마인드봄".

#### 플랫폼 묶음 개념은 3층이다

| 개념 | 성격 | 엔드포인트 | 마인드봄 |
|---|---|---|---|
| `assessment_sets` | **템플릿** — 자주 쓰는 조합 재사용 | 5개 | 없음 |
| `assessment_packages` | 템플릿 + **가격**(판매 단위) | 5개 | 없음 |
| `assessment_cases` | **실시 인스턴스** — 실제 배정된 건 | 10개 | `ExaminationBattery` |

`ExaminationBattery`는 3층 중 맨 아래 하나만, 그것도 얕게 구현한 것이다.

#### 현행 `battery_id`는 땜빵이다 (실측)

| 확인 | 결과 |
|---|---|
| 종합보고서가 배터리를 쓰는가 | **아니오** — `comprehensive_report`·`report` 모듈 grep **0건** |
| 종합보고서의 실제 수집 기준 | `_list_eligible_exams(client_id)` — 내담자의 확정 검사 **전부** |
| 프론트 트리거 | 배터리로 묶어 보여주고 `?ids=1,2,3` **URL 쿼리로 전달** |
| `ExaminationBattery` 행 | `create_battery`가 만들고 — **그 뒤 아무도 읽지 않음** |
| 배터리 `status` | 컬럼은 있으나 갱신 코드 없음 |

즉 배터리는 "같이 등록했다"는 **그룹 라벨**일 뿐이고, 실제 종합보고서 대상은
쿼리스트링이 정한다. 테이블까지 판 것치고 하는 일이 목록 묶어 보여주기뿐이다.

#### 플랫폼 `assessment_cases`는 실물이 있다

| 기능 | 마인드봄 | 플랫폼 |
|---|---|---|
| 상태 자동 갱신 | 없음 | `sync_case_status.py` — task 세어 case 상태 유도 |
| 완료 판정 | 없음 | **전 태스크 종결 시 케이스 자동 완료** |
| 참여자 | 없음 | `assessment_case_participants` (다형, 3 엔드포인트) |
| 링크 발송 | 없음 | `send_link` 8개 — 재발송·전달이력 |
| 결과지 발송 | 없음 | `send_result` 6개 — 무인증 코드 열람 |
| 회기·일정 | 없음 | `assessment_sessions` 8개 → `schedules` |

우리가 `battery_id`로 하려던 "묶음이 다 끝났나" 판정이 저쪽엔 이미 있다.

#### 결정

**`examination_batteries` 폐기.** 묶음 관리 연산(배정·발송·완료판정)이 전부 플랫폼에 있으므로
§5.1과 같은 근거다 — **연산을 소유한 쪽이 상태를 소유한다**.

| 대상 | 처리 |
|---|---|
| `examination_batteries` 테이블 | 폐기 |
| `Examination.battery_id` | `case_id`로 대체 (플랫폼 `assessment_cases` 참조) |
| `create_battery` API·서비스 | 폐기 — 묶음 생성은 플랫폼 `assessment-cases/batch` |
| 프론트 배터리 그룹핑 UI | `case_id` 기준으로 전환 |

#### 다만 종합보고서는 우리 소관이다

묶음 자체는 플랫폼 것이지만, **여러 task를 가로질러 해석하는 일**은 CDSS 영역이라 우리가 갖는다.
그래서 case를 아예 모를 수는 없고 `case_id` 참조가 필요하다 — "이 case의 확정된 task들"을 물어야 하므로.

| 축 | 소유 | 마인드봄의 관여 |
|---|---|---|
| 묶음 자체 (배정·발송·완료판정) | 플랫폼 `case` | 관여 안 함 |
| 개별 실시·채점·CDSS | **마인드봄** | `Examination` = task |
| 종합 해석 (묶음 가로지름) | **마인드봄** | `case_id`로 형제 task 조회 |

현행 `?ids=1,2,3` 쿼리스트링 전달도 임시 방편이므로 함께 정리 대상이다.

#### ~~실측 — 종합보고서의 대상 범위가 이미 어긋나 있다~~ → 해소(2026-08-19)

> **결정: 종합보고서는 case 단위다.** 위 회의 안건이 이렇게 닫혔다.

당시 실측은 종합보고서 백엔드가 **두 벌**이었기 때문에 나온 것이다:

| 모듈 | 대상 결정 방식 | 프론트 호출 |
|---|---|---|
| ~~`examination/report`~~ (구) | `_list_eligible_exams(client_id)` — **client 단위** | 0건 |
| `comprehensive_report` (현행) | `comprehensive_report_examinations` 조인 — **대상을 명시 보관** | 사용 중 |

client 단위인 구 모듈이 case 원칙과 충돌했고, 아무도 부르지 않으면서 API만 열려 있었다.
**구 모듈 폐기**(라우터·facade·models·테이블 `comprehensive_interpretations`, 데이터 0행)로
경로가 하나만 남아 불일치가 사라졌다. 현행 `generate_draft`는 링크된 검사만 읽으므로
화면과 해석 대상이 같다.

프론트도 함께 정리했다 — 내담자 상세의 **검사 체크박스·임의 조합 진입을 제거**하고
배터리(묶음) 단위 진입만 남겼다. "무엇을 묶을지"는 묶음이 정하는 것이지 화면에서
그때그때 고를 일이 아니기 때문이다.

남은 것은 `battery_id` → `case_id` 전환(착수순서 9)뿐이고, `battery_id`가 그 자리표
역할을 하므로 전환 시 진입 함수 한 곳만 바꾸면 된다.

### 5.6 도메인 간 연동 지점 (API 관계도 실측)

`API-관계도-캔버스.html`의 엣지 데이터에서 검사 도메인이 걸리는 지점은 4개다.
전부 우리가 task를 맡으면 **함께 넘어오거나 붙어야 하는 것**이다.

| 관계 | 종류 | 마인드봄 영향 |
|---|---|---|
| `assessment_task` → `docs` "결과지 PDF 문서 저장" | **tx** | **§5.6.1** — 우리는 저장하지 않는다 |
| `send_link` → `comm` "응답 링크 알림톡" | event | 자가보고 경로 — 플랫폼 잔류(§6) |
| `send_result` → `comm` "결과지 알림톡" | event | 결과지 발송은 플랫폼 소관 |
| `assessment_case` → `client.profile` "검사 참여자" | ref | case 소유가 플랫폼이므로 그대로 |

#### 5.6.1 PDF — 우리는 생성만, 저쪽은 영속화

| | 마인드봄 | 플랫폼 |
|---|---|---|
| 생성 | on-demand | on-demand |
| 저장 | **안 함** — `Response(media_type="application/pdf")` 즉시 스트리밍 | `documents` 테이블 (`storage_path`·`checksum`·`file_size`) |
| 접근 제어 | 세션 인증만 | `access_level` + `document_access` |
| 외부 공유 | 없음 | `share_token` — 만료·다운로드 상한·비밀번호 |
| 태스크 연결 | 없음 | `assessment_tasks.report_document_id` |

초안 §4.5가 "PDF ← 비저장 on-demand 생성이라 **전송 시점 계약 신설**"이라 한 지적이 정확하다.
통합 시 우리가 만든 PDF를 저쪽 `documents`에 넣고 `report_document_id`를 채워야
결과지 발송·보호자 열람이 성립한다.

> **SaMD 관점 추가 사안**: `checksum`이 있다는 것은 **문서 무결성 검증**이 가능하다는 뜻이다.
> 우리 쪽은 재생성할 때마다 결과가 달라질 수 있는데(LLM 편집분 반영),
> "그때 발급한 그 보고서"를 재현·증명해야 하는 요구가 있다면 저장이 필수다.
> 현행 비저장 구조는 감사추적 관점에서 약하다.

### 6.2 규약 관련 확인

| 항목 | 내용 |
|---|---|
| `publish` 동사 | 보고서 발행이 통제어휘에 없다. `create_report`로 표현할지, loop 결정 로그에 등재할지 |
| `administer`·`score` | 동사로 쓰려면 등재 필요. 현재는 progress 축·분류로 처리 가능 판단 |

| D2 결번 | DECISIONS.md에 D1 다음이 D3 |
| `aggregate` 키 집합 | ontology.md §6이 "아직 안 묶여 있다 — 공역마다 달라지기 시작하면 같은 누수가 재발"이라 경고. 검사 축이 첫 확장이면 여기서 묶어야 할 수 있음 |
