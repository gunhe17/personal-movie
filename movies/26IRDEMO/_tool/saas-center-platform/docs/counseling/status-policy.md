# 상담 상태 정책 (3단계 혼란 방지)

> 케이스·세션·참여자 3단계 상태를 사용자 관점에서 혼란 없이 설계하기 위한 정책

---

## 0. 문서 구조

이 문서는 **추상 → 몰입 → 규칙** 순으로 구성됩니다.

| 단계 | 목적 | 독자가 얻는 것 |
|------|------|----------------|
| **추상 (§1)** | 설계 철학, 원리 | "왜 이렇게 해야 하는가" |
| **몰입 (§2)** | 구체적 사용 시나리오 | "실제로 어떤 느낌인가" |
| **규칙 (§3~)** | 데이터·표현·조작 규칙 | "무엇을 어떻게 할 것인가" |

규칙만 따르면 표면은 맞출 수 있지만, **추상과 몰입**을 먼저 공유해야 일관된 판단이 가능합니다.

---

## 1. 추상: 설계 철학

### 1.1 근본 질문

상담 상태 설계의 출발점은 다음 질문입니다.

> **"상담사가 기록할 때, 머릿속에 떠오르는 것은 무엇인가?"**

데이터 구조(케이스/세션/참여자)가 아니라, **사용자의 인지 모델**이 먼저입니다.

### 1.2 설계 원리 (Abstraction)

| 원리 | 의미 | 함의 |
|------|------|------|
| **단일 질문** | 한 시점에 사용자가 답하는 질문은 하나 | 화면을 "이 질문에 답하는 곳"으로 설계 |
| **맥락 의존** | 같은 "상태"라도 보는 맥락에 따라 의미가 다름 | "완료"가 회기 맥락이면 "진행됨", 상담 맥락이면 "종결" |
| **행동 우선** | 상태는 "결과"이지 "목표"가 아님 | "회기 완료하기"가 목표, "completed"는 그 결과 |
| **되돌림 가능** | 실수해도 복구할 수 있어야 함 | 취소·확인 흐름, 재예약 가능성 명시 |

### 1.3 3단계가 필요한 이유 (모델 정당화)

왜 케이스·세션·참여자 3단계인가?

- **케이스**: "이 내담자와의 상담 관계가 지금 어떻게 되어 있나" — **관계 수준**
- **세션**: "이 날짜의 예약이 어떻게 됐나" — **일정 수준**
- **참여자**: "이 사람이 이 날 왔나" — **출석 수준**

세 단계는 **서로 다른 시간·공간 단위**를 다룹니다. 케이스는 수주~수개월, 세션은 그날, 참여자는 그 순간.  
이 구분이 없으면 "상담 취소"와 "회기 취소"를 같은 것으로 착각하게 됩니다.

## 2. 몰입: 사용자 여정

### 2.1 시나리오 A: "오늘 상담 끝났어"

**상황**: 오후 3시, 1:1 상담이 막 끝났다. 상담사는 일지를 쓰기 전에 먼저 기록해야 할 것이 있다.

**순간별 흐름**:

1. **진입**: 상담 상세 화면. "오늘 회기"가 눈에 들어온다.
2. **기대**: "이 회기 완료 처리해야지" — **세션 상태**를 바꾸려는 의도.
3. **혼란 포인트**: "완료" 버튼이 여러 곳에 있으면 — 상담 전체? 이 회기? — 멈춘다.
4. **이상적**: "이 회기 완료"가 한 곳에만 있고, 클릭 시 "출석 체크했어?" 같은 자연스러운 다음 단계가 보인다.

**몰입 관점**: 상담사는 **"회기"** 단위로 생각한다. "케이스"는 의식하지 않는다. UI가 케이스/세션을 동시에 보여주면 인지 부하가 생긴다.

### 2.2 시나리오 B: "내담자가 안 왔어"

**상황**: 예약 시간이 지났는데 연락이 없다. 노쇼로 처리하려 한다.

**순간별 흐름**:

1. **진입**: 해당 회기 선택.
2. **기대**: "노쇼" 처리 — **세션**을 한 번에 바꾸려는 의도.
3. **혼란 포인트**: "내담자별로 출석을 먼저 체크해야 하나?" — 집단이면 더 복잡.
4. **이상적**: "회기 노쇼" 한 번에 처리. 내담자 출석은 시스템이 자동 반영. "전원 불참으로 처리됩니다"만 확인하면 된다.

**몰입 관점**: 노쇼는 **세션 단위 결정**이다. 참여자별 출석을 먼저 하게 만들면 단계가 늘어나고, "왜 내가 하나씩 바꿔야 하지?"라는 불만이 생긴다.

### 2.3 시나리오 C: "확인 취소했는데 바뀌었어"

**상황**: 회기 상태를 "취소"로 바꾸려다, 확인 모달에서 "취소" 버튼을 눌렀다. 그런데 화면에는 취소로 바뀌어 있다.

**순간별 흐름**:

1. **의도**: "아, 생각 바꿨어. 안 할래." → 모달의 "취소" 클릭.
2. **기대**: 아무것도 바뀌지 않아야 한다.
3. **실제**: 상태가 바뀌어 있다.
4. **감정**: "내가 뭘 잘못 눌렀지?" → 불신, 다시 확인하는 습관 생김.

**몰입 관점**: "취소"라는 단어가 **모달에서는 "작업 취소"**, **회기 상태에서는 "회기 취소"**로 쓰인다. 같은 단어, 다른 의미. 사용자는 맥락으로 구분해야 하는데, 모달 안에서는 "작업 취소"가 자연스럽다. **모달의 취소 = 작업 취소**가 반드시 지켜져야 한다.

### 2.4 몰입에서 도출되는 원칙

- **작업 단위와 화면 단위를 맞춘다**: "이 회기 완료" 하려면, 그 작업에 필요한 것만 보여준다.
- **시스템이 추론할 수 있는 것은 사용자에게 묻지 않는다**: 노쇼 시 전원 불참은 자동.
- **확인/취소 버튼의 의미는 맥락에서 일관된다**: 모달의 "취소" = "이번 작업 안 함".

### 2.5 몰입 → 규칙 연결

| 시나리오 | 적용 원리 (§1) | 대응 규칙 (§5~8) |
|----------|----------------|------------------|
| A: 회기 완료 | 단일 질문, 행동 우선 | §7.1 표시 위치, §8.2 조작 순서 |
| B: 노쇼 처리 | 행동 우선, 시스템 추론 | §6.2 계층 간 연동, §6.4 참여자 혼재, §8.3 확인 모달 |
| C: 모달 취소 | 되돌림 가능, 맥락 일관 | §8.3 확인 모달 (취소=abort) |

## 3. 정책의 관점

**주의**: 이 문서는 (1) **데이터/비즈니스 규칙**과 (2) **UX/UI 가이드라인**을 함께 다룹니다.  
현재 일부 내용은 기존 구현을 기준으로 작성되었을 수 있습니다. **§1~2의 철학·몰입**을 우선으로 검토·수정할 것을 권장합니다.

## 3-1. UX/UI 우선 원칙 (§1~2 원리 적용)

### 사용자 작업 관점 (Task-based)

| 사용자 목표 | 필요한 정보 | 혼란 포인트 |
|-------------|-------------|-------------|
| "오늘 상담 끝났어, 기록해야지" | 이 회기 완료 처리, 출석 체크 | 세션 "완료" vs 케이스 "종결" 구분 |
| "내담자가 안 왔어" | 회기 노쇼 처리 | 세션 상태 vs 내담자별 출석 |
| "이 상담 더 이상 안 해" | 상담 취소 | 케이스 취소 vs 회기 취소 |
| "다음 회기 예약 바꿔야 해" | 회기 일정 변경/취소 | 회기 취소 = 재예약 가능 |

**원칙**: UI는 **"무엇을 하려는가"**에 맞춰 정보를 제공한다. 데이터 구조(케이스/세션/참여자)를 그대로 노출하지 않는다.

### 인지 부하 감소

- **한 화면에 한 가지 질문**: "지금 이 화면에서 사용자가 답해야 할 질문은 하나"
- **점진적 노출**: 맥락에 맞는 정보만 표시. 필요 시 펼쳐서 상세 확인
- **행동 유도**: "다음에 할 일"이 명확해야 함 (예: "출석 체크 후 회기 완료")

### UX 검토 질문 (정책 수립 시)

1. 사용자가 **가장 자주 하는 작업**은? 그 작업에 필요한 정보만 먼저 보여주는가?
2. **실수로 바꾸기 쉬운** 조작은? 확인·되돌리기가 있는가?
3. **같은 단어**가 다른 의미로 쓰이는 곳은? 사용자가 구분할 수 있는가?
4. **검사(Assessment)** 화면과 비교했을 때, 상담만 다르게 느껴지는 부분은 없는가?

## 3-2. 피드백 대응 현황

| 피드백 | 정책 반영 | 구현 현황 |
|--------|-----------|-----------|
| **진행/완료/취소 구분 모호** | §5.1~5.3 계층별 라벨 분리 (종결 vs 완료 vs 취소) | ⚠️ 케이스 "종결" 미적용 |
| **3단계 상태 혼란** | §4.1 계층별 의미·질문 정의, §7.1 표시 위치 | ⚠️ 참여자 "대기" 미적용 |

## 4. 규칙: 핵심 원칙 (§1~2 → 구체화)

아래 규칙은 §1 설계 철학과 §2 몰입 시나리오를 **구체적인 결정**으로 옮긴 것입니다. 규칙을 바꿀 때는 "어떤 원리가 깨지는가"를 먼저 확인하는 것이 좋습니다.

### 4.0 데이터 vs 표현 구분

| 구분 | 내용 | UX 의존 |
|------|------|---------|
| **데이터 규칙** | 케이스/세션/참여자 각각 어떤 상태값을 가지는가, 전이 조건은 | 낮음 (시스템 제약) |
| **표현 규칙** | 어떤 라벨을 쓸지, 어디에 보여줄지, 몇 단계를 동시에 노출할지 | 높음 (UX 결정) |

정책 문서의 §5~6은 **데이터 규칙**, §7~8은 **표현 규칙**에 가깝습니다. 표현 규칙은 사용자 테스트로 검증·수정하는 것이 좋습니다.

### 4.1 "상태"가 3곳에 있다는 것의 의미

| 계층 | 의미 | 질문 |
|------|------|------|
| **케이스** | 이 상담 전체가 어떻게 되었나? | "이 내담자의 상담은 지금 진행 중인가, 끝났는가?" |
| **세션** | 이 회기가 어떻게 되었나? | "1월 10일 3회기는 실제로 했는가, 취소했는가?" |
| **참여자** | 이 내담자가 이 회기에 왔는가? | "김OO는 3회기에 출석했는가, 불참했는가?" |

**정책**: 각 계층의 상태는 **서로 다른 질문**에 답한다. 같은 값(예: completed)이라도 **의미가 다르다**.

## 5. 계층별 상태값 정리

### 5.1 케이스 (상담 전체)

| DB 값 | UI 라벨 | 의미 | 변경 시점 |
|-------|---------|------|-----------|
| `active` | 진행중 | 상담이 진행 중 | 상담 생성 시 기본값 |
| `completed` | 종결 | 상담 목표 달성, 종결 | 상담사가 "상담 종결" 처리 시 |
| `cancelled` | 취소 | 상담 자체가 취소됨 | 상담사가 "상담 취소" 처리 시 |

**용어 정책**: 케이스의 `completed`는 **"종결"**로 표기 (회기 "완료"와 구분)

---

### 5.2 세션 (회기 단위)

| DB 값 | UI 라벨 | 의미 | 변경 시점 |
|-------|---------|------|-----------|
| `scheduled` | 예약 | 예약됨, 아직 진행 전 | 회기 추가 시 기본값 |
| `completed` | 완료 | 회기가 실제로 진행됨 | 상담 후 "회기 완료" 처리 |
| `no_show` | 노쇼 | 예약했는데 내담자 미참석 | 내담자 미참석 시 |
| `cancelled` | 취소 | 회기 취소(재예약 가능) | 일정 변경/취소 시 |

**용어 정책**: 세션의 `completed`는 **"완료"**로 표기 (케이스 "종결"과 구분)

---

### 5.3 참여자 (출석)

| DB 값 | UI 라벨 | 의미 | 변경 시점 |
|-------|---------|------|-----------|
| `scheduled` | 대기 | 출석 확인 대기 | 회기 생성 시 기본값 |
| `attended` | 참석 | 출석함 | 출석 체크 시 |
| `absent` | 불참 | 불참 | 불참 처리 시 |

**용어 정책**: 참여자의 `scheduled`는 **"대기"**로 표기 (출석 확인 대기).  
`late`(지각), `excused`(사유 불참)는 UI 옵션에서 제외.

## 6. 혼란 포인트와 해결 방안

### 6.1 같은 단어, 다른 의미

| 단어 | 케이스 | 세션 | 참여자 |
|------|-------|------|--------|
| completed | 상담 종결 | 회기 완료 | (없음) |
| cancelled | 상담 취소 | 회기 취소 | (없음) |
| scheduled | (없음) | 예약됨 | 출석 대기 |

**해결**: UI에서 **접두어 또는 맥락**으로 구분
- "상담 종결" / "회기 완료"
- "상담 취소" / "회기 취소"
- "예약" (회기) / "대기" (출석)

### 6.2 계층 간 연동

| 상황 | 처리 |
|------|------|
| 세션 → completed | 대기 내담자만 → attended 일괄 처리 (참석/불참 유지) |
| 세션 → no_show | 참석·대기 내담자 → absent 일괄 처리 |
| 세션 → cancelled | 참여자 상태 변경 없음 (기록 보존, 재예약 시 참고) |
| 케이스 → completed | 예약된 세션 있으면 오류 (먼저 처리 필요) |
| 케이스 → cancelled | 예약된 세션 있으면 오류 (먼저 처리 필요) |

**정책**: 하위 계층 상태가 확정되지 않으면 상위 변경 시 확인 모달 표시

### 6.3 집단 상담: 일부 참석, 일부 불참

| 상황 | 세션 상태 | 참여자 상태 예시 |
|------|-----------|------------------|
| A 참석, B 불참 | **completed** | A=참석, B=불참 |
| 전원 불참 | **no_show** | A=불참, B=불참 |

**판단 기준**:
- **completed**: 1명 이상 참석 → 회기가 진행됨
- **no_show**: 전원 불참 또는 사유 불참 → 회기가 진행되지 않음

참여자 출석을 전원 확정한 뒤, 위 기준으로 세션 상태를 자동 제안한다.

### 6.4 참여자 상태 혼재 시 세션 변경

참석·불참·대기가 섞여 있는 상태에서 사용자가 **세션 상태를 직접 변경**할 때의 처리 규칙.

| 참여자 혼재 예시 | 세션 변경 | 참여자 처리 | 확인 모달 |
|------------------|-----------|-------------|-----------|
| A=참석, B=불참, C=대기 | → 완료 | C만 attended로 일괄 처리. A·B 유지 | "대기 내담자(C)를 참석으로 일괄 처리합니다" |
| A=참석, B=불참 (전원 확정) | → 완료 | 변경 없음 | (없음, 바로 적용) |
| A=참석, B=대기 | → 노쇼 | A·B 모두 absent로 일괄 처리 | "내담자 전원을 불참으로 일괄 처리합니다" (기존 참석 기록 덮어쓰기 경고) |
| A=참석, B=불참 | → 노쇼 | A만 absent로 변경 (B는 이미 불참) | 동일 |
| (어떤 혼재든) | → 취소 | 참여자 상태 변경 없음 | "회기 취소 (재예약 가능)" |

**원칙**:
- **세션 → 완료**: 대기만 attended로 보정. 이미 확정된 참석/불참은 그대로 둔다.
- **세션 → 노쇼**: 참석·대기 → absent로 덮어쓴다. "노쇼"이므로 기존 참석 기록은 무효화.
- **세션 → 취소**: 참여자 기록은 보존. 재예약 시 참고용으로 활용 가능.

## 7. UI 표시 정책

> ⚠️ **UX 검증 필요**: 아래 내용은 현재 구현을 참고한 권장안입니다.  
> 실제 사용자 테스트·피드백을 통해 "한 화면에 무엇을 보여줄지", "어디에 상태를 둘지"를 재검토할 것을 권장합니다.

### 7.1 표시 위치 (UX 관점)

**질문**: "이 화면을 볼 때 사용자가 궁금한 것은?"

| 화면 | 사용자 질문 | 표시할 상태 | 비고 |
|------|-------------|-------------|------|
| **상담 상세 진입** | 이 상담 전체 흐름은? | 미표시 | 세션·참여자 중심으로 단순화 |
| **회기 목록** | 각 회기는 어떻게 됐어? | 세션 상태 | 예약/완료/노쇼/취소 |
| **회기 상세 (내담자 카드)** | 이 회기에 누가 왔어? | 참여자 상태 | 대기/참석/불참 |

**원칙**: 한 화면에서 **동시에 보이는 "상태" 개념은 최대 2단계**. 3단계를 한꺼번에 보여주지 않는다.

### 7.2 라벨 매핑 (UI 표시용)

```
[케이스]
active     → "진행중"
completed  → "종결"
cancelled  → "취소"

[세션]
scheduled  → "예약"
completed  → "완료"
no_show    → "노쇼"
cancelled  → "취소"

[참여자]
scheduled  → "대기"
attended   → "참석"
absent     → "불참"
```

### 7.3 색상 정책

| 의미 | 색상 | 적용 대상 |
|------|------|-----------|
| 진행/예약/대기 | 파랑 계열 | active, scheduled |
| 완료/참석 | 초록 계열 | completed, attended |
| 취소/불참/노쇼 | 빨강/회색 계열 | cancelled, absent, no_show |

## 8. 조작 흐름 정책

### 8.1 변경 가능 조건

| 대상 | 변경 가능 조건 |
|------|----------------|
| 케이스 상태 | 예약된 세션이 없어야 함 (completed/cancelled로 전환 시) |
| 세션 상태 | 해당 세션의 날짜/시간이 지났거나, 수동 변경 의도가 있을 때 |
| 참여자 상태 | 세션이 completed/no_show/cancelled가 아닐 때 |

### 8.2 권장 조작 순서

1. **회기 진행 후**: 참여자 출석 체크 → 세션 "완료"
2. **노쇼 시**: 세션 "노쇼" (참여자 자동 absent)
3. **회기 취소 시**: 세션 "취소"
4. **상담 종결 시**: 모든 회기 처리 후 → 케이스 "종결"

### 8.3 확인 모달 표시

| 변경 | 확인 모달 |
|------|-----------|
| 세션 → 완료 | 대기 내담자 있으면 "대기 내담자(이름)를 참석으로 일괄 처리합니다" (§6.4) |
| 세션 → 노쇼 | "내담자 전원을 불참으로 일괄 처리합니다" (참석·대기 → absent 덮어쓰기) |
| 세션 → 취소 | "회기 취소 (재예약 가능)" |
| 케이스 → 종결 | 예약 회기 있으면 오류, 없으면 확인 |
| 케이스 → 취소 | 예약 회기 있으면 오류, 없으면 확인 |

### 8.4 청구(Billing) 연동

세션 취소 시 참여자 상태는 유지하지만, **청구는 세션 상태를 기준**으로 한다.

| 세션 상태 | 청구 대상 | 비고 |
|-----------|-----------|------|
| completed | attended 참여자만 | 청구 가능 |
| no_show | 없음 | 노쇼 |
| cancelled | **없음** | 세션 취소 = 회기 취소, 청구 제외 |
| scheduled | 없음 | 미실시 |

**원칙**:
- **세션 상태 우선**: `cancelled`이면 참여자가 attended여도 청구 대상 아님.
- **참여자 상태**: 세션이 `completed`일 때만 의미 있음 (attended → 청구).

**세션 취소 시 기존 청구 처리**:
- 이미 해당 세션으로 PaymentRecord가 생성된 경우 → status = `cancelled` 또는 환불 처리.

## 9. 검사(Assessment)와의 차이

| 항목 | 상담 | 검사 |
|------|------|------|
| 케이스 상태 수 | 3개 | 4개 (pending 추가) |
| 세션 "완료" 표현 | completed | attended |
| 세션 "노쇼" 표현 | no_show | noshow |
| 참여자 상태 | 5개 (late, excused 포함) | 3개 |

**정책**: 상담·검사 각각 도메인에 맞는 용어 유지. UI 라벨만 사용자 친화적으로 통일.
