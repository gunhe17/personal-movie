## 0. v3에서 무엇이 바뀌었나

| | v3 (07-02) | v4 (07-03) |
|---|---|---|
| 관점 | 내담자에게 **무엇이 오나** (수신 피드) | 내담자가 **무엇을 해야 하나** (할 일) |
| 북극성 | 여정 원장 (ledger) | **여정을 잘 챙기게 하는 도구** — 원장은 그 부산물 |
| 킬러 | 세션 브리핑 (상담사 발행) | **할 일 스택 홈** (센터 기존 운영 데이터 파생) |
| 홈 | 가족 통합 타임라인 (시간 역순) | **할 일 스택** (토스식, 지금→다음 순) |
| 온보딩 | 코드 입력 + OTP + 자동 매칭 | **토큰 초대 3경로** (자동 매칭 폐기) |
| 상담사 의존 | 브리핑 발행 = P1 필수 노동 | **P1은 상담사 신규 노동 제로** |

**진단 (v3의 문제):** 유저가 앱을 열 이유가 전부 공급자(상담사) 노동에 걸려 있었다. 킬러(브리핑)는 상담사가 지치면 죽고, 북극성(원장)은 남이 채워줘야 하는 빈 장부였고, 감정 화력(사진)은 공급자 제약(치료실 촬영 불가)에 갇혔고, "세션마다 발행" 노동 모델이 성립하는 유일한 세그먼트(아동 발달)에 설계가 붙들렸다.

**유지되는 것:** 컴패니언 프레임(톱다운 배포, 07-01), Account→Profile→CenterLink 3층 모델, 6원칙, 센터 유형 중립(아동 발달 = 비치헤드), 디자인 레퍼런스 = 토스.

## 1. 핵심 프레임: 여정 = 해야 할 일들의 연속

토스 홈은 거래내역이 아니라 "지금 할 일"의 스택이다. 상담·발달 여정도 마찬가지다:

- **세션 전** — 예약 확인·변경 대응 / 사전 설문·검사지 작성 / 결제·바우처 확인
- **세션 사이** — 과제(퀘스트) 수행 / 관찰·기분 기록 / 다음 세션 질문 메모
- **세션 후** — 브리핑 확인 / 다음 예약 / 결제
- **여정 레벨** — 검사 결과 확인 / 서류 발급 / 센터 이동 시 기록 공유

앱 = 이 할 일들을 하나씩 해치우게 해주는 도구. 기록(원장)은 할 일을 해낸 **결과로** 쌓인다.

### 결정적 사실 (2026-07-03 백엔드 조사)

**할 일 5종은 이미 SaaS가 생산하고 있고, 이미 문자 링크로 흩어져 날아가고 있다:**

| 할 일 | 공급원 (기존 모델) | 상태 |
|---|---|---|
| 예약 확인 / D-1 | `Schedule` | ✅ 있음 (단, client 연결 필드 확인 필요) |
| 검사 온라인 실시 | `AssessmentSendLink` (verification_code, 알림톡) | ✅ 있음 — 지금도 문자로 발송 중 |
| 검사 결과지 확인 | `AssessmentTask.is_report_visible_to_guardian` + Document | ✅ 있음 |
| 사전 설문 작성 | `FormTemplate`/`FormSend` (SMS 발송) | ✅ 있음 |
| 바우처 잔여 임박 / 결제 | `ClientVoucher.remaining_sessions` / `Payment` | ✅ 있음 |

→ **P1 가치 제안: "문자로 흩어져 있던 할 일들이 모이는 곳."** 상담사 신규 노동 없이 센터의 기존 운영 데이터만으로 홈이 산다.

**신규 구축 필요 (조사 확인):** 내담자/보호자 인증 체계(현재 Account는 상담사·관리자용 이메일 기반뿐, Client↔Account 연결 없음) / 홈워크·퀘스트 모델(전무) / 예약 취소·변경 이력(`cancel_reason` 없음 — "일정의 진짜 가치=예외"인데 백엔드가 예외를 못 담음) / 서류 발급 비즈니스 로직(Document 기반만 있음).

## 2. 자체 질문 리스트와 답 (결정 선언)

### A. 할 일 인벤토리

**A1. 할 일 카드 전체 타입과 공급원은?**

| # | 카드 | 공급원 | Phase |
|---|---|---|---|
| 1 | 예약 D-1 확인 / 임박 안내 | 센터 자동 (Schedule) | P1 |
| 2 | 예약 변경·휴강 대응 | 센터 자동 (백엔드 보강 필요) | P1 |
| 3 | 검사 온라인 실시 | 센터 발행 (기존 링크의 앱 수신) | P1 |
| 4 | 검사 결과지 확인 | 센터 발행 (기존) | P1 |
| 5 | 사전 설문 작성 | 센터 발행 (기존) | P1 |
| 6 | 바우처 잔여 임박 / 결제 | 센터 자동 (기존) | P1 |
| 7 | 관찰기록 남기기 | **유저 자립** (신규, 경량) | P1 |
| 8 | 다음 세션 질문 메모 | **유저 자립** (신규, 경량) | P1 |
| 9 | 브리핑 확인 | 상담사 발행 (신규 노동) | **P1.5로 강등** |
| 10 | 과제(퀘스트) 수행 | 상담사 발행 (신규 모델) | **P1.5** |
| 11 | 서류 발급 (영수증·확인서) | 유저 요청형 (로직 신규) | P1.5 |

**A2. P1에서 데이터가 실존하는 것은?** → 1~6번. 이것만으로 홈이 굴러간다 (상담사 신규 노동 제로 원칙).

**A3. 자립형 최소셋은?** → 7·8번 (관찰기록 + 질문 메모). 센터가 아무것도 안 해줘도 홈이 죽지 않는 바닥. 미연동 모드의 주인공이기도 함.

**A4. 할 일이 없는 날의 홈은?** → "이번 주는 다 챙기셨어요" + 다음 예약 정적 카드 + 최근 기록 한 조각. **빈 홈 = 실패가 아니라 평온** (죄책감 금지의 홈 버전). 채우기용 콘텐츠 금지 (가짜 어포던스 금지).

### B. 죄책감 없는 할 일 (6원칙과의 긴장 해소)

**B1. 생성·만료 규칙:** 모든 카드는 **자연 만료**를 가진다 — 예약 카드는 세션이 지나면 소멸, 설문·검사는 마감일, 퀘스트는 다음 세션까지. 만료 = **조용한 소멸**. 원장에 "놓침" 흔적을 남기지 않는다.

**B2. 미완료 이월의 시각 언어:** 빨간 배지·카운트 금지. 카드가 그대로 남아있는 것 자체가 상태 표현. 색·아이콘은 중립 유지.

**B3. 완료의 보상:** 완료된 카드는 **기록으로 변환되어 원장에 쌓인다** — 할 일→기록의 전환 그 자체가 보상. 집계는 긍정문만 ("이번 주 3개를 챙기셨어요"), 미완료 집계는 어디에도 없음. 스트릭 없음.

**B4. 퀘스트 미수행이 상담사에게 보이나?** → 안 보인다. P1.5 회신도 **완료만 전송**, 미완료는 신호 자체가 없음 (죄책감 금지의 서버측 대칭).

### C. 연결 3경로 (자동 매칭 폐기)

**전제 결정: 전 센터 대상 전화번호 자동 매칭은 폐기한다.** 성립 조건(센터의 번호 입력 품질 × 설치자=등록 번호 주인 × 번호 단일 근거 매칭)이 전부 약하고, 오매칭 리스크를 안는 도박이다. 매칭을 "검색"이 아니라 **"토큰 확인"** 문제로 바꾼다.

**C1. 문자 인프라 실존?** → ✅ MessageLog(SMS/알림톡/LMS) + 템플릿 관리 있음. `AssessmentSendLink`가 토큰 발송 패턴(recipients + verification_code + failed_attempts + revoked_at)을 이미 구현 — **초대 토큰은 이 패턴의 확장으로 구축한다** (자기확장 프로토콜). 단, 예약 리마인더 "자동 발송" 비즈니스 로직은 모델만 준비된 상태 → **P1 선행 과제로 편입**.

- **경로 1 (주경로): 문자 편승 초대.** 이미 나가는 문자(예약 확정·리마인더, 검사·설문 링크)에 고유 토큰 링크를 자동 탑재. 탭 → 설치/열기 → 전화번호 본인인증(토큰의 수신 번호와 대조) → 연결 완료. 토큰이 이미 보호자 Client 레코드를 가리키므로 매칭이 아닌 확인. 번호가 틀리면 문자가 안 갈 뿐, 오연결이 없다. **센터 직원 노동 제로.**
- **경로 2 (현장): 데스크 QR.** 센터가 특정된 상태로 본인인증 → **그 센터 스코프 안에서만** 번호 대조. 실패해도 눈앞의 직원이 즉석 해결 — 데드엔드 없음.
- **경로 3 (fallback): 가족 초대 + 수동 코드.** 아빠·조부모는 이미 연결된 보호자가 앱에서 초대 (센터 노동 0, 대기 0).

**C2. 토큰 규칙:** 1회 claim + 본인인증 이중 게이트, 유효기간, 실패 횟수 제한, revoke 가능 — 전부 AssessmentSendLink 선례 재사용.

**C3. 데스크 QR 실패 시 web 화면:** 승인 "큐"(비동기 대기)가 아니라 **현장 연결 보조 화면** — 직원이 내담자 검색 → 초대 문자 즉석 발송 (기존 발송 패턴).

**C4. 가족 초대 권한:** 초대자와 동일 열람을 기본으로, `ClientRelation.is_primary`(주보호자) 보유자가 초대 권한. 세부 차등은 P2.

**C5. 연결 직후 첫 홈:** 최소 1개 할 일 보장 — 다음 예약 카드(거의 항상 존재). 없으면 1회성 시작 할 일(프로필 확인 등)로 대체. **목표: 설치 후 1분 안에 첫 할 일이 보이는 홈 도착.**

### D. 데이터 모델

**D1. "할 일"은 새 엔티티인가?** → **파생 뷰가 원칙.** 카드 1~6은 원본(Schedule, AssessmentSendLink, FormSend, ClientVoucher…)의 상태에서 파생 — 원본이 바뀌면 카드가 자동 소멸해 정합이 깨질 수 없다. 앱 측에는 열람·완료 view-state만 저장. 신규 엔티티는 퀘스트·브리핑(P1.5)과 관찰기록·메모(유저 소유)뿐.

**D2. 귀속:** 할 일은 **Profile 귀속**(여정의 주체 기준), 공급원 표시는 CenterLink 경유. 자립형 할 일은 CenterLink 없이 성립 (미연동 모드 자동 성립).

**D3. 초대 토큰이 가리키는 것:** 센터 소유의 보호자 `Client` 레코드 → 검증 성공 시 CenterLink 생성, `ClientRelation`을 따라 아동 Profile 연결을 제안.

**D4. 다자녀 홈:** Account 단위 **통합 스택 하나**, 카드에 사람 태그. v3의 "축은 시간 하나, 사람·센터는 태그" 원칙의 액션 버전 — 정렬 축만 시간→긴급도로 바뀜.

### E. 일관성 점검

**E1. 6원칙:** 전부 생존. 죄책감 금지는 B에서 구체 규칙으로 승격. 원본 미러링 금지(필드노트 원문·AI 분석 앱 비노출), 디스크리트(중립 푸시), 가짜 어포던스 금지(A4), 소유자 노출 통제, 부재의 비대칭 — 유지.

**E2. 센터 유형 중립:** 오히려 개선. 할 일 구조(예약·검사·설문·기록·과제)는 성인 상담에 그대로 성립 — 보호자 대행이 아니라 본인 Profile일 뿐. 임상적으로 민감했던 브리핑이 P1 핵심에서 빠지면서 아동 발달 편향이 구조에서 제거됨.

**E3. 3면 동시 출시 → 폐기.** P1은 **앱 + web 최소 설정**만. 브리핑·퀘스트가 P1.5로 가면서 상담사 모바일 발행 화면도 P1.5로 이동. 출시 표면적 대폭 감소.

**E4. 원장·미연동 모드:** 원장 = "기록" 탭으로 존치 (완료된 할 일 + 수신 기록의 아카이브, Profile 소유·센터 초월·이동 가능 속성 유지 — intake 공유 = P2). 미연동 모드 = 자립형 할 일(7·8)만 있는 홈으로 자연 성립 + 블러 프리뷰 + [우리 센터에 알리기] 유지.

### F. Phase 컷 (재정의)

- **P1 — "흩어진 할 일이 모이는 곳" (상담사 신규 노동 제로)**
  - [앱] 내담자 인증(신규: 소셜 + 전화 본인인증) / 온보딩 3경로 / 홈 = 할 일 스택 (카드 1~8) / 기록 탭(원장) / 일정 / 마이 / 중립 푸시
  - [web] 초대 관리(토큰 발송 현황·QR)·노출 토글 / 데스크 연결 보조 화면
  - [api] 예약 리마인더 자동 발송 로직 / 예약 취소·변경 이력 보강 / 초대 토큰(AssessmentSendLink 패턴 확장) / Client↔Account 연결층 (Profile·CenterLink)
- **P1.5 — 상담사가 주는 것들**: 브리핑(상담사 모바일 원탭 발행, 3칸 템플릿 유지) / 퀘스트 v1(텍스트) / 관찰기록 공유 + 상담사 수신 / 서류 발급 / 리드 집계
- **P2+ — 기존 유지**: AI(브리핑 초안·퀘스트 초안, 프로덕션 승인 후) / 무소속·마켓 / 구조화 퀘스트 v3 / 예약 write / intake 공유(원장 이동성) / F12 뷰

## 3. 미해결 (대표님 판단 필요)

1. **문자 편승 위치** — 권장: 신규 등록 환영 문자 1회 + 예약 문자 상시 탑재 (문자 비용 증가 미미, 노출 최대). 운영 정책이라 확인 필요.
2. **대표님 정렬 스토리 개정** — "화려한 앱 = SaaS 영업사원"에서 **"센터가 보내던 문자가 앱이 된다"**로. 도입 장벽 서사가 더 정직해짐.
