## 1. 출발점 (대표님 요구 vs 현실)

- **대표님 요구**: "예쁘고 화려한, 센터 앱 같지 않은" 앱. 누구나 설치 가능하고 소속 센터가 있으면 연결하는 범용 앱.
- **원래 미해결 4대**:
  - (A) 무소속 초기 화면에 뭘 보여줄지
  - (B) 센터 데이터 연동 방식
  - (C) 다중 센터 처리
  - (D) 다중 내담자(보호자 관점) 처리

## 2. 논의 흐름 — 제품 척추가 4번 바뀜

토론 중 앱의 정체(척추)가 계속 이동했고, 최종적으로 **컴패니언**으로 수렴.

| 단계 | 제안된 정체 | 왜 흔들렸나 / 왜 넘어갔나 |
|------|------------|------------------------|
| 1 | 화려한 무소속 B2C 앱 | 목적이 (a)신규획득 vs (b)기존만족 사이에서 모호 |
| 2 | 무소속 유저 획득 → 영세 센터에 리드 공급하는 **양면 마켓플레이스** | SaaS 구독 모델과 충돌(리드 공짜=본업 잠식 / 유료=영세센터 배제). 위기 유저를 수익기준 배분 불가(윤리) |
| 3 | 자가진단·감정기록 콘텐츠형 → **탐색·예약 마켓(안 C)** | 자가진단은 **라이선스**(K-WAIS/BDI/MMPI 등 유료·저작권) 문제로 폐기. 콘텐츠는 획득 아닌 리텐션 장식 |
| 4 | **케어보드형 홈**(케어보드처럼 기록) | 케어보드는 리텐션엔 좋으나 **획득 엔진 아님**. 다시 top-down 회귀 |
| 5(최종) | **SaaS 컴패니언** — 센터가 핵심, 앱은 내담자가 자기 상태를 보는 동반 앱 | ✅ 채택 |

## 3. 결정적 재정의 — "획득"이 아니라 "JTBD"

> **틀린 질문**: "무소속 유저를 어떻게 획득하나"
> **맞는 질문**: "방금 앱을 설치한 사람은 대체 뭘 하려고 깔았나(Job-to-be-done)"

- **아무도 상담센터 앱을 스토어에서 검색해 깔지 않는다.** 우울할 때 검색하면 명상앱·심리테스트가 나오지 특정 센터 도구가 아님.
- **첫 설치자 = 이미 센터가 있는 사람.** 센터가 "예약·검사결과 여기서 봐요" 하고 설치를 요청했을 때 깖.
- 그의 JTBD = *예약 안 놓치기 / 준비물·검사 챙기기 / (보호자면) 아이 진행 보기*. "상담받을 곳 찾기"가 **아님**.
- → **획득은 틀린 게 아니라 "지금"이 틀림(premature).** 방문자 없는 마켓부터 지으면 유령 앱.

## 4. 확정 사항

### 4.1 제품 정체 (Phase 구분)
- **Phase 1 (지금)**: 기존 센터 내담자를 위한 **컴패니언 앱** (top-down 획득 = 센터가 밀어줌).
- **Phase 2 (나중)**: 소속 유저가 쌓인 뒤 무소속 획득/마켓/디렉터리 확장.
- **원칙**: 지금은 획득을 접되, **아키텍처에서 미래 획득 가능성을 죽이지 않는다** (CenterLink 없는 Profile = 무소속 유저 자리 = 미리 비워둠).

### 4.2 데이터 모델 (다중 아동·다중 센터 해결) — 3층 분리

```
┌─ Account (앱 로그인 = 폰 주인) ─ 인증·알림 수신 단위. 1개.
│   ├─ Profile "나 자신"    (role=both 가능) ─ 케어보드/기록의 대상
│   ├─ Profile "첫째 아이"
│   └─ Profile "둘째 아이"
│         ├─ CenterLink → A센터 (Client레코드 #a)   ← 코드로 연결
│         └─ CenterLink → B센터 (Client레코드 #b)   ← 한 아이가 두 센터
```

**3원칙:**
1. **Account ≠ Profile ≠ Client 분리**
   - Account: 로그인 주체(폰 주인). 인증·알림 수신.
   - Profile: "기록/조회의 대상"(나/첫째/둘째). **앱(유저) 소유.**
   - Client: 각 센터가 가진 연락처 레코드(기존 백엔드 그대로). **센터 소유.**
   - "복제냐 참조냐" 논쟁의 답: **둘 다 아님.** Profile(유저 것)과 Client(센터 것)를 **CenterLink 연결 테이블**로 잇고, 공유는 링크별 통제.
2. **다중 아동 = Profile 여러 개** / **다중 센터 = 한 Profile에 CenterLink 여러 개**
   - 최상단 **Profile 전환기**(첫째↔둘째↔나). Profile 안에서 센터는 탭/섹션으로 분리(데이터 안 섞임).
3. **role="both"(보호자=본인도 내담자)** = "나 자신" Profile 하나 더 두면 끝. 특수처리 불필요. (프로젝트 CLAUDE.md role=both 원칙과 일치)

**이 모델이 자동 해결:**
- 알림 라우팅: "첫째 Profile / A센터" 컨텍스트로. 엄마 Account가 받되 어느 Profile인지 명확.
- 프라이버시: 공유는 **CenterLink 단위 토글**. 첫째 케어보드를 A센터엔 공유, B센터엔 비공유 가능. → "센터끼리 내 기록 공유되나" 불안 해소.
- 이동성: 코드연결 = CenterLink 생성. 예약 성사도 CenterLink 생성. 센터 이동 = 링크 해제+생성. Profile·기록은 유지.

### 4.3 "실시간 상태"의 실체 (함부로 미러링 금지)
- **케이스노트(상담기록)는 원래 내담자에게 안 보여주는 게 임상 원칙** — 상담사 가설·감별진단이 날것이라 오해·자기낙인 유발. 검사 원점수 그대로 노출도 위해 가능.
- **"실시간"은 상담사 입력 성실도에 인질** — 3일 뒤 기록하면 앱은 3일간 텅 빔.
- → "상태"는 **자동 생성 데이터 위주**로:
  - ✅ 자동: 다음 예약(D-day), 예약 확정/변경, 검사 "받아야 함" 알림, 결제/바우처 잔여, 준비물
  - ⚠️ 수기의존(있으면 좋음, "실시간" 약속 금지): 상담 소감, 진행도, 숙제
  - 케이스노트는 **내담자용으로 큐레이션된 뷰**로만(원본 미러링 ❌)

### 4.4 대표님 "화려함" 요구의 재해석
- ❌ (원래) 무소속 유저를 낚는 미끼
- ✅ (수정) **소속 유저가 "센터 도구답지 않게 세련됐다"고 느끼게 하는 완성도** — EMR 같은 촌스러움❌, 토스처럼 매끈함✅
- 대표님이 진짜 싫었던 건 "무소속 획득"이 아니라 "관공서 같은 촌스러움"일 가능성 높음.

## 5. 미해결 (내일 결정)

### 5.1 대표님 정렬 필요 (내가 임의 결정 불가 — 정책/이해관계 상충)
- **컴패니언 피벗을 대표님이 수용하는가?** 원래 "누구나 쓰는 화려한 무소속 앱" 비전과 충돌.
  - (가) 대표님 설득 → 컴패니언으로 정렬
  - (나) 컴패니언 먼저 출시 → 나중에 무소속/마켓 확장 (권장: Phase 진화)
  - (다) 대표님 비전 유지 → 컴패니언 폐기, 마켓 회귀

### 5.2 실무 결정 (내가 정할 수 있음)
1. **홈 첫 화면 1순위** — 코드연결 마친 소속 유저의 홈:
   - ① 다음 예약(D-day) 중심 대시보드
   - ② 케어보드(기록) 중심
   - ③ 내 센터 소식/알림 피드 중심
2. **온보딩** — 초대코드 입력 / 초대 수락 흐름 구체화
3. **claim 키** — Profile↔Client 연결 식별 기준 (전화번호+OTP? 센터 승인 매칭? 둘 다?)
4. **케어보드 성격** — "혼자 쓰는 일기❌ → 상담사에게 전달되는 관찰기록✅"으로 갈지 확정
5. **엣지케이스**: 공동보호자(이혼·별거 시 같은 아이 Profile 중복) v1 포함/제외, 아이 성장 후 Account 독립·기록 이관
