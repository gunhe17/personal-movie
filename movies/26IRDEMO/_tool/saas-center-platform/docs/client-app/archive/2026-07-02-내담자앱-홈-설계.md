## 1. §5.2 실무 결정 (확정)

전제: 이 결정들은 내가 코드베이스·기존 원칙(CORE.md 읽기 투영·가짜 어포던스 금지, §4.3 실시간 상태 원칙)에서 도출했다. 정책·이해관계 상충이 아니므로 자체 확정한다.

### D1. 홈 첫 화면 1순위 = **① 다음 예약(D-day) 대시보드** ✅

- **결정**: 홈 first fold의 주인공은 **가장 임박한 다음 예약**(D-day 히어로). 그 아래 "챙길 것"(검사·결제/바우처·준비물) → 이후 예정 일정 → 검사 결과 순.
- **이유**:
  - JTBD 1순위가 "예약 안 놓치기". 첫 설치자의 실제 동기와 정확히 일치.
  - §4.3 원칙 — **자동 생성 데이터가 신뢰의 척추**. 예약·D-day·검사 요청·결제/바우처는 상담사 입력 성실도와 무관하게 항상 채워짐.
  - ②케어보드(기록)는 **수기 의존 → 3일 비면 텅 빔**. first fold에 두면 "실시간" 약속을 못 지킴. → Phase 1.5로 미룸.
  - ③소식 피드는 저빈도·수동 콘텐츠 → 홈 중력 중심이 될 밀도 없음. 알림으로 충분.
- **폐기**: 셀프체크·주변센터·매거진·바우처 발견을 홈 상단에 두던 06-25 시안(획득 모드)은 Phase 2로 내림.

### D2. 최상단 = **Profile 전환기 (다중일 때만 노출)** ✅

- **결정**: 헤더에 Profile 스위처(나 ↔ 첫째 ↔ 둘째). **Profile이 1개면 스위처를 숨긴다.**
- **이유**: §4.2 데이터 모델(다중 아동 = Profile 여러 개). 단, CORE.md "전역 프로파일 스위처 = 가짜 어포던스 금지" 원칙 → **실제로 2개 이상일 때만** 노출해 빈 스위처를 막는다.
- **센터 컨텍스트**: 한 Profile 안에 CenterLink 여러 개면, **자동 데이터(예약·검사·결제)는 통합 타임라인 + 센터 태그**로 집계 표시(안 놓치기 우선). "센터별 격리"가 필요한 건 유저 소유 기록(케어보드)이며 그건 CenterLink 단위 공유 토글로 통제 → Phase 1.5. 홈의 자동 데이터 집계는 프라이버시 이슈 없음.

### D3. 온보딩 = **초대코드 입력 + 딥링크 수락** ✅

- **결정**: 센터가 발급한 **초대코드/초대링크**로 진입. 링크 탭 → 앱 설치/실행 → 코드 자동 채움 → 전화번호 OTP → CenterLink 생성 → 홈. 코드 수기 입력 경로도 병행.
- **이유**: Phase 1은 top-down(센터가 밀어줌). 스토어 검색 유입(무소속)은 Phase 2라 온보딩 진입점은 "코드/링크"로 충분. 첫 진입 전 CenterLink가 반드시 하나 생겨 홈이 빈 화면이 아니게 됨.

### D4. claim 키 = **전화번호 + OTP 자동매칭 (센터 승인 fallback)** ✅

- **결정**: `초대코드(→센터 식별) + 전화번호 OTP 본인확인`으로 센터의 Client 레코드를 **자동 매칭**. 매칭 실패(번호 불일치·미등록·중복 후보)는 **센터 승인 큐로 fallback**.
- **이유**:
  - 프로젝트 원칙 — Client = 통합 연락처, **1인1레코드 가드 = 전화번호**. 전화번호가 자연 claim 키.
  - OTP = 본인확인(타인 데이터 탈취 차단). 코드 = 센터 스코프 축소(전체 Client 탐색 방지).
  - 자동매칭이 대부분을 흡수, 예외만 사람(센터)이 처리 → CS 부담 최소.
  - 거절/실패 처리는 CORE.md D10 계승: **사유 비노출 + 재시도 허용**("센터에 문의" 일반 안내).
- **엣지**: 자녀 Client는 Account 없음 → 보호자가 자기 OTP로 인증 후, 자녀 코드로 자녀 Client를 자기 Account 하위 Profile에 claim(보호자–자녀 relation 근거).

### D5. 케어보드 성격 = **관찰기록(내담자→상담사), 단 Phase 1 홈 미탑재** ✅

- **결정**: 케어보드는 "혼자 쓰는 일기"❌ → **상담사에게 전달되는 관찰기록**✅ 방향으로 확정. 그러나 **Phase 1 홈 first fold에는 넣지 않는다.** Phase 1.5에서 별도 탭/섹션 + 상담사 수신(web) 설계와 함께 출시.
- **이유**:
  - 방향(관찰기록)은 임상 원칙과 충돌 안 함 — 케이스노트 미러링 금지는 "상담사 기록을 내담자에 노출" 금지이고, 케어보드는 **반대 방향**(내담자 관찰 → 상담사)이라 안전.
  - 하지만 (a)수기 의존이라 홈 척추가 될 수 없고(D1), (b)상담사 쪽 수신·활용 UX(web/counselor 앱)가 함께 없으면 "허공에 쓰는 기록"이 됨. → 양면 설계 필요 = Phase 1.5.

### D6. 엣지케이스 = **v1 제외, 데이터 모델만 개방** ✅

- **공동보호자**(이혼·별거 시 같은 아이를 두 Account가) / **아이 성장 후 Account 독립·기록 이관**: **v1 범위 밖**.
- **이유**: 발생 빈도 낮고 정책(친권·동의) 복잡. 단 §4.2의 **Account ≠ Profile ≠ Client 분리** 덕에 나중에 Profile 소유 이전/공동 링크로 확장 가능 → 지금 막지 않고 열어둠.

## 2. 홈 화면 구조 (Phase 1 컴패니언)

```
┌─ 헤더 ────────────────────────────────────
│  인사("○○님 안녕하세요")
│  [Profile 스위처 ▾]  ← Profile 2개↑일 때만       [🔔 알림]
├─ 1. 히어로: 다음 예약 (D-day) ★ 1순위 ─────────
│  D-3   개인상담 · 이수진 선생님
│         6/19 (목) 오후 3:00
│         🌳 마음숲 심리상담센터
│         [오시는 길]     [준비물 보기]
├─ 2. 챙길 것 (조건부, 최대 3) ──────────────────
│  · 검사 요청됨 (BDI 응답 필요)        → 안내/센터앱
│  · 남은 회기 8회 · 다음 결제 안내      → 결제/바우처
│  · 준비물: 지난 검사지 지참
├─ 3. 예정된 일정 (통합 타임라인) ───────────────
│  6/24 종합심리검사 · 온마음   [센터 태그]
│  7/03 개인상담 · 마음숲
├─ 4. 검사 결과 (발행분만, 읽기) ────────────────
│  종합심리검사 결과지 · 6/10 발행    [PDF 보기]
└─ (Phase 1.5) 케어보드/기록 — 미탑재
```

**하단 탭 (Phase 1 = 3탭 축소)**: 홈 / 일정 / 마이
- 06-25 시안의 "콘텐츠·내 센터(디렉터리)" 탭은 Phase 2. Phase 1은 **동반 코어만**.
- "일정" = 통합 타임라인 전체 + 과거 회기. "마이" = Profile·센터연동 관리·설정·검사결과 아카이브.

## 3. 상태별 (State Matrix)

| 상태 | 조건 | 홈 표현 |
|------|------|---------|
| **A. 단일 센터·단일 Profile** | 성인 본인, 1센터 | 스위처 숨김. 히어로 예약 + 챙길 것 + 결과. 센터 태그 최소. **가장 흔한 첫 설치자.** |
| **B. 다중 Profile (보호자)** | 아이 여럿 | 헤더 Profile 스위처. 선택 Profile의 예약/검사/결제만. |
| **C. 다중 센터 (한 Profile)** | 한 사람 N센터 | 통합 타임라인 + 센터 태그. (선택적 센터 필터 칩) |
| **D. 방금 연동 (데이터 얕음)** | 온보딩 직후 | 예약이 아직 없으면 히어로 = "첫 예약을 기다리고 있어요" + 센터 연결됨 확인. 빈 화면 아님(연결 성공 자체가 상태). |
| **E. 예약 없음 (기존 유저)** | 활성이나 다음 예약 미정 | 히어로 자리 = 최근 회기 요약 + "다음 일정은 센터에서 잡혀요" 안내. |

> **비연동(무소속) 상태 = Phase 2.** Phase 1은 온보딩에서 반드시 CenterLink 1개를 만들고 진입하므로 홈에 무소속 상태가 없다.
