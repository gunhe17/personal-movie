> **성격:** [`2026-07-07-내담자앱-기획-종합.md`](2026-07-07-내담자앱-기획-종합.md)(방향·구조·Phase)의 **자매 문서**.
> 종합본이 "왜/어떤 구조로"라면, 이 문서는 **"전문가앱(mobile 상담사 전용)·SaaS web에 실제로 존재하는 화면/데이터를 하나씩 훑어 → 내담자 앱에 무엇이 보여져야 하고 무엇이 가려져야 하는가"**를 기능 단위로 도출한 **노출 매트릭스**다.

## 0. 도출 방법과 3대 게이트

**소스 3종을 교차 스캔:**
- 전문가앱 `apps/mobile` — 상담사 전용 5탭(홈·일정·내담자·상담/검사·마이) + 필드노트
- SaaS web `apps/web/src/routes/(protected)` — 상담사+관리자 콘솔
- 백엔드 `apps/api/app/modules/*` — 도메인 엔티티(무엇이 저장돼 있는가 = 노출 가능 상한)

**핵심 통찰:** 전문가앱/웹의 거의 모든 화면은 *상담사가 내담자에 대해* 하는 일이다. 내담자 앱은 그 **주어를 뒤집은 거울**이다 — "상담사가 A의 회기를 관리" → "A가 자기 회기를 확인". 단, 거울을 그대로 비추면 안 되고 **3대 게이트**를 통과한 것만 노출한다:

| 게이트 | 규칙 | 근거 |
|---|---|---|
| **G1 원본 미러링 금지** | 임상 원문·AI 분석·상담사 사견은 앱에 비노출 | 종합본 §3. 필드노트 원문/분석, `CounselingNote.private_notes/raw_notes`, `AssessmentTask.opinion` |
| **G2 소유자 노출 통제** | 자기(및 연결된 자녀) 데이터만. 센터 내부 운영값·타 내담자·직원 관리값 숨김 | `Client.memo/code/status`, `counselor_id`, `created_by`, `PriceList` |
| **G3 명시 가시성 플래그 우선** | 스키마에 이미 있는 가시성 게이트를 그대로 존중 | `AssessmentTask.is_report_visible_to_guardian`, `ClientRelation.is_primary` |

**노출 = 파생 뷰(종합본 §2 데이터 원칙 재확인):** 앱은 원본(Schedule·ClientVoucher·AssessmentTask…) 상태에서 파생만 하고, 자체 저장은 열람/완료 view-state뿐. 원본이 바뀌면 카드가 자동 소멸 → 정합이 깨질 수 없다.

## 1. 정체성·온보딩 — 노출의 전제 (Person ↔ Client)

노출 매트릭스에 앞서, **누가 무엇을 볼 자격이 있나**의 뼈대. 이게 없으면 나머지가 성립 안 한다.

```
Account(로그인 자격) ─1:1─ Person(실제 사람, 앱 유저) ─N─ Client(센터별 내담자 레코드)
                                                        └─ CenterLink(연결·승인)
```

- 앱 유저 = **Person**(전화·생년월일·성별). 한 Person이 **여러 센터의 Client 레코드**를 집약한다(센터마다 별도 행). → 홈은 Person 귀속, 공급원 표시는 CenterLink 경유(종합본 §2).
- **연결 = 토큰 확인**(전화번호 자동매칭 폐기, 종합본 §2). 관련 엔티티가 이미 있음: `ClientLinkRequest`(전화 매칭·직원 승인·pending/approved/rejected), `ClientUnlinkLog`, `ClientFavorite`.
- **보호자 모델이 스키마에 이미 존재:** `ClientRelation`(guardian↔child, `relation_detail`=엄마/아빠/조부모/사회복지사…, `is_primary`), `SiblingRelation`. → 다자녀 통합 스택·가족 초대(종합본 온보딩 3경로)의 데이터 기반이 준비돼 있음.
- ⚠️ **없는 것:** 내담자용 인증 체계 자체(현재 `Account`는 센터 직원용). Person·CenterLink 연결층은 **P1 백엔드 선행 과제**(§5).

## 2. 도메인별 노출 매트릭스

각 도메인: **전문가앱/웹에서 상담사가 하는 일 → 내담자 앱 노출 → 숨김 → 소스 엔티티 → Phase**. Phase는 종합본 §5 컷을 따름.

### 2-1. 내 프로필 · 가족 관계
| | |
|---|---|
| 상담사측 | web `clients/[id]`, mobile `client/[id]` — 프로필 CRUD, 즐겨찾기, 관계(보호자·자녀) 등록, 메모 |
| **노출** | 자기 프로필(이름·생년월일·성별·전화·이메일·주소·아바타), 역할(`role`: 내담자/보호자/both), 연결된 자녀·보호자 관계(관계호칭) |
| **숨김(G2)** | `code`(센터 내부코드), `memo`(직원 메모), `status`(active/inactive) |
| 소스 | `Client`, `ClientRelation`, `SiblingRelation` |
| Phase | P1 (마이) |

### 2-2. 일정 · 예약
| | |
|---|---|
| 상담사측 | mobile `schedule` / web `schedule` — 월·주·일 캘린더, 회기 상태·노트 편집. web `schedule/reservations` = 예약 신규/변경 승인 워크플로(현재 mock) |
| **노출** | 자기 예약만: 날짜·시간·프로그램명·룸·담당 상담사명·상태(예정/완료/불참). D-1 확인 카드(종합본 카드 #1) |
| **숨김(G2)** | `note`, 타 내담자 일정, 충돌(conflict) 정보, 상담사 배정 로직 |
| 소스 | `Schedule`, `CounselingSession`, `AssessmentSession` |
| Phase | **읽기** P1 / **예약 변경·휴강 대응** P1(백엔드 보강) / **예약 write(신청·변경 요청)** P2 |
| ⚠️ 선행 | `Schedule`/세션에 `cancel_reason`·변경 이력 보강, 리마인더 자동발송 로직(모델만 존재) |

### 2-3. 상담 회기 (진행 현황)
| | |
|---|---|
| 상담사측 | mobile `counseling/*` — 케이스·회기·출석·상담일지(mood/topic/intervention/homework/next_goal/**private_notes**), 필드노트→일지 자동생성 |
| **노출** | 회기 진행(N회기차/총 M), 출석 상태(참석/불참/취소), 완료 시각. **공유용 부분만**: homework(과제)·next_goal(다음 목표)·승인된 요약 |
| **숨김(G1)** | 상담일지 임상 원문 전체 — `mood/main_topic/intervention/progress/raw_notes/**private_notes**`, `chief_complaint`, `CounselingCaseAnalysis`(AI 분석) |
| 소스 | `CounselingCase`, `CounselingSession`, `CounselingSessionParticipant`(attendance/`is_consumed`), `CounselingNote`(일부만) |
| Phase | 진행/출석 P1(기록 탭) / homework·요약 공유 P1.5(상담사 발행) |

### 2-4. 검사 (실시 · 결과)
| | |
|---|---|
| 상담사측 | mobile/web `assessment/*` — 케이스, 과제별 상태, **소견(opinion) 작성**, 취소/거부, 결과 보고서(`report_payload`/PDF), `is_report_visible_to_guardian` 플래그. web `assessment-flow/*`는 **이미 내담자 대면 검사 실시 플로**(별도 auth) |
| **노출** | 배정된 검사(온라인 실시 가능분), 상태(대기/진행/제출/완료), 마감일, 소요시간. **결과 보고서는 `is_report_visible_to_guardian=true`일 때만**(G3) |
| **숨김(G1/G3)** | `opinion`(상담사 사견), raw `process`, 가시성 플래그 false인 보고서, 케이스 태그/summary |
| 소스 | `Assessment`(카탈로그), `AssessmentTask`(실시·`report_document_id`·가시성 플래그), `AssessmentSession`, `Document`(보고서 PDF) |
| Phase | 실시·결과 확인 P1 / 재검사 리마인더 P1.5 |
| 재사용 | `assessment-flow/`가 내담자 실시 UI를 이미 구현 — 앱은 이걸 수신/재사용 |

### 2-5. 바우처
종합본 §6에서 **3층 노출(L1 할 일 카드 / L2 마이 상시현황 / L3 상세)로 확정** — 여기서 재서술 안 함. 노출 인벤토리 관점 요약만:
- **노출:** `ClientVoucher`의 프로그램명·**잔여/총 회기·유효기간**, 제도 정보(주관·정부 고시 지원금·문의처), 사용 내역(세션 연결)
- **숨김:** 금액(`remaining_amount` — 센터 내부 운영값, 정부포털과 어긋나 분쟁 소지 → P1 회기 수만), `CenterVoucher`(단가), `created_by`
- 소스: `Voucher`(카탈로그)→`CenterVoucher`(내부)→`ClientVoucher`(발급분), `BillableItem`(차감 이력)

### 2-6. 청구 · 결제
| | |
|---|---|
| 상담사측 | mobile `billing`(권한 `read:billing` 게이팅) / web `billing` — 청구서 발행, 결제 수납, 영수증, 바우처 차감. 환불·삭제는 상담사 권한 밖 |
| **노출** | 내 청구서(총액·할인·지원금·미납·상태), 항목 내역, 결제 내역·영수증, 납부기한 |
| **숨김(G2)** | `notes`, `created_by`, `PriceList`(센터 단가표). **센터 구독 결제(SaaS 요금)는 완전 무관** |
| 소스 | `Billable`, `BillableItem`, `Payment` |
| Phase | 조회 P1(할 일 카드 "미납"·마이) / 인앱 결제 P2+ |

## 3. 화면(탭)별 집약 — 위 도메인이 어디에 뜨나

종합본 §5 P1 탭 골격(홈=할 일 스택 / 기록 / 일정 / 마이)에 §2 노출 요소를 매핑:

| 탭 | 표면화되는 노출 요소 | 비고 |
|---|---|---|
| **홈 (할 일 스택)** | 예약 D-1(2-2)·검사 실시/결과(2-4)·사전설문(2-7)·바우처 임박 L1(2-5)·미납(2-6)·관찰기록/질문메모(신규 자립형)·브리핑/퀘스트(P1.5) | 종합본 카드 인벤토리 1~11과 1:1 대응 |
| **기록 (원장)** | 완료된 할 일이 변환돼 쌓임 — 회기 진행(2-3)·검사 결과(2-4)·제출 서류(2-7) | "전환 자체가 보상"(종합본 §3) |
| **일정** | 내 예약 캘린더(2-2), 회기 진행(2-3) | 읽기 전용(P1) |
| **마이** | 프로필·가족(2-1)·바우처 상시현황 L2(2-5)·청구/영수증(2-6)·알림 설정(2-9) | |
| (전역) | 알림 피드·푸시(2-9), 미연동 모드·센터 디렉터리(종합본 §4) | |

## 5. 노출을 위한 백엔드 선행 과제 (P1)

노출 인벤토리를 실제로 띄우려면 필요한 것들 — 종합본 §5 [api]와 정합:

1. **내담자 인증층** — Person·CenterLink 연결층 신설(현재 `Account`는 직원 전용, 내담자용 인증 체계 전무). **최상위 블로커.**
2. **초대 토큰** — `AssessmentSendLink`(토큰·verification_code·채널) 패턴 확장 → 온보딩 3경로.
3. **예약 리마인더 자동발송** — 모델만 있고 로직 없음(2-2 카드 #1 전제).
4. **예약 취소·변경 이력 보강** — `cancel_reason` 없음, 변경 이력 없음(2-2 카드 #2).
5. **`PushToken.platform`에 모바일 추가**(현재 web 기본) — 2-9 푸시.
6. **가시성 플래그 클라 노출 경로** — `is_report_visible_to_guardian`를 내담자 조회 API로 노출(2-4).
