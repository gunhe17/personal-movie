# 청구/결제 피드백 메모 (2026-04-21)

> 현장 결제 패턴을 반영한 청구 기능 개선 아이디어. 논의/우선순위 정리 전 원본 메모.

---

## 📌 청구에 대한 고민

### 1. 미납 관리

- **문제**: 현재 구조로는 미납이 누락되기 쉬움
- **아이디어**: `청구 → 청구 내역`에서 **오늘 스케줄 기준**으로 미납 건을 볼 수 있게
- **기대 효과**: 방문 시점에 미납을 바로 확인/안내 가능

### 2. 일괄 완납 처리

- 여러 청구서를 **한 번에 완납 처리**할 수 있는 기능 필요성
- 지금은 청구서 하나씩만 처리 가능

### 3. 프로그램 단가 관리 등록 → 일괄 청구서 발행

- 프로그램(단가)을 미리 등록해두고
- 등록된 단가를 기반으로 **일괄 청구서를 발행**하는 기능
- (⚠️ **예외 사항은 따로 발행** 가능해야 함)

### 4. 바우처 자부담 관리

- 바우처 결제 시 **자부담 부분을 별도로 추적**해야 함
- 소득 기준에 따라 자부담액이 다르므로 케이스별 관리 필요

---

## 💳 결제 상황 (실제 현장 패턴)

### A. 치료 회차 결제

- **방문할 때마다** 회차별로 결제
- 가장 빈번한 케이스

### B. 단건 결제

- 검사, 초기상담, 1회 상담 등
- 1회성 결제로 종료

### C. 패키지 선결제

- 10회 / 20회 / 30회 등 묶음 결제
- 보통 **할인 적용**됨
- 선결제 후 회차 차감 방식
- **적용 도메인**: 주로 상담(`CounselingSession`이 `session_number`로 회차 명시), 검사도 케이스 단위 번들 가능

### D. 바우처 (회차 결제 + 자부담 결제 분리)

- **바우처 회차 결제**: 매번 방문 시마다 결제
- **자부담 결제**: 달마다 1회 결제
- 내담자 **소득 기준에 따라 자부담액이 모두 다름** → 확인 필요

## 🧩 현재 구조로 어디까지 되나?

### ✅ 가능한 것

- **케이스 단위 묶음 청구**: `BillableItem.related_case_id`로 여러 세션을 한 청구서에 묶기
- **다중 아이템**: 한 청구서에 N개 항목 자유롭게 추가
- **편법 할인**: 항목 `unit_price`를 깎아서 입력 (예: 정가 50,000 → 45,000 직접 기입)

### ❌ 안 되는 것

- **체계적 할인**: `discount_amount`, `discount_rate`, `original_price` 같은 필드 자체가 없음
- **"얼마 할인해줬는지" 기록 불가** → 통계/리포트에서 할인 총액 집계 불가
- **정가 vs 실제 청구가 비교 불가** → 프로그램 단가표 연동의 의미가 반감

## 🛠️ 할인 기능 도입 작업 가늠

### T-shirt Size: **M (2~3일)**

| 레이어  | 파일 수 | 범위                                                   |
| ------- | ------- | ------------------------------------------------------ |
| 백엔드  | ~9개    | 모델/스키마/서비스/마이그레이션                        |
| 프론트  | ~6개    | BillableCreate/Detail 모달, 리스트 테이블, view-model  |

### 주요 의사결정 필요

1. **할인 레벨**: 항목별 할인 + 청구서 전체 할인 둘 다? 한쪽만?
2. **할인 표현**: 정률(%) vs 정액(원) — 둘 다 지원? 하나만?
3. **수정 가능 시점**: draft만? issued도 가능?

### 접근 옵션

**옵션 A — MVP (1~1.5일)**
- Billable 레벨 전체 할인 필드 1개 (`discount_amount`)
- 항목별 할인 X (필요 시 단가 조정)
- draft/issued 구분 없이 수정 가능
- 👉 "10회 묶음 5만원 할인" 같은 현장 패턴 80% 커버

**옵션 B — 본격 (3일)**
- 항목별 + 전체 할인
- 정률/정액 둘 다 지원
- 정가 필드 분리 → 정가 대비 할인율 자동 계산
- 프로그램 단가표 연동

## 🏷️ `related_type` 구분 규칙 (케이스 vs 세션 청구)

### 설계 원칙

`BillableItem.related_type`으로 **청구 의도**를 데이터에 명시해, 세션/케이스 레벨 판정을 쿼리 한 방에 가능하게 한다.

| 청구 유형             | `related_type`         | `related_case_id` | `related_session_id` |
| --------------------- | ---------------------- | ----------------- | -------------------- |
| 개별 세션 청구        | `counseling_session`   | 있음 (참고용)     | **있음**             |
| 케이스 패키지 선결제  | `counseling_case`      | **있음**          | 없음                 |
| 검사 개별 청구        | `assessment_session`   | 있음              | **있음**             |
| 검사 패키지 청구      | `assessment_case`      | **있음**          | 없음                 |

### 이점

- **케이스 완전 커버 판정**: `EXISTS(Billable WHERE related_type='counseling_case' AND status='paid')` 한 방
- **세션 커버 판정**: 케이스 선결제 OR 해당 세션 단위 청구 중 하나라도 있으면 커버
- **혼합 케이스 누락 감지**: `전체 세션 - 커버된 세션` 계산 가능
- **리포트 분리**: `GROUP BY related_type`으로 패키지/단건 매출 집계

### 조회 규약

- **세션 화면**: `related_type IN ('counseling_session', 'counseling_case')` 로 조회해 케이스 선결제까지 감지
- **백엔드**: `find_by_related`가 `related_type: str | list[str]` 지원
- **API**: `GET /billables/by-related?related_type=counseling_session,counseling_case` (쉼표 구분)

### UI 표시

- **"청구 완료"**: 세션 단위 청구 완납 (`source='session'`)
- **"선결제 완료"**: 케이스 패키지 선결제로 커버됨 (`source='case'`)

### 알림 원칙 (향후 구현 시)

- **알림/미납 판단은 Billable 기준**, 세션 기반 아님
- 세션 화면의 미납 뱃지는 "관련 Billable(세션+케이스) 중 unpaid > 0 존재 여부"로 판정
- 이러면 패키지 선결제가 있는 세션에 잘못된 "청구 필요" 알림이 안 감

## 📦 묶음 할인 적용 단위 (Billable vs Case)

### 쟁점

할인이 "**청구서(Billable) 단위**"인지 "**케이스(Case) 단위**"인지에 따라 구조가 달라짐.

- **청구서 단위** = 한 청구서에 여러 회차를 묶어 발행 + 전체 할인 1건
- **케이스 단위** = 매 회차마다 청구서 별도 발행, 할인은 케이스 전체에 걸쳐 배분

### ✅ 실무자 확인 (2026-04-21)

> 패키지 할인(10회 5만원 할인 등)은 **선결제** 방식으로 운영.
> → 10회분을 **한 청구서**에 묶어 발행하고 할인 1건 적용.

### 결론: 현재 Billable 레벨 할인 구조로 충분

| 항목              | 처리 방식                                         |
| ----------------- | ------------------------------------------------- |
| 패키지 선결제     | 1 Billable + 10 BillableItem + `discount_amount` |
| 회차별 청구       | 할인 없음 (정가 청구)                             |
| 케이스 단위 정산  | 선결제 청구서 1건으로 케이스 전체 커버            |

### 운영 가이드

- **패키지 판매 시점**: "10회 패키지" 청구서 생성 → 항목 10개 추가 → 묶음 할인 입력 → 선결제 완료
- **이후 회차 진행**: 이미 선결제 완료된 상태이므로 추가 청구 없음
- 회차별 차감 추적은 BillableItem의 `related_session_id`로 연결 가능

### 도입 보류된 것

- `CaseDiscount` 별도 엔티티 (회차별 청구 + 케이스 단위 할인 배분)
- → 회차별 청구에 할인을 주는 관행이 없어 **불필요**
- → 정책 변화 시 재검토 (예: 정부 지원 프로그램 회차별 청구 요구)

## ⚠️ 할인 × 바우처 충돌 가능성

바우처는 "**금액의 일부를 지원금(바우처)으로, 나머지를 본인부담금으로 분리 결제**"하는 구조 ([voucher-integration-plan.md](voucher-integration-plan.md) §2 참고). 할인은 "**총액 자체를 깎는**" 구조. 두 개가 한 청구서에 공존할 때 **계산 순서·범위**가 모호해질 수 있음.

### 충돌 시나리오

**예시**: 정가 50,000원 × 10회 = 500,000원 / 10회 묶음 50,000원 할인 / 그 중 절반은 바우처 지원

| 쟁점 | 케이스 A | 케이스 B | 케이스 C |
| ---- | -------- | -------- | -------- |
| **할인 적용 순서** | 할인 먼저 → 바우처 | 바우처 먼저 → 할인 | 동시 비율 |
| 실제 총액 | 500,000 − 50,000 = **450,000** | 500,000 | 500,000 |
| 바우처 지원금 | 450,000 × 50% = **225,000** | 500,000 × 50% = **250,000** | 혼합 |
| 본인부담금 | **225,000** | 250,000 − 할인? | 혼합 |

→ **같은 상황에서 결과가 달라짐**. 바우처 사업별로 "할인 전 정가 기준"을 요구할 수 있어 정책 결정 필수.

### 구조적 충돌 포인트

1. **`BillableItem.voucher_amount`([§9-2](voucher-integration-plan.md)) vs `discount_amount`(신규)**
   - voucher_amount는 Item의 지원금 절대값. 할인 들어가면 `amount`가 바뀌어서 **비율이 흔들림**
   - 예: amount=50,000, voucher_amount=25,000인데 할인 5,000 적용 시 → voucher_amount는 그대로? 재계산?
2. **환불 재계산 복잡도 증가**
   - 현재 voucher rollback은 Payment void + VoucherUsage reverse 한 트랜잭션. 할인까지 섞이면 **"할인이 남은 건수에 어떻게 재분배되는지"** 도 정해야 함
3. **청구 양식(바우처 사업)**
   - 사회서비스전자바우처는 보통 **정가 기준 청구**가 원칙. 할인을 반영하면 양식 자동 생성([§2-2 monthly_summary](voucher-integration-plan.md)) 로직이 "정가 vs 실가" 중 뭘 쓸지 분기 필요
4. **세무 분리([§9-3 payment_category](voucher-integration-plan.md))**
   - 바우처 결제=면세, 일반 결제=과세. 할인액은 **어느 쪽에서 빼는지**에 따라 과세 매출 총액이 달라짐

### 권장 대응

> **✅ 실무자 확인 (2026-04-21)**: 바우처 적용 건에는 **할인이 적용되는 경우가 거의 없음**.
> → **옵션 A로 확정**. 옵션 B는 현재 시점 불필요.

**옵션 A — 단순화 (채택)**
- **할인은 "일반 결제분"에만 적용**. 바우처 지원금은 항상 정가 기준
- 규칙: `item.amount`는 정가 유지, 할인은 `Billable.discount_amount`(전체 레벨)로만, **바우처 지원금 계산 후 남은 본인부담금에서 차감**
- 장점: 바우처 사업 청구 양식 안전, 환불 로직 단순, MVP 범위 유지 가능
- 운영 가이드: 만약 "바우처 + 묶음 할인" 요구가 실제로 발생하면 단가(`unit_price`) 직접 조정으로 우회 대응

**옵션 B — 전면 허용 (보류)**
- 실무상 수요가 거의 없다는 피드백으로 **도입 보류**
- 추후 정책 변화(예: 특정 바우처 사업에서 할인 허용)가 생기면 재검토
- 재검토 시 필요한 것: `original_price` 필드 보존, 계산 순서 "할인 → 바우처" 고정, 환불 재분배 로직

### 구현 시 체크리스트 (옵션 A 기준)

- [ ] `Billable.discount_amount` 추가 — 청구서 전체 레벨 할인
- [ ] 금액 계산 순서: `subtotal = Σ item.amount` → `(subtotal - discount_amount) - voucher_amount_total = 본인부담금`
- [ ] `discount_amount`는 **바우처 지원금이 0인 부분에만** 적용되도록 검증 (방어 로직)
- [ ] 청구서 상세/리스트 UI에 "정가 / 할인 / 바우처 / 본인부담금" 분리 표시
- [ ] 바우처 쓰인 Billable에 할인 입력 시 **경고 토스트**로 안내 (실무상 드문 케이스)

### 3. 패키지 선결제 기능 (케이스 단위)

**저장 구조**: 1 BillableItem × quantity=N 대신 **N BillableItem × quantity=1 (세션별 1:1 매핑)**

- 회차 번호는 description에 박지 않음 (순서 꼬임 방지)
- 세션 추가 시 자동으로 "미청구" 상태 유지 (items에 없는 세션)

**UI**: 좌측 클라이언트 카드 옆에 **PackageBillingPill** — 호버 시 왼쪽으로 슬라이드 확장되는 핀 형태

### 🕒 보류된 기술 작업

#### 1. DB unique index로 세션 중복 청구 원천 차단

**배경**: 현재 `create_billable` 서비스에 3중 방어 로직이 있지만 앱 레벨 체크라, 동시 요청 시 레이스 컨디션으로 중복 생성 가능성이 이론상 남아있음 (실무 빈도 낮음).

**작업 내용**
- `billable_items` 테이블에 partial unique index 추가
  ```sql
  CREATE UNIQUE INDEX uq_billable_items_session_unique
  ON billable_items (related_type, related_session_id)
  WHERE deleted_at IS NULL
    AND related_session_id IS NOT NULL;
  ```
- 모델 `__table_args__`에도 동일 선언 추가 ([models.py](../../apps/api/app/modules/billing/billable/models.py))
- `CreateBillableService`에 `sqlalchemy.exc.IntegrityError` → `ConflictException` 변환 추가

**선행 조건 (중요)**
- 현재 alembic autogenerate 돌리면 **다른 팀원 작업(notification_logs 생성, lab_* 테이블 삭제, field_notes 컬럼 추가 등)의 미반영 마이그레이션**이 섞여 나옴
- 즉, **코드 모델과 DB 스키마 사이에 쌓인 갭을 먼저 정리하는 마이그레이션**이 선행되어야 함 (다른 팀원 영역)
- 갭이 정리된 후에 수동으로 unique index만 딱 담은 마이그레이션을 작성해야 안전함

**중복 데이터 체크 쿼리** (마이그레이션 전 반드시 실행)
```sql
SELECT related_type, related_session_id, COUNT(*)
FROM billable_items
WHERE deleted_at IS NULL
  AND related_session_id IS NOT NULL
GROUP BY 1, 2
HAVING COUNT(*) > 1;
```
- 2026-04-22 로컬 DB 기준: **중복 없음 (0 rows)** — 확인 완료
- 운영 DB에서는 배포 직전 다시 확인 필요

**예상 공수**: 30~40분 (단, 선행 마이그레이션 정리 후)
