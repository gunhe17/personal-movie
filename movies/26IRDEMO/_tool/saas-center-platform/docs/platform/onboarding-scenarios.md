# 플랫폼 온보딩 케이스 (Onboarding Scenarios)

> **목적**: "센터 승인 → 상담사 초대 → 내담자 등록 → 운영" 이라는 현재 강결합 파이프라인이 커버하지 못하는 **이탈 케이스** 를 enumerate 하고, 각 케이스에서 선택 가능한 대응 전략을 정리한다. 결정 확정 문서가 아니라 **의사결정 지원 문서** 다.

---

## 1. 배경

현재 플랫폼은 "센터(Center)"를 중심으로 모든 도메인이 묶여 있다. 센터가 승인되어야 비로소 멤버(상담사)/내담자/상담/검사/청구가 성립한다. 그런데 실제 필드에서는:

- 센터는 있지만 아직 우리 플랫폼에 **등록하지 않은** 경우
- 내담자는 앱을 쓰는데, **소속 센터나 상담사는 우리 시스템을 쓰지 않는** 경우
- 프리랜서/1인 상담사처럼 **소속 센터 자체가 없는** 경우
- 관리자는 SaaS를 쓰지만 **상담사는 기존 아날로그 방식을 유지** 하는 경우

이런 케이스들이 정리되지 않으면 ① 타겟 고객 정의가 애매해지고, ② 미등록 센터 소속 상담사의 진입 경로가 닫히고, ③ 권한 모델이 현실과 어긋난다 (현재 접수 제어는 관리자 중심, 상담사는 본인 케이스만 가능).

---

## 2. 현재 구조에서의 결합점

| 층 | 결합 현황 | 코드 |
|---|---|---|
| `Account` | 센터와 무관하게 생성 가능 (email+password) | `apps/api/app/modules/auth/facade/auth_facade.py:364` |
| `Person` | Account 와 1:1 (로그인 없는 보호자는 Account 없이 Person 만 존재 가능) | `apps/api/app/modules/person/models.py` |
| `Center` | **플랫폼 관리자 수동 승인** 필요. `CenterApplication` → 승인 → `Center` 자동 초기화 (role/catalog/operating time) | `apps/api/app/modules/platform_admin/center_application/services/approve_application.py` |
| `Member` | `center_id` **NOT NULL**. Account 가 센터에 귀속되어야 상담사로 활동 가능 | `apps/api/app/modules/center/member/models.py:21` |
| `Client` | `center_id` **NOT NULL**. 센터별 6자리 코드 유일성. | `apps/api/app/modules/client/profile/models.py:34` |
| 접수 | `POST /centers/{id}/counseling/intake` 는 `write:counseling` 권한 필요. 기본 role 체계상 관리자/전체권한 상담사만 보유 | `apps/api/app/modules/counseling/router.py:34` |

**핵심 요약**: Account/Person 까지는 플랫 하지만, **Member/Client 가 생기는 순간 센터 소속이 강제** 된다. 그리고 "센터 승인"은 사람이 직접 눌러야 한다. 이 두 가지가 모든 이탈 케이스의 공통 병목이다.

## 3. Surface 현황

| Surface | 실체 | 대상 |
|---|---|---|
| `apps/web` | SvelteKit, **구축 완료** | 센터 운영자 (관리자/상담사/검사자) |
| `apps/mobile` | Expo RN, **구축 완료** | **상담사/스태프** (내담자 앱 아님) |
| `apps/admin` | 별도 SvelteKit, **계획 단계** | 플랫폼 관리자 (센터 승인 등) |
| 내담자 surface | **전용 앱 없음**. 웹의 `/assessment-flow` 로 제한적 제공 | 내담자 |

즉 "내담자만 앱을 쓴다"는 시나리오는, 정확히는 **"내담자가 웹 flow 로 접근한다"** 를 의미한다.

## 4. 케이스 공간 정의

3개 축으로 조합:

- **Center**: `등록(registered)` / `미등록(unregistered, 존재는 함)` / `없음(none, 개인)`
- **상담사**: `앱/웹 사용` / `미사용`
- **내담자**: `앱/웹 사용` / `미사용`

3 × 2 × 2 = 12 조합. 의미 있는 것만 아래에서 다룬다.

## 5. 케이스 매트릭스

> 각 케이스 공통 템플릿: **상황 / 현재 대응 / 막히는 지점 / 선택지 / 우선순위 추정**

### C1. Full SaaS — 센터(등록) + 상담사(사용) + 내담자(사용)

- **상황**: 현재 설계가 상정하는 정상 경로. 센터가 승인된 후, 관리자가 상담사를 초대하고, 상담사가 내담자를 등록하거나 내담자가 초대 링크로 가입.
- **현재 대응**: 완전 지원.
- **막히는 지점**: 없음.
- **선택지**: 유지.
- **우선순위**: 기본값 (baseline).

### C2. Staff-only — 센터(등록) + 상담사(사용) + 내담자(미사용)

- **상황**: 센터와 상담사는 SaaS 를 쓰지만, 내담자는 앱/웹에 들어오지 않고 오프라인으로만 상담 받음. 예약/일정/기록은 상담사가 대신 입력.
- **현재 대응**: 거의 완전 지원. `Client` 는 `person_id` nullable 이 가능하므로 **로그인 계정 없는 내담자** 를 상담사가 대리 생성할 수 있음 (`apps/api/app/modules/client/profile/models.py`).
- **막히는 지점**: ① 설문/자가보고형 검사는 내담자 입력이 필수라 일부 기능 사용 불가. ② 내담자 알림(카톡/SMS) 채널이 없으면 리마인더 약함.
- **선택지**:
  - **A**: 현재 상태 유지 (내담자 미사용도 1급 지원으로 문서화)
  - **B**: 내담자용 경량 OTP-link flow (1회용 링크로 설문만 수행, 계정 없음)
- **우선순위**: 높음. 한국 상담 현장에서 흔한 패턴.

### C3. Manager-driven — 센터(등록) + 상담사(미사용) + 내담자(사용/미사용)

- **상황**: 센터 관리자만 플랫폼을 쓰고, 상담사는 기존 방식(종이/엑셀)을 고수. 관리자가 모든 접수·일정·회기 기록을 대신 입력.
- **현재 대응**: 지원 가능. 관리자가 `write:counseling` 권한으로 대리 접수. 다만 UX 가 "상담사 접속" 을 전제로 한 화면이 많음.
- **막히는 지점**: ① 필드노트/회기 요약은 상담사 1인칭 관점으로 설계되어 관리자 대리 입력 시 의미 변형. ② 상담사별 성과/부하 분석 기능이 공허해짐.
- **선택지**:
  - **A**: "상담사는 플랫폼 밖 리소스" 로 취급 (Member 는 단순 엔티티, 계정 비활성)
  - **B**: 상담사에게 읽기 전용 포털을 최소한 제공 (이탈 방지 + 추후 전환 유도)
- **우선순위**: 중간. 영업 초기 단계에 자주 등장.

### C4. Admin-only SaaS — 센터(등록) + 상담사(미사용) + 내담자(미사용)

- **상황**: 관리자가 청구/바우처/재무/통계 등 **운영 툴 목적** 으로만 사용. 임상 워크플로우는 전부 플랫폼 밖.
- **현재 대응**: 부분 지원. 청구/바우처 도메인은 충분하지만, 내담자/회기 데이터 없이 청구만 입력하는 흐름이 1급 시민은 아님.
- **막히는 지점**: 대부분의 청구는 "회기 발생"을 트리거로 하는데, 회기가 없는 상태에서 수동 청구 입력이 자연스럽게 지원되는지 애매.
- **선택지**:
  - **A**: "청구 전용 센터" 티어 정의 (저가/제한 플랜)
  - **B**: 이 케이스는 의도적으로 비타깃으로 두고 거절
- **우선순위**: 낮음. 타깃 정의 문제.

### C5. Shadow Center — 센터(미등록, 존재) + 상담사(사용) + 내담자(사용)

- **상황**: 실재 센터가 있으나 플랫폼에 등록/승인은 아직 안 됨. 그 센터 소속 상담사와 내담자가 앱을 쓰고 싶어함.
- **현재 대응**: **불가능**. `Member.center_id` 가 NOT NULL 이라 승인된 센터 없이 상담사 레코드를 만들 수 없음.
- **막히는 지점**:
  - 상담사 입장: 가입 후 갈 데가 없음 (초대받을 Member 슬롯이 없음)
  - 내담자 입장: 상담사 측에서 `Client` 를 만들어줘야 하는데 그 상담사가 Member 가 아님
  - 승인 대기 중 사용 경험이 전무함
- **선택지**:
  - **A**: **Claimable Center** — 내담자/상담사가 "내가 다니는 센터" 를 지목하면 시스템이 임시 `UnclaimedCenter` 레코드 생성 → 이후 실제 센터가 가입하면 승인과 동시에 기존 데이터 이관
  - **B**: **Personal Fallback** — 센터 승인 전까지는 각 상담사/내담자를 "Solo" 모드 (C6/C7) 로 운영하고, 나중에 센터 승인되면 Member/Client 를 migrate
  - **C**: 무시하고 "센터 승인 완료될 때까지 대기" 라는 UX 로 일관
- **우선순위**: **높음**. 이 경로가 막혀 있으면 영업 초기 바이럴 루프가 끊긴다.

### C6. Solo Practitioner — 센터(없음) + 상담사(사용) + 내담자(사용)

- **상황**: 프리랜서 상담사. 자기 내담자를 관리하고 싶지만 소속 센터 자체가 없음.
- **현재 대응**: **불가능**. 같은 NOT NULL 제약.
- **막히는 지점**: C5 와 동일 + 청구/정산도 "센터 단위 구독" 을 전제로 함.
- **선택지**:
  - **A**: **Personal Center 자동 생성** — 가입 시 1인 센터를 자동 생성하고 본인을 Admin 으로 세팅. 스키마 변경 최소. UX 상에서는 "센터" 개념을 숨김.
  - **B**: **Center Optional 리팩터** — `Member.center_id` / `Client.center_id` 를 nullable 로 전환하고 "소속 없음" 을 1급 시민화. 파급 매우 큼 (권한/쿼리/청구 전면 영향).
  - **C**: 이 케이스는 타깃 밖이라고 선언 (SMB/센터 중심 포지셔닝 유지)
- **우선순위**: 전략 의존. 포지셔닝 결정 필요.

### C7. Self-care Client — 센터(없음) + 상담사(없음) + 내담자(사용)

- **상황**: 일반 개인이 자가 검사(MMPI 자가형, 우울/불안 척도 등) 를 목적으로 플랫폼에 단독 가입.
- **현재 대응**: **불가능**. `Client.center_id` NOT NULL.
- **막히는 지점**: 검사 결과 해석을 누가 하느냐, 데이터 귀속이 누구냐 (본인 계정?), 청구 모델은?
- **선택지**:
  - **A**: Self-care 전용 라인 (검사/저널링만, 상담사 매칭 없음)
  - **B**: 검사만 수행 후 "상담사에게 공유" 버튼으로 센터/상담사 경로로 합류 → 내담자 유입 퍼널
  - **C**: 타깃 밖
- **우선순위**: B2C 진입 의사에 달림.

### C8. Pending Counselor — 센터(미등록) + 상담사(사용, 가입대기) + 내담자(미사용)

- **상황**: 상담사가 먼저 플랫폼에 가입하고 자기 센터를 끌고 들어오려는 경우. 센터 승인은 아직.
- **현재 대응**: Account/Person 까지는 만들 수 있으나 Member 가 없어 아무 기능도 못 씀.
- **막히는 지점**: 승인 대기 상태의 사용자 경험이 공백.
- **선택지**:
  - **A**: 가입 시 본인이 `CenterApplication` 을 제출하도록 유도 (applicant = 본인)
  - **B**: 승인 대기 중에는 "Personal Center" (C6 의 A안) 로 임시 운영 → 센터 승인 시 migrate
  - **C**: 가입 게이트 자체를 "센터 승인 후 초대" 로 막음 (현재 사실상 이쪽)
- **우선순위**: C5 와 묶어서 처리.

## 6. 공통 마찰 포인트 (케이스 전반에 걸쳐)

| 제약 | 영향 받는 케이스 | 해결 없이는 |
|---|---|---|
| `Member.center_id` NOT NULL | C5, C6, C8 | Solo / Pre-approval 경로 불가 |
| `Client.center_id` NOT NULL | C5, C6, C7 | Self-care / Shadow client 불가 |
| `CenterApplication` 수동 승인 | C5, C8 | 승인 대기 중 UX 공백 |
| `write:counseling` 권한 = 관리자 기본 | C6 (Solo 상담사 본인이 접수 필요) | Solo 상담사 기능 반쪽 |
| 내담자 앱 부재 | C5, C6, C7 의 내담자 측 | B2C/직접 유입 경로 없음 |
| 센터 단위 청구/구독 모델 | C6, C7 | Per-seat / per-person 과금 불가 |

## 7. 전략 옵션 카탈로그

아래는 **권고 아님**. 각 케이스의 "선택지" 에서 참조되는 옵션들을 한데 모은 카탈로그다.

### Option A — Personal Center 자동 생성

1인 상담사 가입 시 시스템이 "1인 센터" 를 자동 생성하고 본인을 admin member 로 등록.

- **장점**: 스키마 변경 최소. 기존 `center_id NOT NULL` 제약 유지. 권한/쿼리 코드 재사용.
- **단점**: UX 에서 "센터" 개념이 불필요하게 노출되면 혼란. 청구 모델이 1인 센터에 그대로 적용되면 과금 설계가 어색.
- **영향 범위**: auth signup flow, admin approval bypass, 청구 플랜 분리.

### Option B — Center Optional 리팩터

`Member.center_id`, `Client.center_id` 를 nullable 로 전환.

- **장점**: "소속 없음" 을 1급 시민화. C6/C7 자연스럽게 표현.
- **단점**: **파급 매우 큼**. 모든 쿼리가 `center_id IS NULL` 분기 고려 필요. 권한 모델(`access_level=all` 의 범위) 재정의. 유니크 제약(`uq_clients_center_code`) 재설계.
- **영향 범위**: 거의 모든 모듈. 마이그레이션 난이도 최상.

### Option C — Claimable / Shadow Center

내담자/상담사가 센터명을 입력하면 `UnclaimedCenter` 레코드 생성. 동일 센터를 가리키는 지목이 쌓이면 플랫폼 영업이 해당 센터에 컨택. 실제 센터가 가입하면 claim 프로세스로 기존 데이터 이관.

- **장점**: **B2B 영업 리드 자동 생성**. 하단 유저가 영업을 끌어오는 구조.
- **단점**: UnclaimedCenter ↔ Center claim 시 데이터 정합/소유권 이슈. 스팸 지목 방어 필요.
- **영향 범위**: center 도메인 확장 (신규 테이블), 내담자 web flow UI.

### Option D — Solo 상담사 전용 Role

기존 role-per-center 체계에서 "센터 소속 없음" 상담사에 적용할 글로벌 role 정의 + `write:counseling` 부여.

- **장점**: 권한 모델 일관성 유지.
- **단점**: Role 이 `center_id` 에 묶여 있어 우선 전제 조건으로 B 또는 A 옵션이 필요.
- **의존**: A 또는 B 선행.

### Option E — Self-care 전용 라인

검사/저널만 제공하는 별도 제품 라인. `Client` 가 아니라 별도 엔티티 `SelfCareUser` 로 분리.

- **장점**: 기존 센터 도메인을 건드리지 않음. B2C 가능성 탐색.
- **단점**: 제품 라인이 둘로 갈라짐. 임상적 책임 주체 공백 (결과 해석 누가).
- **영향 범위**: 신규 도메인 모듈 + 새 과금 모델.

### Option F — 현상 유지 (explicit)

"우리는 등록된 센터만 서비스한다" 를 정책으로 명문화하고 외의 케이스는 거절/대기.

- **장점**: 현재 코드 변경 없음. 메시지 명확.
- **단점**: 이탈 케이스는 경쟁사로 흘러감. 바이럴 유입 경로 없음.

## 9. 다음 의사결정 포인트

이 문서는 결정을 내리지 않는다. 결정이 필요한 질문들:

1. **포지셔닝**: 1차 타깃이 "센터" 인가 "개인 상담사" 인가? (A/B 선택의 프리컨디션)
2. **미등록 센터의 상담사·내담자를 유입시킬 것인가?** (C 채택 여부)
3. **B2C 를 하는가?** (E 채택 여부)
4. **승인 프로세스를 사람 없이 돌릴 수 있나?** (self-serve center approval — 현재 수동 승인이 병목)
5. **청구 모델을 per-seat / per-person 으로 재설계 하는가?**

각 질문의 결정이 확정되면 해당 도메인 (`center`, `auth`, `client`, `billing`) 의 `decision-log.md` 로 옮겨 기록한다.
