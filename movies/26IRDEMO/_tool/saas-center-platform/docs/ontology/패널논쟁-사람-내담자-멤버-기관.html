합의된 원칙

Person 비승격 AB

"Person을 신원 스파인으로 승격시키지 않는다"(합의 종결). Person = 계정 보유자의 크로스센터 앵커. 승격은 본인 앱 계정 순간(CenterLink)만. Person 자동 병합 금지 — 병합은 Client 층 수동 merge만. 근거: persons.account_id NOT NULL vs clients.person_id nullable

스크리닝 대상자 ≠ Client ABC

2테이블 깔때기 만장일치(B는 자기 client_stage안 철회). Client의 새 정의 = "개별 관리 관계를 맺은 사람". 탄생 관문은 승격 시트 하나. 전역 검색 정본은 Client만

role 3층 분리 ACB

저장: enum 3값 동결 / 정합: 관계 변경 시 재계산+감사(파생-검증값) / 표시: 관계에서 파생, 관계 없으면 무표시. 기관 트랙 화면·집계는 role 무참조(참조축=승격 여부·enrollment)

시간성 2원 AB

컨테이너 수명(org_units 행 valid_from/to) + 배정 구간(enrollments). period_key는 식별자에만. 소급 불변 3중: unit 행 불변 · enrollment append-only · 과거 참조는 당시 행

턴별 발언 전문

전체 기록은 패널논쟁-사람-내담자-멤버-기관.md가 정본. 아래는 동일 내용의 접이식 수록.

A Turn 1 — "스파인은 이미 맞다. 문제는 세 곳의 미완이다"

총론: Account(인증)→Person(자연인)→역할 인스턴스(Client/Member) 3층 스파인은 확장에 그대로 유효. persons.account_id NOT NULL(계정 가진 자연인) vs clients.person_id NULLABLE(계정 없이 존재)의 비대칭이 핵심 자산 — 학생·용사·환자는 계정 없이 등록되고 나중에 center_links로 접합. 고칠 곳 3: ① 테넌트 유형 부재 ② 외부 식별자 자리 부재 ③ 조직 위계 부재.

고유함 — 층마다 다른 규칙

Person=자연인 전역 1(account 1:1 유니크, 불변) / Client=테넌트 내(center_id+code 유니크, name+birth 차단) / Member=테넌트 내 직원(person_id NOT NULL).

주장 1: 학번·군번·환자번호는 Person이 아니라 Client 소유 — "기관이 부여한 역할 인스턴스의 좌표"(전학하면 바뀌고 병원마다 다름). Person에 올리면 테넌시 격리가 깨짐. 전용 테이블 client_identifiers + partial unique(JSONB엔 유니크 불가). 주민번호는 어느 층에도 금지. 병합은 Client 층 수동 merge만(관계·케이스 승계 + merged_into 마커), Person 자동 병합 금지(되돌릴 수 없는 개인정보 사고).

정보 — 컬럼 vs JSONB

"거르거나·정렬·집계할 정보는 컬럼, 보여주기만 할 정보는 JSONB"(아키타입 유도 규칙이 근거). Person 코어 불변. Client 코어 + extension JSONB(기관 팩이 키 선언·검증, 필터 수요 실측 시 컬럼 승격). EAV 금지(감사 체계 무력화). 주장 2: clients.name/phone 중복 저장은 결함이 아니라 계약 — 개명이 임상 기록을 소리 없이 바꾸면 안 됨.

기관 사상 — 어휘는 바뀌고 구조는 안 바뀐다

주장 3: Institution은 테넌트가 될 수 없다 — 테넌트는 영원히 Center(center_type enum 추가, institutions는 의뢰처 디렉터리로 강등). 주장 4: 조직 위계는 1급 테이블(org_units + clients.org_unit_id) — "3학년 2반 현황"은 group_by 질문이고 dim은 자기 FK여야(JSONB 불가). 주장 5: role enum 3값 동결 — 담임·지휘관·주치의는 관계(relation_detail)지 role 값이 아니다.

UI 계약

API는 중립 코드만, 어휘는 center_type 용어 팩(세션 1회 로드) · 프론트 한국어 분기 금지 · extension은 팩 서술자로 렌더 · 필터는 승격 컬럼만 · 외부 식별자 검색은 정확 일치 전용.

(c) 제외 부분 동의 + 1건 불가: 지휘관 계정·보존 엔진·절단선 로직 제외 동의(회차 purge 실행·threshold 기록 필드는 v1). ⚠ 익명 집계 화면+반출(n<5 게이트)은 제외 불가 — 계약 성립 조건. 수신자는 시스템 밖, 산출물은 시스템 안.

외부 확인: 군 국방망(최우선) / 상담관 훈령 / 교육부 검사 지침 / 만 14세 동의 / 판권. — "종단 계보와 집계 반출이 빠진 합의라면 나는 서명하지 않았을 것이다."

C Turn 3 — 최종: "안전은 사용자의 기억이 아니라 구조가 지킨다"

(a) 2테이블 지지: 판정 기준 — "기본 제외"가 네거티브 규칙이냐 위상적 사실이냐. client_stage면 Client 읽기 표면 십수 곳(목록·즐겨찾기·일정 피커·검사 접수·바우처·청구·알림·admin·에이전트 query_client)이 전부 필터를 기억해야 하고, 아키타입 자동 유도로 client_stage가 에이전트 필터에 자동 편입. 한 곳이라도 새면 800명이 자동완성·에이전트 답변에 침입. 2테이블이면 보장이 공짜 + 파기 오폭 구조적 불가능. 승격 시트는 mutation이 아니라 탄생(creation) — roster 프리필 Client 생성 폼.

(b) 방출 = 대시보드의 모드: 뷰 문법은 동일 아키타입, 새로운 건 방출 액션 표면(수신자→마스킹 미리보기→산출물 확정 게이트)+이력. "보이는 것=나가는 것". n<5는 플랫폼 고정·팩 완화 불가. 아키타입 총수 4 유지.

(c) 기간 스코프: 통합 검색창 유지 + periodic 감지 시 기간 칩 행([2026 ✓][2025][전체], 기본=팩의 현재 period). 자동완성은 현재 기간만. 검색어 문법은 만들지 않는다 — 스코프는 항상 시각적 칩.
