먼저 — 궁극 목표와 두 트랙

궁극 목표 (한 문장)

기존 스키마(테이블)는 최대한 건드리지 않고, 그 위에 "온톨로지 레이어"를 얹어서 — 나중에 군대·학교·병원으로 확장할 때 코드가 아니라 레이어의 설정(프로필)만 추가하면 되게 만든다.

온톨로지 레이어가 뭔가

"내담자·학생·환자·장병은 사실 같은 개념(서비스 대상자)이고, 기관마다 부르는 말과 화면만 다르다" — 이 공통 개념을 코드 바깥의 데이터(정의서)로 만든 것입니다. 3장짜리 문서라고 생각하면 됩니다:

맨 아래: 기존 테이블 (원칙적으로 불변)clients · members · centers · cases · sessions … 지금 그대로. 이번에 추가하는 컬럼은 centers.center_type(기관 유형) 하나뿐.
▲ ② 바인딩이 연결
가운데: 온톨로지 레이어 (이번에 만드는 것) ① 개념 카탈로그 — 중립 개념 목록: Subject(대상자)·Guardian(보호자)·Practitioner(제공자)·Organization(조직)·Encounter(만남)… 각각의 속성·관계 정의
② 바인딩 — 개념이 실제 어느 테이블·컬럼·API에 사는지 연결표: "Subject = clients 테이블, Subject.이름 = clients.name"
③ 버티컬 프로필 — 기관 유형별 해석: 학교 프로필이면 "Subject를 '학생'이라 부르고, Guardian은 '학부모', 첫 화면은 명부" / 군 프로필이면 "Guardian은 없음"
▼ 소비자가 레이어를 읽음
맨 위: 레이어를 읽는 것들화면(라벨·탭·첫 화면을 프로필에서) · graph explorer(카탈로그+바인딩을 그래프로 그려서 눈으로 확인) · 새 기관 온보딩(프로필 파일 하나 추가 = 끝)

이게 되면 뭐가 좋아지나 — "군대 버전 만들어주세요"가 왔을 때

지금:   군대용 화면·용어·로직을 코드에 분기 추가 → 몇 주 개발
목표:   military.json 프로필 하나 작성 →
        { "Subject": "장병", "Guardian": null(없음), "첫화면": "명부", "식별자": "군번" }
        → 화면·explorer가 자동으로 군대 모습이 됨. 코드 변경 0.

왜 트랙이 두 개인가

레이어를 만들다 보면 기존 테이블에 대응물이 아예 없는 개념이 나옵니다 — 조직 단위(반·중대), 스크리닝 명부(전교생 명단). 이건 레이어(매핑)로는 해결이 안 되고 저장 공간이 실제로 필요합니다. 그래서:

  • 트랙 1 (레이어): 개념 카탈로그·바인딩·프로필·소비자. 스키마 변경 거의 0. — 궁극 목표 그 자체
  • 트랙 2 (스크리닝 기능): 대응물 없는 개념 중 사업상 당장 필요한 것(조직 단위·명부)만 새 테이블로 구현 + 그 화면들
  • 연결 규칙 하나: 트랙 2가 만드는 테이블·API는 반드시 트랙 1 카탈로그의 개념 이름·속성을 따라 만든다. (트랙 1이 먼저 개념 정의를 내려놓고, 트랙 2가 그걸 구현하는 순서 — 안 그러면 나중에 레이어에 안 붙는 섬이 생김)
🔴 아직 만들면 안 되는 것 (대표 결정 대기): ① 외부 기관(교육청·부대)에 통계 내보내기 ② 검사 점수를 화면에 어디까지 보여줄지 ③ 명부의 사람을 승격할 때 과거 기록 자동 연결. — 이 셋만 피하면 전부 오늘부터 시작 가능.
⚠ 전원 공통 규칙: ① 화면에 "Person", "Account" 같은 시스템 내부 개념을 글자로 노출하지 않기 ② 어떤 직원이 내담자이기도 하다는 사실은 어떤 화면에도 표시하지 않기 ③ 5명 미만 통계 가리기는 서버가 한다.

트랙 1 — 온톨로지 레이어 (궁극 목표)

담당: BE-B(정의·바인딩 — 먼저 이것부터) + FE-B(소비자 구현) + 디자이너(프로필 내용). 스키마 변경: center_type 컬럼 1개.

백엔드 — BE-B ①

먼저 맡는 것: 레이어의 정의 그 자체 — 개념 카탈로그 + 바인딩 표. 이게 나와야 두 트랙이 다 돈다 (그다음에 아래 트랙 2로 넘어감)

1. (최우선, 3일 내) 개념 카탈로그 초안중립 개념 10±개(Subject·Guardian·Practitioner·Organization·OrgUnit·Encounter·Episode·Assessment·Identifier·Referral)의 속성·관계 + 기관별 존재 여부 표. 맨땅이 아님 — docs/ontology/도메인-API흐름-온톨로지-분석.html §4 매핑 표가 초안의 8할
기계가 읽을 수 있는 형식(JSON/YAML) + 사람이 읽는 설명 1장
2. 바인딩 표개념→기존 테이블·컬럼·API 연결. "Subject=clients, Guardian=clients(role=guardian)+client_relations, Organization=centers…". 대응물 없는 개념(OrgUnit·Roster)은 "미구현 — 트랙 2가 구현"으로 표시
FE-B가 이 표만 보고 explorer를 그릴 수 있음
3. center_type 컬럼 + 프로필 데이터 형식 확정프로필 JSON 스키마(디자이너 사전이 담길 그릇) — FE-B·디자이너와 첫 주에 합의

프론트 — FE-B

맡는 것: 레이어의 소비자 — 프로필 로더, 기존 화면의 하드코딩 걷어내기, graph explorer

시작 전에 이해할 것

① "학교 버전"은 새 화면이 아니라 프로필이다

API는 role: "client" 같은 중립 코드만 줍니다. 화면에 "내담자"라 쓸지 "학생"이라 쓸지는 그 센터의 center_type이 가리키는 프로필이 정합니다. 그런데 지금 코드엔 features/clients/constants.ts에 "아동"이 하드코딩돼 있는 식의 위반이 있습니다 — 이걸 걷어내고 프로필을 읽게 바꾸는 게 이 작업의 절반.

② 프로필은 단어만이 아니라 화면 구성도 정한다

군대엔 "보호자" 개념이 없습니다 → 군 프로필에선 보호자 탭이 번역되는 게 아니라 아예 안 생겨야 합니다. 프로필이 정하는 것 = 단어 + 탭 구성 + 첫 화면 + 검색 방식. 컴포넌트는 하나, 프로필 데이터로만 달라짐.

③ explorer는 레이어의 거울이다

graph explorer는 예쁜 그림이 목적이 아니라 "카탈로그+바인딩이 실제 데이터와 맞는지 눈으로 확인하는 도구"입니다. BE-B의 카탈로그·바인딩 표를 입력으로 받아 그대로 그리세요 — explorer에 별도 하드코딩이 생기면 목적이 무너집니다.

할 일

1. 프로필 로더center_type → 프로필 JSON 로드(로그인 시 1회) → 전 화면이 읽는 스토어/헬퍼
center_type만 바꾸면 재배포 없이 "내담자 관리"→"학생 관리", 보호자 탭 유무가 바뀜
2. 하드코딩 걷어내기역할·관계 한국어 리터럴 전수 수색 → 프로필 키로 교체, 탭 구성도 프로필에서
clients 화면군에서 역할·관계 한국어 리터럴 0건 (grep으로 확인)
3. graph explorer카탈로그·바인딩을 읽어 개념 그래프 + 실제 데이터 조회. 팬·줌 캔버스는 docs/ontology/API-관계도-캔버스.html 코드 재사용
카탈로그에 개념을 추가하면 explorer에 코드 수정 없이 나타남 · Person·Account 노드 없음

디자이너 — DE (두 트랙 겸)

맡는 것: 프로필 4종의 내용(기관별 말 사전) + 트랙 2 신규 화면 시안 + "보여주면 안 되는 것" 가이드

시작 전에 이해할 것

① 프로필의 내용물은 디자인 산출물이다

"내담자→학생"은 번역이 아니라 그 기관 사람들이 실제로 쓰는 말과 안 쓰는 말의 목록입니다. 군대에 "보호자"가 없다는 것, 학교의 공식 용어가 "관심군"이라는 것 — 개발자가 정할 수 없는 영역이고, 이 사전의 품질이 "오, 우리 기관용이네"라는 첫인상을 결정합니다. 각 프로필에는 단어 + 탭 구성 + 첫 화면 + "이 기관에 없는 개념" 목록이 들어갑니다. (형식은 BE-B·FE-B와 첫 주 합의, 내용은 전적으로 DE 소유)

② 이 제품은 "안 보여주는 것"이 기능이다

심리 데이터라서요. 공통 규칙 3가지(§0)의 화면 적용 예시집 — 해도 되는 표현/안 되는 표현을 나란히 — 을 만들면 모든 PR의 체크리스트가 됩니다.

할 일

1. (최우선) 명부 화면 + [개별 관리 시작] 시안트랙 2의 FE-A 착수 조건. 800행 표의 정보 우선순위, 발송/회수/판정 컬럼, 승격 플로우
3일 내 전달 · FE-A가 추가 질문 없이 1차 구현 가능

FE-B가 그대로 JSON에 옮길 수 있는 표 형태
3. 통계·explorer 시안가려진 칸 표현(빈칸 금지 — "5명 미만 비표시"가 읽히게) 포함

트랙 2 — 스크리닝 기능 (대응물 없는 개념의 구현)

담당: BE-B(테이블·API) + FE-A(화면). 새 테이블 허용 — 단 트랙 1의 개념 카탈로그에 정의된 이름·속성을 따라 만든다. 기존 테이블은 안 건드림.

이 트랙의 배경 — 깔때기

학교·군대 영업의 핵심은 "전체 검사(스크리닝)"인데, 전교생 800명을 내담자로 등록하면 기존 목록·검색·일정이 전부 오염됩니다. 그래서:

전교생 800명 명단 업로드→ 검사 발송·회수→ 기준 넘은 12명→ [개별 관리 시작] → 그때부터 내담자

명단은 별도 테이블(명부)에 두고, 걸러진 소수만 내담자로 "승격"합니다. 회차가 끝나면 명단은 통째로 삭제 가능, 승격된 사람의 기록만 남습니다. 조직 단위(반·중대)도 기존 테이블에 없어서 이 트랙에서 새로 만듭니다.

백엔드 — BE-B ②

그다음 맡는 것: 새 테이블(조직 단위·명부·회차)과 그 API — 반입·파기·집계. 트랙 1에서 본인이 정의한 개념 이름·속성을 그대로 따라 만들면 됨

시작 전에 이해할 것 3가지

① "3학년 2반"은 매년 새로 만들어지는 행이다

2026년의 3-2와 2027년의 3-2는 이름만 같지 구성원·담임이 다른 실체. 조직 단위 행에 시작일·종료일을 두고 학교 반은 1년짜리, 군 중대는 종료일 없는 행으로. 끝난 행은 수정 금지(고칠 일 있으면 종료+새 행) — 안 그러면 작년 통계가 나중에 슬쩍 바뀝니다.

② "지금 어느 반"과 "그동안 어느 반이었나"는 저장 위치가 다르다

현재 소속 = clients 캐시 컬럼(빠른 조회), 이력 = 배정 테이블(추가만, 삭제 없음).

③ 명부가 내담자와 다른 테이블인 이유

  • 내담자에는 코드 발급·중복 검사 절차가 붙어 있어 800명 일괄이 안 됨
  • 내담자는 표시만 삭제(soft delete), 명부는 회차 끝나면 진짜 삭제
  • 테이블이 다르면 기존 화면·검색·AI 조회가 수정 없이 안전

할 일

1. 조직 단위 + 배정 이력 API
반 이동시키면 이력이 남고 캐시 갱신 · "반별 인원" 집계가 나옴
2. 명부 엑셀 반입 API업로드→검사→미리보기→확정
800행 10초 내 · 오류는 "몇 번째 줄이 왜" · 두 번 올려도 중복 없음
3. 회차 삭제(파기)
파기해도 승격된 내담자 데이터는 멀쩡함을 테스트로 증명
4. 통계 API (내부용)회차별·반별 + 5명 미만 가리기
API 직접 호출로도 5 미만 숫자 안 나옴

🟡 팀 논의 후 결정

🔴 만들지 않기

프론트 — FE-A

맡는 것: 스크리닝 화면 4개 — 명부, [개별 관리 시작], 조직 편성, 통계

시작 전에 이해할 것 — 사용자가 다르게 생각한다

상담사는 "아이 한 명 한 명"을 봅니다(한 명 등록, 프로필, 일정). 학교·군대 사용자는 "명단을 굴립니다" — 800명 올리고, 검사 뿌리고, 회수율 보고, 걸러진 소수만 들여다봄. 일하는 방식이 달라서 새 화면을 만듭니다.

꼭 지킬 것: 명단 800명이 기존 화면에 새면 안 된다

명부는 회차 화면 안에서만. 내담자 목록·전체 검색·일정의 사람 선택·자동완성 어디에도 안 나옴.

[개별 관리 시작] = 기존 내담자 등록 폼이 미리 채워져 열리는 것

저장하면 진짜 내담자가 되고, 기존 등록 화면의 노란 중복 경고 배너를 그대로 재사용("비슷한 기록이 있어요 → [기존 기록 열기] [새로 등록]"). 명부 행에는 "관리 중" 배지만 남음.

실제 사용 흐름 (학교 상담 선생님의 검사 주간)

  1. 행정실에서 받은 엑셀을 회차에 업로드 → 오류 3줄 고치고 확정
  2. 명부에서 반별 발송 → 매일 회수 상태 확인
  3. 회수 끝 → 정렬 → 기준 넘은 12명 확인
  4. 12명 [개별 관리 시작] → 이 12명만 기존 내담자 화면에 등장
  5. 학기 끝 → 회차 삭제 → 명단은 사라지고 12명 기록은 그대로

저장하면 내담자 목록에 등장 · 명부 행에 배지 · 중복이면 기존 기록 연결 가능
