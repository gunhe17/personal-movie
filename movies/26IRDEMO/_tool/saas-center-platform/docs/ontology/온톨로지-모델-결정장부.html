온톨로지 모델 결정 장부 사람·기관 축 v1

2026-08-12 확정. 질문 6개(고유함 → 필드 → 기관별 변환 → 화면 표현 → 멘탈 모델 → 제품별 분화)를 사람 축 · 기관 축 두 라운드로 하나씩 짚어 합의한 결과. 이 장부가 최종 산출물 두 개 (① 온톨로지 graph explorer ② UI/UX 통일성 개선)의 유일한 입력이다. 목적: 비즈니스 대상(학교·병원·군대)이 바뀔 때마다 서비스를 새로 수정하지 않고, 프로필 추가만으로 적용되게 하는 것.

1

공리 7 — 모든 후속 판단의 기준

A1고유함 = 기관 스코프 + 식별자 수명

사람의 전역 통합은 하지 않는다(개인정보). 계정 연결(person)이 유일한 전역 고리 — 옵션이지 전제가 아님. 단 기관은 전역 디렉터리 — 공개 정보라 리스크 구조가 반대(학교코드·요양기관번호 등 공적 코드가 정본).

A2필드 3분류: 코어 / 역할 기록 / 가변

코어 = 모든 기관에서 의미가 같은 최소(변환되지 않는 것). 역할 기록 = 기관이 값을 소유(개명해도 차트 표기는 불변). 가변 = 프로필이 선언.

A3변환 3종: 어휘 / 존재 / 속성

어휘=사전 한 장. 존재=제거(번역 아님) — 프로필에 없는 개념은 화면·입력·관계에서 아예 안 생긴다. 속성=프로필이 선언.

A4온톨로지는 '순간'으로만 노출

화면에 명사(Person·계정 등)로 노출 금지. 허용 순간 화이트리스트: 중복 경고·병합 제안 / 앱 연결 배지 / 외부 기관 자동완성 제안 / 관리자 병합 화면. graph explorer는 내부 도구로서 예외.

A5프로필은 주입 시점 중립

독립 정의(파일/데이터)로 만들어 SaaS에선 런타임 로드, 납품에선 빌드타임 주입(기관 에디션 생성 — 군 격리 배포 대비). DB 설정 전용으로 만들면 납품의 문이 닫힌다.

A6화면 분화의 정본 축 = 코어 루프(용도), 기관 아님

기관 차이는 프로필(어휘·존재·속성)로 흡수. 새 화면군은 일하는 방식이 다를 때만 — v1의 신규 루프는 검사용(명단→발송→집계→소수 개별 관리) 하나.

A7새 개념 도입 = 기존 고객 무영향

센터 프로필이 선언하지 않은 것(조직 위계 등)은 현행 센터 화면에 생기지 않는다. 확장 작업이 기존 제품을 건드리지 않음을 구조로 보장.

2

사람 축 확정

개념: 자연인 · 대상자 · 보호자(=관계) · 직원

현재 저장: persons(계정 1:1) / clients(person_id nullable — 계정 없이 존재가 기본값) / members(person 필수) / 보호자=clients 행+관계 테이블

D1
고유함: 기관 내 유일까지만

내부 코드(정본) + 이름+생년(중복 방지 휴리스틱). 크로스 기관 신원 통합 안 함. 외부 식별자는 수명이 있다 — 학번=번호+연도(매년 재사용), 군번·환자등록번호=평생.

D2
코어 4개: 이름 · 생년월일 · 성별 · 전화

이메일·주소는 역할 기록으로(학교·군에서 비수집). 생년은 전 기관 공통 중복 방지 키 + 연령 정책 입력. clients의 name/phone 중복 저장은 버그가 아니라 "기관은 자기 기록의 표기를 소유한다"는 규칙.

D3
role(client/guardian/both)은 관계의 요약 캐시

모델의 정본은 관계("대상자다/보호한다"). both가 화면에서 뭉개지는 현상은 캐시를 정본처럼 쓴 결과 — 라벨은 관계에서 파생한다.

D4
보호자의 화면 정본 = 관계

목록 기본은 대상자만, 보호자는 대상자 행의 부속 정보 + 검색 시 "누구의 보호자"로 부상. 등록 화면의 현재 은유("함께 저장돼요")가 정본, 목록이 따라온다. 저장 구조는 불변.

기관 축 확정

개념: 테넌트 · 외부 기관 · 조직 단위 · 계약 조직

현재 저장: centers(유형 필드 없음) / institutions(이름·주소뿐, 역할 미정의) / directory_centers(공공 명단 — 전역 디렉터리 선례) / 조직 단위·계약 조직 없음

D5
외부 기관 = 전역 디렉터리

공적 코드(학교코드·요양기관번호)가 고유함의 정본, 없으면 이름+주소. 센터는 참조만. 사람과 반대인 이유: 기관은 공개 정보 + 교육청 단위 사업에서 전역 식별이 필수.

D6
테넌트의 유형 필드 = 프로필 포인터

기관 축과 프로필 체계가 만나는 유일한 접점. 테넌트에 유형별 가변 필드를 두지 않는다 — 차이는 프로필이 담당.

D7
조직 위계의 모양은 프로필이 선언

학교=학년>반, 군=대대>중대>소대, 병원=진료과>병동, 센터=없음. 테넌트는 틀 안에서 칸(3-2, 1중대)만 생성. 칸은 기간을 가진다 — 2026년 3-2 ≠ 2027년 3-2 (사람 축 식별자 수명과 대칭).

D8
외부 기관 입력 = 자유 입력 + 디렉터리 제안

강제 선택 금지. 타이핑하면 제안이 뜨고, 무시하면 텍스트로 남되 뒤에서 매칭 — 사람 축 중복 경고와 대칭인 '순간' 패턴 (A4 화이트리스트 등재).

군대(수요 적음)같은 신규 루프 + 군 프로필 + 격리 배포 가능성(A5)

세로(기관)로는 화면이 갈라지지 않고 가로(용도)로만 갈라진다. 학교와 군대는 다른 제품이 아니라 같은 검사용 화면군에 다른 프로필을 꽂은 것. 신규 루프는 "개별 관리 시작" 이후 기존 상담용 화면으로 합류하며, 합류 지점의 신원 판단은 A4의 병합 제안이 담당.

5

미결 (별도 트랙) · 산출물 연결

미결: ① 기관별 배포 모드 — 사업 결정 + 군 국방망 요건 외부 확인 (A5 덕에 모델 작업을 막지 않음) ② 계약 조직 구현 시점 — 교육청·사단 계약이 실물일 때
이 장부 → 산출물: graph explorer = §2·§3의 개념·관계·바인딩(개념↔실제 테이블)을 그대로 그리는 내부 도구(A4의 예외 공간). 카탈로그에 개념을 추가하면 코드 수정 없이 그래프에 나타나야 한다. UI/UX 통일성 개선 = D3·D4(role 파생·보호자 관계 통일) + 어휘 하드코딩 제거(A3 어휘 변환의 전제) + A4 화이트리스트 밖 노출 제거 — 수정 목록이 이 장부에서 기계적으로 도출된다.
