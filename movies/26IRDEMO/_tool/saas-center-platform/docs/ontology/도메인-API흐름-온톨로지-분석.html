신원 스파인 — Account ↔ Person ↔ 역할 인스턴스

온톨로지의 척추. "한 사람"이 시스템에 세 층으로 존재한다: 로그인 주체(Account) → 자연인(Person) → 컨텍스트별 역할 인스턴스(Member·Client·FamilyMember). 이 3층 구조는 이미 서 있고, 기관 확장 시에도 그대로 간다 — 바뀌는 것은 역할 인스턴스의 종류와 어휘뿐.

LAYER 1 — 인증 주체

Account accounts

email · password · provider(소셜) · token_version — 프로필 필드 없음(건전). JWT: 직원=aud 없음 / 내담자 앱=aud=client_app 상호 차단. 예외: admin_accounts(플랫폼 운영자, Person 미연동 별도 체계)
▼ 1:1 — persons.account_id (NOT NULL, soft-delete unique)
LAYER 2 — 자연인 (전역, 테넌시 무관)

Person persons

name · phone · birth · gender · is_certified — 시스템에서 "사람"의 유일 신원. 온톨로지 중립 개념 그대로.
▼ 1:N — 컨텍스트마다 역할 인스턴스 (Party-Role 패턴)
Member members 센터 스코프
person_id NOT NULL · role_id → Role(code: ADMIN/MANAGER/COUNSELOR/STAFF, access_level all/own) · status
직원은 반드시 실존 인물. 센터당 1행.
Client clients 센터 스코프
person_id NULLABLE · role: client|guardian|both · name/phone 중복 저장(미연동 대비 비정규화)
통합 연락처 DB — 1인 1레코드/센터, 계정 없이도 존재.
FamilyMember family_members 전역 평면
family_id · person_id · role(owner/member)
내담자 앱 세계 — Family → Profile → CenterLink가 테넌트로 건너가는 다리.
CenterLink center_links = 전역(family_id·profile_id·person_id) ↔ 테넌트(center_id·client_id·guardian_client_id) 다리 · 상태 requested/active/suspended · append-only 감사(center_link_audits)

한 사람 = 여러 역할 (실제 데이터 형태)

사례데이터비고
A센터 보호자 + B센터 내담자Person 1행 : Client 2행(센터별)구조가 지원 — Person 1 : Client N
내담자이자 보호자(형제 케이스)Client 1행, role="both"role enum에 조합이 박힘 — 역할 늘면 N×N 폭발
같은 센터에서 직원이면서 내담자Member 1행 + Client 1행 (같은 person_id)가능 — 단 같은 센터 내 Client 중복 생성은 차단
흐림 지점 1 — Client가 Person 필드(name·phone)를 중복 저장. person_id 미연동 대비 비정규화인데, 연동 후 동기화 계약이 암묵적. 온톨로지에서 "override는 언제 유효한가"를 명시해야 함.
흐림 지점 2 — role="both"는 역할 조합을 enum에 인코딩한 것. 일반화하면 Party-Role 다중 행(Subject + SubjectRole N행)이 정본.
보존할 것 — Account(인증)/Person(자연인)/역할 인스턴스(테넌트 스코프) 3층 분리와 CenterLink(전역↔테넌트 다리) 패턴은 기관이 바뀌어도 그대로 간다.

온톨로지 시스템 설계 방향 (다음 단계 입력)

분석의 결론: 구조는 이미 절반 중립적이다. Account/Person/역할 3층, 테넌시 강제, 참여자 다형, 검사 플러그인 SPI는 보존 대상. 확장을 막는 것은 ① enum에 박힌 어휘 ② 조직 위계 부재 ③ Entitlement 단일형 — 셋뿐이다.

P1
어휘 카탈로그화 (스키마 무수술)

RoleCode·ClientRole·ParticipantType·relation_detail 등 하드코딩 enum을 organization_type별 어휘 카탈로그(설정)로 분리. 중립 코드가 정본, 기관별 표시명은 레이블. UI/UX ↔ API 사이 번역층의 첫 조각.

P2
Organization 일반화

Center.organization_type(counseling_center/school/military/hospital) 추가 + OrganizationUnit(parent 자기참조·unit_type) 신설. 기존 center_id 쿼리는 그대로 유효(root unit 자동 생성으로 역호환). institutions 모듈의 역할을 이때 확정.

P3
Party-Role 다중화

role="both" 같은 조합 enum을 역할 인스턴스 N행으로 정규화. 관계(ClientRelation/SiblingRelation)를 "혈연" 전제에서 CohortMembership(학급·중대·병동)과 RelatedParty(보호자·간병인) 두 축으로 분리.

P4
Entitlement 3형 + 수량 단위 추상화

선지급(현 바우처) / 역청구(교육청·국방 예산: 승인 상태 머신) / 보험심사(수가 코드·심사액·payer 분할). quantity_unit(회기/시간/건/수가)으로 소진 단위 일반화. Charge·Payment 골격은 유지.

P5
검사 스크리닝 표면 확장

익명 수검(participant_type=anonymous) · 보고 가시성 등급(본인/보호자/지휘부/기밀) · 상급 조직 집계 read-model(학년별·부대별 고위험군). 엔진 SPI와 무인증 채널은 그대로 활용 — 스크리닝 피벗과 직결.

원칙 — 온톨로지의 정본은 중립 개념(영문 코드), 기관별 어휘는 표시층. 코어 구조·정체성은 항상 기관 유형 중립으로 유지하고(아동 발달은 비치헤드), 기관 특화는 카탈로그·템플릿·정책 팩으로 주입한다.
