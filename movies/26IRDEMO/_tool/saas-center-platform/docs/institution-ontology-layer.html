02

레이어의 위치와 책임

Microsoft Graph의 발상 — 하나의 리소스, 여러 표현. 무엇을 소유하고 무엇을 소유하지 않는가.

MS Graph에서 /users/{id}는 언제나 같은 리소스지만, 요청하는 애플리케이션과 스키마 확장(extensions)에 따라 다른 필드 집합으로 응답한다. 리소스는 하나, 투영은 여럿이다. 우리가 빌려올 것은 정확히 이 구조다.

다만 Graph와 다른 점이 하나 있다. Graph의 확장은 임의 키-값이지만, 우리는 기관 타입이 곧 스키마다. 학교를 선택하면 확장 속성이 자동으로 「학년·반·담임」으로 결정된다. 센터가 마음대로 키를 만드는 게 아니라, 온톨로지가 정의한 집합을 받는다.

03

Person · Account · Client · 기관 — 개념 재정의

네 개념이 이미 잘 분리돼 있다. 기관 확장 시 각각의 역할이 어떻게 달라지는지.

다행히 현재 구조가 확장에 유리하다. Account(로그인)와 Person(사람)이 분리돼 있고, Client는 센터별 레코드다. 실측한 연결 구조는 Account → Person → Member → Center이며, Client는 person_id가 nullable이라 계정 없는 대상자도 존재할 수 있다.

확인 필요Person 중복이라는 진짜 문제

Client.person_id가 nullable이라, 실무에서는 Person 없는 Client가 대량으로 생긴다. 심리센터에서는 이게 괜찮았다 — 내담자가 앱을 안 쓰면 그만이니까. 그런데 학교·군대에서는 다르다. 학생·장병은 기관이 이미 명부를 갖고 있는 사람들이고, 전입·전출·진급이 일어난다.

즉 기관 확장의 실제 난점은 온톨로지가 아니라 명부 동기화일 수 있다. 이 문서는 표현 레이어를 다루지만, 이 지점은 별도 과제로 떼어놔야 한다 → §7 Q4.

04

공통 필드와 기관별 확장

화면이 실제로 요구하는 정보를 실측한 뒤, 무엇이 코어이고 무엇이 확장인지 가른 결과.

판정 기준은 하나다. 1차 세 기관 전부에서 의미가 성립하면 코어, 하나라도 비면 확장. "있으면 좋은 것"이 아니라 "없으면 화면이 깨지는 것"이 코어다. EAP 열은 보류 표시로 남겨둔다 — 재개 시 판정을 다시 하지 않기 위한 기록이다(§13).

07

결정해야 할 것

이 문서가 답하지 못하는, 팀이 정해야 하는 질문들. 순서는 의존도 순.

  1. institutions 이름 충돌을 어떻게 정리하나 기존 테이블은 「단체검사 의뢰기관」이고 우리가 원하는 의미가 아니다. 선택지는 ⓐ 기존을 referral_organizations로 개명하고 institutions를 새 의미로 확보, ⓑ 온톨로지는 org_type으로만 부르고 새 테이블을 만들지 않음 — Center에 컬럼 추가로 충분, ⓒ 그대로 두고 이름만 다르게. ⓑ가 가장 싸다.
  2. 온톨로지 정의를 코드로 둘까, DB로 둘까 코드(Python 상수 + API 노출)면 리뷰·타입체크가 되지만 기관 추가에 배포가 필요하다. DB면 운영자가 추가할 수 있지만 검증이 약해진다. 초기 3종(+기본값)은 코드, 안정화 후 DB 이관을 제안하지만 결정 필요.
  3. EAP 익명 정책을 표현으로 볼 것인가, 권한으로 볼 것인가 결정됨 — 1차 제외 §5에서 드러난 유일한 규칙 충돌이었다. 온톨로지가 마스킹을 선언해도 강제는 API에서 일어나야 안전하고, 그러면 §2의 「응답 필드는 항상 동일」 규칙에 예외가 생긴다. EAP를 1차 범위에서 빼기로 결정했으므로 이 예외는 지금 만들지 않는다 — §2 불변 규칙이 온전히 유지된다. 재개 조건은 §13.
  4. 명부 동기화를 이 범위에 넣을 것인가 학교·군대는 기관이 이미 명부를 갖고 있고 전입·전출·진급이 일어난다. 이건 표현 레이어가 아니라 별도 과제다. 1차 범위에서 빼고 수기 등록 전제로 가는 것을 권장하되, 뺐다는 사실을 명시해야 나중에 놀라지 않는다.
  5. attributes JSONB의 unique·검색 성능 군번·학번으로 검색·중복검사가 일어난다. JSONB 부분 인덱스로 충분한지, 아니면 자주 쓰는 키만 생성 컬럼으로 승격할지. 실측 후 결정 — 지금 판단하면 「될 것 같다」로 구현하는 것.
  6. 기존 200파일 인라인 문자열을 언제 걷어내나 한 번에 전부는 불가능하다. 온톨로지 레이어를 만들어도 기존 화면은 여전히 하드코딩이다. 신규 화면부터 적용 + 내담자 화면군만 우선 전환이 현실적이지만, 그동안 두 방식이 공존한다는 비용을 감수해야 한다.
  7. 성별 2값 강제를 먼저 풀 것인가 MALE/FEMALE만 있고 매핑 실패 시 FEMALE로 폴백하며 아바타 색까지 결정한다. 기관 확장과 독립적인 기존 결함에 가깝다. 온톨로지 작업과 묶을지, 별도로 처리할지.

검증 먼저 — 구현 순서 제안

"될 것 같다"로 시작하지 않기 위한 최소 실험.

이 설계에서 가장 불확실한 건 "온톨로지 정의만으로 화면이 정말 구성되는가"다. 전면 착수 전에 이것부터 확인한다.

0단계 — 종이 위 검증 (착수 전)

§6 스펙을 1차 세 기관 전부에 대해 손으로 다 써본다. 학교·군대만 쓰면 잘 맞는 것처럼 보인다. 병원의 진단코드·이중 식별번호가 스펙 형식을 깨는지가 진짜 시험이다. 여기서 형식이 부러지면 스펙을 고치는 게 코드를 고치는 것보다 100배 싸다. (EAP 익명은 1차 범위 밖이라 지금 답하지 않아도 된다 — §13.)

1단계 — 내담자 목록 하나만 (실측 실험)

/clients 목록 단 하나를 온톨로지 기반으로 다시 그린다. org_type 컬럼 추가 + 정의 API + 목록 컬럼·1차 축·라벨 소비까지. 기존 화면은 건드리지 않고 병존시킨다.

확인할 것: 축 교체가 탭·필터·정렬까지 자연스럽게 전파되는가. 여기서 막히면 설계가 틀린 것이다.

2단계 — attributes 저장·검색

clients.attributes JSONB 추가, 등록폼에 온톨로지 기반 필드 생성, 군번·학번 unique 검증과 검색 성능 실측(§7 Q5의 답). 실제 데이터 규모로 확인한다 — 합성 데이터 통과는 보증이 아니다.

3단계 — 상세·등록폼 확산, 그 다음 나머지

내담자 화면군을 완성한 뒤 Member·Center로 넓힌다. Case·Session은 §4에서 확인했듯 대부분 중립이라 라벨 교체만으로 상당 부분 커버된다 — 가장 나중에 해도 되는 영역이다.

이 문서의 한계 네 기관의 실제 요구사항은 현장 확인 없이 추정한 것이다. 학년·반·담임은 확실하지만, 군의 보안등급이나 병원의 진단코드 연동이 실제로 필요한지는 해당 기관 담당자에게 확인해야 한다. 스펙 형식(§6)은 재사용 가능하되, 개별 attributes 목록은 초안으로 읽어야 한다.

발견대응
슬롯 03이 공통으로 필요하다 — 학적/복무/진료/소속 정보. 네 기관 전부 「이름 아래, 사전기록지 위」에 기관 고유 정보 블록을 원한다. 온톨로지의 attributes를 렌더하는 단일 슬롯 신설. 기관마다 다른 컴포넌트가 아니라 스키마 기반 1개.
가족관계·앱연결이 함께 사라진다 — 군·EAP에서 둘 다 죽는다. 두 슬롯은 사실 같은 축(보호자 존재)에 매달려 있었다. relations.guardian.enabled: false 하나로 두 슬롯이 동시에 꺼지게 — §6 스펙이 이미 이 형태.
진행현황 2열이 하드코딩 — 상담·검사 고정. 병원은 3종 이상이 자연스럽다. 온톨로지가 progress_items 배열을 주고 grid 열 수를 길이에서 파생.
아바타 색이 성별 의존 — MALE이면 blue, 아니면 red. EAP 마스킹 시 성별이 없어 전원 red가 된다. §7 Q7과 묶어 처리. 성별 대신 이름 해시 기반 색 등 기관 무관한 규칙으로 교체 검토.
EAP만 성격이 다르다 — 나머지 셋은 「슬롯 채우기」인데 EAP는 「슬롯 비우기」다. 반영됨 1차 범위를 학교·군대·병원으로 확정. EAP는 §13으로 분리.
1단계 범위에 주는 함의 §8의 1단계는 「목록 화면 하나」였다. 이 그림을 그려보니 카드가 상세보다 훨씬 싸다 — 카드는 슬롯 3개 내용 지정으로 끝나지만, 상세는 신규 슬롯 1개 + 조건부 소거 2개 + 진행현황 가변화가 함께 필요하다. 1단계를 목록(카드+테이블)까지만으로 명확히 긋고, 상세는 2단계 attributes 저장이 끝난 뒤로 미루는 게 맞다.

원칙 한 줄 조건문을 없애는 게 아니라, 한 곳으로 모은다. 기관별 분기는 어딘가에 반드시 존재한다 — 문제는 그게 화면 200곳에 흩어지느냐, 정의 파일 1곳에 모이느냐다. 화면에는 「무엇을 그릴지」만 남기고 「기관마다 무엇이 다른지」는 전부 정의로 밀어낸다.

12-1라벨 — 조회 함수 하나

가장 쉽고 가장 많이 쓰인다. 현재 200파일에 흩어진 「내담자」 문자열의 대체재다. 분기 없이 조회만 한다.

// ✗ 이렇게 하지 않는다
{#if orgType === 'school'}학생{:else if orgType === 'military'}장병{:else}내담자{/if}

// ✓ 조회 한 번 — 기관이 몇 개든 코드는 그대로
{t('client')}                  // "학생" | "장병" | "환자" | "내담자"
{t('client.code_label')}       // "학번" | "군번" | "등록번호" | "코드"
{t('status.active')}           // "재학" | "복무중" | "외래" | "활동중"

// 구현 — 스토어에서 정의를 읽어 경로로 꺼낸다
export function t(path: string, fallback?: string): string {
  return get(ontology)?.labels?.[path] ?? fallback ?? path
}

// 화면은 org_type을 모른다. 정의가 바뀌면 문자열이 따라 바뀔 뿐.
왜 i18n 라이브러리가 아닌가 형태는 i18n과 같지만 축이 다르다. i18n은 같은 사용자에게 다른 언어를, 온톨로지는 다른 기관에게 다른 어휘를 준다. 나중에 진짜 다국어가 필요해지면 두 축이 곱해지므로(ko × school), 지금 i18n 라이브러리를 끌어와 기관 축에 써버리면 언어 축을 넣을 자리가 없어진다. 별도 레이어로 두는 게 맞다.

12-2반복 영역 — 스키마가 컴포넌트를 고른다

§9~11에서 확인된 「N개 반복」 영역이 여기 해당한다 — attributes 블록, 목록 컬럼, 통계 타일, 등록폼 필드. 이 영역들은 스키마를 순회해 렌더하면 기관 추가 시 코드가 그대로다.

핵심은 타입 → 컴포넌트 레지스트리다. 분기가 if가 아니라 맵 조회가 된다.

attribute block — 레지스트리 패턴 기관 추가 시 무수정 
// 레지스트리 — 타입 하나당 컴포넌트 하나. org_type은 등장하지 않는다.
const FIELD_COMPONENTS = {
  string: TextField,
  int:    NumberField,
  date:   DateField,
  enum:   SelectField,
  ref:    RefField,      // ref: "member" → 구성원 검색 드롭다운
}

// 렌더 — 스키마를 순회할 뿐
{#each ont.entities.client.attributes as attr (attr.key)}
  {@const Field = FIELD_COMPONENTS[attr.type]}
  <Field
    label={attr.label}
    required={attr.required}
    bind:value={form.attributes[attr.key]}
    {...attr}
  />
{/each}

// 기관을 5번째로 추가해도 이 코드는 열지 않는다.
// 새 타입(예: "phone")이 생길 때만 레지스트리에 한 줄 추가.

12-3구조적 분기 — capability 플래그

§9~11에서 「사라지는 슬롯」으로 나온 것들이다. 이건 반복이 아니라 있냐 없냐라서 순회로 안 된다. 하지만 기관 이름으로 묻지 않는 것이 핵심이다 — 능력으로 묻는다.

capability flag — 기관명으로 묻지 않기 불리언 1개 = 슬롯 N개 
// ✗ 기관을 물으면 기관이 늘 때마다 조건이 늘어난다
{#if orgType === 'school' || orgType === 'clinic'}
  <GuardianBlock />
{/if}

// ✓ 능력을 묻는다 — 기관이 몇 개든 조건은 하나
{#if ont.relations.guardian.enabled}
  <GuardianBlock />
  <AppLinkBlock />      // §10에서 확인: 같은 축에 매달린 두 슬롯
{/if}

// §11의 유상 전제도 같은 방식
{#if ont.capabilities.billing}
  <BillingMenu />
{/if}
<PriceField required={ont.capabilities.billing} />   // 무상 기관은 필수 해제

// 플래그 목록 — 화면이 아니라 정의가 소유
capabilities: {
  billing:  true,   // 과금·청구·금액 필수  (학교·군 = false)
  guardian: true,   // 보호자 관계·앱연결   (군 = false)
  voucher:  true,   // 바우처 관리         (심리센터만 true)
}

// 플래그 하나가 슬롯 여러 개를 동시에 지운다:
//   guardian=false → 보호자 블록 + 앱연결 블록
//   voucher=false  → 목록 바우처 컬럼 + 상세 바우처 블록

// 실제로 쓰는 것만 선언한다. 대상자 마스킹(anonymous)은
// EAP 전용이라 1차 범위 밖 — 착수 시 플래그를 추가한다 (§13).
왜 이게 결정적인가 기관명으로 물으면 조건이 기관 수만큼 늘고, 기관을 추가할 때 그 조건을 가진 모든 파일을 찾아 열어야 한다. 능력으로 물으면 조건은 영원히 하나이고, 기관 추가는 정의에 true/false를 쓰는 일이 된다. §10에서 「가족관계와 앱연결이 같은 축에 매달려 있었다」고 한 것이 바로 이 이야기다 — 플래그 하나가 슬롯 여러 개를 동시에 지운다.

12-4슬롯 내용 지정 — 이름으로 가리키기

§9-1의 「군은 생년월일 줄이 계급·전역일로 바뀐다」, §10-1의 「병원은 연락 2행이 진료과·면허로 교체된다」가 여기다. 슬롯은 그대로 있고 내용만 다르다. 정의가 어떤 필드를 넣을지만 이름으로 가리킨다.

slot binding — 필드 이름으로 지정 슬롯 고정 · 내용 가변 
// 정의
card_slots: {
  subline:  ["birth_date", "gender"],           // 군: ["rank", "discharge_date"]
  contact:  ["phone", "email"],                 // 병원: ["department", "license_no"]
}

// 화면 — 슬롯은 고정, 내용은 이름으로 해소
<SubLine fields={ont.card_slots.subline} data={client} />
<ContactLines fields={ont.card_slots.contact} data={client} />

// SubLine 내부 — 값 해소기 하나로 코어·확장 모두 처리
function resolve(data, key) {
  return key in data ? data[key] : data.attributes?.[key]
}

// 코어 필드(birth_date)든 확장 속성(rank)이든 같은 방식으로 꺼낸다.
// → 화면은 그 필드가 컬럼인지 JSONB인지 알 필요가 없다.
이 해소기가 §6 스펙을 지탱한다 resolve() 한 줄이 「코어는 컬럼, 확장은 JSONB」라는 저장 구조를 화면에서 완전히 감춘다. §6에서 「기관 고유키를 컬럼으로 올리지 않고 attributes에 둔다」고 결정할 수 있었던 근거가 이거다 — 화면이 차이를 모르므로 나중에 성능 때문에 특정 키를 컬럼으로 승격해도(§7 Q5) 화면 코드는 그대로다.

12-6어디까지 스키마로 밀 것인가

「궁극적으로 유연하게」가 목표라면 슬롯 순서까지 정의가 소유하는 게 종착점이다 (detail_sections: [{type, ...}]를 순회). 다만 §9~11 실측이 말해주는 게 있다 — 슬롯 구조 자체는 네 기관에서 잘 버텼다. 사라지는 슬롯은 capability로 처리되고, 순서가 기관마다 달라야 할 근거는 아직 나오지 않았다.

그래서 전면 스키마화를 목표로 두되, 근거가 나온 순서로 간다. §8의 「될 것 같다로 구현하지 마라」가 여기에도 적용된다 — 처음부터 전 화면을 섹션 렌더러로 만들면, 검증 안 된 유연성에 디버깅 난이도와 타입 안전성을 미리 지불하는 셈이다.

전환 순서 — 근거가 확보된 것부터

기업 EAP — 1차 제외 결정

왜 뺐는지, 뺀 결과로 무엇이 쉬워졌는지, 재개하려면 무엇이 선행돼야 하는지. 분석은 지우지 않고 보존한다 — 재개 시 실측부터 다시 하지 않기 위해.

§9~11에서 EAP는 세 번 독립적으로 걸렸다. 한 번이면 예외 처리로 넘어갈 수 있지만, 서로 다른 층위에서 세 번 걸린다는 건 신호다 — EAP는 「표현이 다른 기관」이 아니라 「구조가 다른 제품」에 가깝다.

13-1제외 근거 3개

EAP가 걸린 세 지점 — 각각 다른 층위
# 근거 층위 출처
1 익명 정책이 §2 불변 규칙을 깬다. 온톨로지가 마스킹을 선언해도 강제는 API에서 일어나야 안전하다. 그러면 「어떤 기관에서도 응답 필드는 동일」이라는 전제에 예외가 생긴다. 아키텍처 규칙 §7 Q3
2 상세 슬롯 10개 중 5개가 죽는다. 이름·생년월일·기본정보 3행이 마스킹되고 가족관계·앱연결이 사라진다. 나머지 셋은 「슬롯 채우기」인데 EAP만 「슬롯 비우기」다. 화면 구조 §9-2
3 기관↔고객사 2단 구조가 모델에 없다. 고객사를 Center로 만들면 상담사가 여러 Center에 속해야 하고, attributes에 넣으면 고객사별 쿼터·통계가 안 나온다. 데이터 모델 §11-3
세 근거가 말하는 것 근거 1·2는 익명에서 나오고, 3은 2단 구조에서 나온다. 즉 EAP의 문제는 둘로 압축된다 — 그리고 둘 다 온톨로지 레이어로 풀리지 않는다. 익명은 권한·API 문제고, 2단 구조는 모델 문제다. 표현 레이어를 아무리 잘 만들어도 이 둘은 그대로 남는다. 순서를 바꿔 넣을 이유가 없다는 것이 제외의 본질이다.

13-3재개 조건 — 무엇이 선행돼야 하나

EAP를 다시 꺼낼 때 이 문서의 §9~11 분석은 그대로 유효하다 (EAP 열·목업을 남겨둔 이유). 새로 해야 할 것은 아래 셋이며, 순서가 있다 — 1번이 없으면 2·3번을 설계할 수 없다.

  1. 고객사 계층을 어떻게 모델링할 것인가 가장 먼저다. 세 안이 있다 — ⓐ 고객사를 Center로(상담사가 다중 Center 소속), ⓑ Center 하위에 client_organization 테이블 신설, ⓒ Center에 parent_center_id로 자기참조 계층. ⓑ가 유력하지만 바우처·통계·권한이 전부 이 결정에 딸려 온다. 이건 표현 레이어가 아니라 도메인 설계 과제다.
  2. 익명을 권한 모델에 어떻게 넣을 것인가 「누가 실명을 볼 수 있는가」가 본질이다. 담당 상담사는 보고, 고객사 담당자는 통계만 보고, 관리자는? — 현재 access_level(all/own) 2단으로는 부족하다. 기존 시크릿 모드(화면 마스킹)와는 다른 축이다 — 시크릿 모드는 보는 사람이 끄고 켜는 것이고 익명은 서버가 강제하는 것.
  3. §2 불변 규칙에 예외를 인정할 것인가 1·2번이 정해지면 답이 따라온다. 익명이 권한으로 처리되면 「필드는 늘 오되 값이 마스킹된 형태」로 규칙을 지킬 수 있고, 필드 자체를 빼야 한다면 예외가 필요하다. 전자가 규칙을 지키는 길이므로 그쪽을 먼저 검토한다.
재개 시 주의 위 셋은 전부 온톨로지 레이어 밖의 과제다. 즉 EAP 재개는 「온톨로지에 org_type 하나 추가」가 아니라 별도 설계 사이클이다. 1차 3기관이 안정화된 뒤 착수 여부를 다시 판단하는 것이 맞고, 그때 이 문서의 §9~11 EAP 열이 출발점이 된다.

14-2확장된 정의 — 엔티티 블록 + capability 파생 메뉴

14-3메뉴 파생 — capability → menuId

canShowSidebarMenu 확장 — 4번째 축 추가 호출부 5곳 무수정 
// 기능이 꺼지면 사라지는 메뉴 — 정의가 아니라 코드가 소유(축 매핑이므로)
const MENU_REQUIRED_CAPABILITY: Partial<Record<SidebarMenuId, string>> = {
  voucher:       'voucher',
  voucherManage: 'voucher',
  billing:       'billing',
  assessment:    'assessment',
  assessmentManage: 'assessment',
}

// 기존 함수에 4번째 파라미터만 추가 — 판정 순서는 블랙리스트 다음
export function canShowSidebarMenu(
  menuId, permissions, role,
  capabilities?: Record<string, boolean>
): boolean {
  if (role && ROLE_EXCLUDED_MENUS[role]?.includes(menuId)) return false

  const cap = MENU_REQUIRED_CAPABILITY[menuId]
  if (cap && capabilities && capabilities[cap] === false) return false

  const required = SIDEBAR_MENU_PERMISSIONS[menuId]
  if (!required?.length) return true
  if (permissions.includes('*')) return true
  return required.some((p) => permissions.includes(p))
}

// 호출부는 인자 하나만 더 넘긴다 (5곳):
//   UnifiedSidebar :701 메뉴 · :713 서브메뉴 · :740 하단
//   MenuAccessGuard :25  ← 이 한 곳이 URL 직접 접근까지 막는다
//   center/+layout :33   문서 양식 탭

데이터 소스는 새 스토어를 만들지 않고 permissionStore.context에 얹는다. 별도 스토어를 두면 로딩 타이밍이 어긋나 메뉴가 깜빡였다 사라지는 기존 문제(permissionReady 게이트가 막고 있는 것)를 다시 만들게 된다.

14-4실측에서 나온 함정 3개

함정내용대응
URL 미차단 라우트 가드가 4곳에만 있다 — center·billing·member·settings/vouchers. /vouchers·/assessment·/counseling엔 없다. 메뉴를 지워도 주소창에 치면 들어가진다. (protected)/vouchers/+layout.svelte 등 가드 레이아웃 신설 필요
대시보드 별도축 「처리할 일」이 권한코드조차 안 보고 accessLevel === 'all' 하나로만 제어된다. 청구 메뉴를 꺼도 「미청구 N건」이 그대로 뜬다. 카테고리 키도 하드코딩 리터럴. §11-2에서 이미 제기 — dashboard_tasks를 capability로 필터
자동 평탄화 서브메뉴가 1개 이하로 줄면 부모가 소리 없이 단일 링크로 바뀐다 (UnifiedSidebar:718-725). 바우처는 자식이 2개라 voucherManage만 꺼도 형태가 변한다. 의도된 동작인지 확인 — 대부분의 경우 자연스러움
가장 위험한 것 URL 미차단이다. 「학교에서는 바우처를 안 쓴다」고 메뉴를 지웠는데 실제로는 접근 가능하면, 그건 숨긴 것이지 끈 것이 아니다. 데이터가 없어 빈 화면이 뜨거나, 더 나쁘게는 다른 기관 개념의 UI가 그대로 노출된다. capability로 메뉴를 끄는 작업은 가드 레이아웃 신설과 반드시 같이 가야 한다.

14-5작업 단위

전역 확장 — 독립적으로 진행 가능한 단위
단위내용선행
A. Client 현재 §8 1~3단계 그대로 — 목록 → attributes → 상세 —
B. 메뉴 게이팅 구현됨 canShowSidebarMenu 4번째 축 + centerStore.orgCapabilities + 가드 레이아웃 3개 신설. §14-6 참조 완료 (2026-08-12)
C. Member entities.member 블록. §10에서 확인했듯 가장 쉽다 — infoRows 배열이 이미 열려 있고 역할은 서버 소유 A로 패턴 검증 후
D. Center entities.center 블록 — info_rows 가변화(병원 이중 식별번호) + 통계 타일 라벨 A로 패턴 검증 후
E. 대시보드 「처리할 일」 capability 필터. 별도 축을 쓰고 있어 손이 제일 많이 간다 B 이후
순서에 대한 판단 B(메뉴 게이팅)를 A(Client)보다 먼저 해도 된다 — 서로 독립이고, B는 「학교엔 바우처·청구가 없다」는 가장 눈에 띄는 차이를 만든다. 기관 확장을 이해관계자에게 보여줘야 한다면 B가 효과가 크다. 다만 B는 반드시 가드 레이아웃 신설과 한 묶음이어야 한다(§14-4). C·D는 A로 패턴이 검증된 뒤에 하는 게 맞다 — 같은 형식의 반복이라 A에서 형식이 틀리면 세 배로 고쳐야 한다.

14-6B 구현 결과 (2026-08-12)

메뉴 게이팅을 실제로 배선했다. 서버에 org_type이 아직 없으므로 기존 센터는 전부 기본값(심리센터)을 받아 동작 변화가 없다 — 서버가 값을 내려주기 시작하면 그때부터 켜진다.
