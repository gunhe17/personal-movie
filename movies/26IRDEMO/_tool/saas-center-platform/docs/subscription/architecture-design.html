구독(Subscription) → 크레딧(Credit) → AI Gateway 연결 구조  |  2026-04-23  |  검토용 초안

1 현재 구조 vs 목표 구조

AS-IS (현재)

관리자가 수동으로 → POST /credit → plan_type="pro" (하드코딩) → CreditBalance 생성
문제: plan_type의 출처가 없음. 센터가 실제로 어떤 플랜을 구독 중인지 관리하는 주체가 없고, 관리자가 API를 직접 호출해야만 크레딧이 생성됨.

TO-BE (목표)

Subscription → plan 변경 이벤트 → CreditBalance 자동 생성/갱신
Subscription → JWT에 plan 포함 → @require_plan 데코레이터 → 기능 접근 제어
Subscription → quota 관리 → 내담자/상담사 수 제한

5 핵심 플로우

5-1. 센터 생성 → Free 구독 자동 생성

POST /centers → CreateCenterHandler → Center 생성
↓ 같은 트랜잭션
CreateCenterHandler → SubscriptionFacade.create_free() → Subscription(plan=free)
포인트: Free 플랜은 AI 크레딧 0이므로 CreditBalance를 생성하지 않음. 크레딧 레코드 없음 = 무제한이 아니라, AI 기능 자체가 플랜 레벨에서 차단됨.

5-2. 플랜 업그레이드 → 크레딧 자동 연동

POST /subscription/upgrade → UpgradeHandler
↓
SubscriptionFacade.upgrade() → Subscription.plan = "pro"
↓ 같은 UoW 내
SubscriptionFacade → CreditFacade.init_credit(plan_type, period) → CreditBalance 생성
↓
JWT 재발급 (plan 필드 포함)

5-3. AI 호출 시 이중 게이팅

AI 기능 요청 → @require_plan("pro") → CheckQuotaService → AIGateway
Layer 1 — 플랜 레벨 체크 (JWT의 plan 필드) → 402 Payment Required
Layer 2 — 크레딧 잔량 체크 (CreditBalance) → QuotaExceededException

5-4. Lazy Reset과 구독 기간 연동

현재 (독립) 목표 (연동) CreditBalance.period_end 만료 Subscription.current_period_end 만료 │ │ ▼ ▼ LazyResetCreditService LazyResetCreditService (이전과 동일 길이로 갱신) (Subscription에서 period 조회 후 갱신) │ │ ▼ ▼ 새 CreditBalance 생성 새 CreditBalance 생성 (plan_type 유지) (Subscription.plan 반영)

7 기존 모듈과의 의존성

연결 지점 방향 방법 상태
Center 생성 → Subscription 생성 Center → Subscription Center Handler에서 SubscriptionFacade.create_free() 호출 구현 필요
플랜 업그레이드 → Credit 초기화 Subscription → Credit SubscriptionFacade에서 CreditFacade.init_credit() 호출 구현 필요
JWT에 plan 필드 포함 Subscription → Auth 토큰 생성 시 SubscriptionFacade.get_plan() 조회 구현 필요
AI 기능 접근 제어 Auth → Domain @require_plan("starter") 데코레이터 구현 필요
내담자/상담사 수 제한 Subscription → Client/Member 생성 전 SubscriptionFacade.check_quota() 호출 구현 필요
Lazy Reset 시 구독 참조 Credit → Subscription LazyResetCreditService가 구독 기간/플랜 조회 수정 필요
크레딧 한도 참조 Credit → Subscription PLAN_CREDIT_LIMITS를 구독 모듈 PlanConfig에서 조회 수정 필요

9 논의 필요 사항

CRITICAL D-1. Free 플랜에서 AI 차단 방식

현재 크레딧 레코드가 없으면 무제한 허용입니다 (CheckQuotaService: if row is None: return). 구독 도입 후 Free 플랜은 AI를 완전 차단해야 합니다.

  • 방안 A: @require_plan("starter") 데코레이터로 라우터 레벨에서 차단 (JWT 기반)
  • 방안 B: CheckQuotaService에서 크레딧 레코드 없음 = 차단으로 변경
  • 권장: 둘 다 적용 (이중 게이팅). A가 1차 방어, B가 2차 방어
CRITICAL D-2. 기존 센터 데이터 마이그레이션

이미 운영 중인 센터들에 대한 처리:

  • 기존 센터에 Subscription 레코드가 없음 → 어떤 플랜으로 할당할 것인가?
  • 방안 A: 모두 Pro로 마이그레이션 (기존 기능 유지, 추후 정리)
  • 방안 B: 모두 Free로 마이그레이션 (기존 AI 기능 즉시 차단 위험)
  • 방안 C: CreditBalance가 있는 센터는 해당 plan_type으로, 없는 센터는 Free로
  • 권장: C — 기존 크레딧 데이터를 존중하면서 자연스러운 전환
CRITICAL D-3. PLAN_CREDIT_LIMITS 소유권 이동

현재 llm/credit/plan_config.py에 있는 PLAN_CREDIT_LIMITS를 어디로 옮길 것인가:

  • 방안 A: subscription/plan_config.py로 이동 — 구독 모듈이 플랜의 모든 것을 소유
  • 방안 B: 크레딧 모듈에 유지하되, 구독 모듈에서 참조 — 결합도 최소화
  • 권장: A — PlanConfig에 credit_limit, client_limit, member_limit, features를 한 곳에서 관리
IMPORTANT D-4. Subscription → Credit 연동 방식

구독 플랜 변경 시 크레딧을 어떻게 연동할 것인가:

  • 방안 A (동기): SubscriptionFacade.upgrade()에서 CreditFacade.init_credit()을 같은 UoW에서 호출
  • 방안 B (비동기): 플랜 변경 이벤트 발행 → Credit 모듈이 구독해서 처리
  • 권장: Phase 1은 A (단순), Phase 2에서 이벤트 기반으로 전환 가능

주의: Facade 협력 규칙상 SubscriptionFacade에서 CreditFacade를 직접 호출은 금지. Handler에서 두 Facade를 순차 호출하거나, 공통 Service를 사용해야 함.

IMPORTANT D-5. JWT plan 필드 — 실시간성 vs 성능

JWT에 plan 정보를 포함하면 토큰 만료까지 변경이 반영되지 않음:

  • 방안 A: 짧은 토큰 만료 (15분) + 업그레이드 시 즉시 토큰 재발급
  • 방안 B: DB 조회 캐싱 (60초) — 크리티컬 기능만 DB 체크
  • 권장: Phase 1은 A — 이미 token refresh 인프라가 있으므로 활용
IMPORTANT D-6. 업그레이드 시 크레딧 잔량 처리

Starter(300) → Pro(1500) 업그레이드 시 이미 사용한 크레딧은?

  • 방안 A: 리셋 — 새 플랜 기준 1500 크레딧으로 초기화 (단순, 사용자 유리)
  • 방안 B: 이월 — 사용량 유지, 한도만 1500으로 증가 (정확하지만 복잡)
  • 방안 C: 비례 배분 — 남은 기간 비율로 새 한도 계산 (가장 공정)
  • 권장: Phase 1은 A (사용자 경험 우선, 구현 단순)
NORMAL D-7. Phase 1에서 결제 없이 업그레이드하는 방법

PG 연동 없이 Phase 1을 진행하려면:

  • 방안 A: 관리자(Admin) 전용 API — 관리자가 수동으로 플랜 변경
  • 방안 B: 플랫폼 관리자(SuperAdmin) 전용 — 내부 운영팀이 변경
  • 방안 C: 둘 다 — Admin은 요청, SuperAdmin이 승인
  • 권장: B — Phase 1은 내부 운영으로 관리, Phase 2에서 셀프서비스 추가
NORMAL D-8. 프론트엔드 구독 UI 범위 (Phase 1)

Phase 1에서 프론트엔드에 어디까지 노출할 것인가:

  • 현재 플랜 표시 (사이드바/설정 페이지)
  • 플랜별 기능 차단 UI (402 → "Pro 플랜으로 업그레이드하세요" 안내)
  • 플랜 비교 페이지 (가격표)
  • 권장: 최소 — 현재 플랜 표시 + 차단 안내만. 결제 UI는 Phase 2
검토 후 각 논의 항목(D-1 ~ D-8)에 대한 결정을 알려주시면 구현을 시작하겠습니다.
