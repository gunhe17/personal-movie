온톨로지 두 트랙 정렬

main에 머지된 백엔드 실행 레이어(app/ontology, PR #194~196, 2026-08-13~14)와 ontology-v1 브랜치의 정의 레이어(ontology/)를 비교하고, 협업 경계를 합의하기 위한 문서.

초안 — 정렬 회의 지참용 (2026-08-14 · 2026-08-18 갱신: 드리프트 3 해소, 4 표기 규약 선언)
1

한눈에 — 경쟁이 아니라 층이 다르다

같은 "온톨로지"라는 이름을 쓰지만 만드는 물건이 다르다. 하나는 사전(무엇이 존재하고 뭐라고 부르나), 하나는 교환기(그 다름을 API 호출 시점에 어느 구현으로 연결하나)다. 교환기는 사전이 정의한 축을 소비하는 쪽이지, 사전을 대체하지 않는다.

우리 — ontology-v1 브랜치 정의 레이어 (사전 · 설계도)

사람·기관 도메인의 개념 정본. "어떤 개념이 존재하고, 기관마다 뭐라고 부르고, 어느 테이블에 사상되는가."

  • ontology/catalog.json — 개념 7종(person·subject·staff·guardianRel·org·orgUnit·extInst) + 관계 5
  • ontology/bindings.json — 개념↔테이블 실측 사상 (bound/partial/missing)
  • ontology/profiles/*.json — 기관 유형별 어휘·존재·가변 (center·school·hospital·military·shelter)
  • 공리 A1~A7 · 결정 D1~D8 (결정장부)
  • tools/ontology-explorer — 모델 그래프·감사 + API 콘솔 (:3503)
  • apps/web .. terms.ts — 화면 어휘가 프로필을 소비 (리터럴 금지)
백엔드 — main (gunhe17) 실행 레이어 (교환기 · API)

기관 무관 조회 표면. "호출자는 기관 종류를 모른다 — 학생 조회·병사 조회가 따로 생기지 않게."

  • GET /api/v1/ontology/centers/{id}/clients · /sessions
  • 한 파일 = 한 연산: .py 시그니처 + .yaml 사상 — 기관 유형(center_type 축)별로 어느 application handler를 부를지 선언
  • 로드 검사 4종 — 축·import·slots·서버 인자 어긋나면 부팅에서 죽음 (조용한 드리프트 차단)
  • dev 전용 /api-map 계약 — 모델 탐색기 콘솔이 이걸 읽어 개념·파라미터를 자동 열거 (내장 페이지 /ontology-explorer는 리다이렉트만 남음, 아래 드리프트 3)
  • 계약 .claude/rules/api/ontology.md · 판정 app/ontology/DECISIONS.md
  • 미구현 기관(school·military·hospital) 좌표는 커밋 전 제거 — "기관이 붙을 때 yaml 한 줄로 되살린다"
# 백엔드 yaml 실물 (handler/client/query_client.yaml)
name: clients.query
codomains:
  center_type:            # ← 축. 이 값 체계가 우리 profiles/index.json과 만나야 하는 지점
    counseling:           # ← 좌표. 현재 상담센터 하나뿐
      operation: app.application.handlers.client.query_client.query_client_handler
      slots: [center_id, owner_scope, name, code, ...]   # 그 기관이 받는 조회 축 전부
2

이미 수렴한 것 — 독립적으로 같은 결론

서로 안 보고 만들었는데 같은 곳에 도달한 지점들. 협업의 토대이자, "두 트랙이 같은 모델을 보고 있다"는 증거로 회의에서 먼저 짚을 것.

수렴 1
새 축은 둘뿐 — 소속 조직 + 상시 담당자

백엔드 DECISIONS.md "D4 준비"가 학교(반)·군(부대)·병원(병동)을 훑고 내린 결론: "진짜 새것은 소속 조직과 상시 담당자 둘뿐, 나머지는 기존 아키타입에 떨어진다." 우리 catalog의 orgUnit(binding: missing) + D7(조직 위계 모양은 프로필이 선언)과 정확히 같은 판정.

수렴 2
개념은 기관 무관 명사

백엔드 D1: "concept은 기관 무관 복수 명사 — clients이지 students가 아니다." 우리 A3(어휘 변환은 프로필 소유)·terms.ts 리터럴 금지와 같은 원칙의 API판.

수렴 3
학번·군번·환자번호 = clients.code 재사용

백엔드: "셋 다 기관 내 유일 식별 코드로 같고, 갈리는 건 표시명·형식 검증뿐. 새 컬럼을 파면 같은 개념이 넷이 된다." 우리 D1(대상자 고유함 = 기관 내 유일까지만)·A1과 일치.

수렴 4
기관별 분화는 선언으로, 코드 분기 금지

백엔드 D6: if center_type == ... 분기 폐기 → yaml 선언. 우리 A5·D6·D7(프로필 = 주입되는 선언)과 같은 철학 — 기관이 늘 때 코드가 아니라 선언 파일 하나가 는다.

3

어긋나기 시작한 것 — 정렬 필요 4건

지금은 전부 싸게 고칠 수 있다. 방치하면 각자 정본이 둘이 된다.

드리프트 1
기관 유형 축 값 — counseling vs center, 그리고 shelter

백엔드 yaml 좌표는 counseling, 우리 프로필 id는 center — 같은 것("상담센터")의 이름이 벌써 둘이다. 우리에게만 있는 shelter(쉼터 선례)도 백엔드 값집합 (CENTER_TYPES = counseling·school·military·hospital)엔 없다. 실측(코드 확인): 축 좌표는 centers.center_type 컬럼의 런타임 값인데 이 컬럼은 아직 DB에 없다 — getattr(..., None) → 기본 counseling, 값집합은 handler 안 튜플 하나뿐. 즉 데이터 마이그레이션 대상이 0건인 지금이 정렬 비용이 사실상 0인 시점이고, 우리 D6("테넌트 유형 필드 = 프로필 포인터")대로 컬럼이 태어날 때부터 ontology/profiles/index.json의 id를 값으로 갖게 합의하는 게 제안.

드리프트 2
개념 명명 — 테이블 명사(clients) vs 개념 명사(subject)

백엔드 URL·폴더는 clients·sessions(테이블에서 온 이름), 우리 catalog는 subject·person·staff(기관 중립 개념). "client"는 이미 상담센터 어휘가 밴 이름이라 백엔드 자신의 D1 원칙("students가 아니다")과도 긴장이 있다. URL을 지금 바꾸자는 게 아니라, catalog 개념 id ↔ API concept 명사의 대응표를 정본에 한 줄로 등재하는 것부터.

해소 3
탐색기 이름 충돌 — 해소됨 (2026-08-18)

호칭을 나누는 대신 장기안대로 한 셸에 합쳤다. 탐색기는 tools/ontology-explorer 하나뿐이고, 서버가 뿌리던 HTML 콘솔은 이 앱의 API 콘솔로 흡수됐다 — 개념·파라미터는 /api-map에서 자동으로 열거하고, 온톨로지 응답 봉투(rows)를 그대로 그래프로 그린다. localhost:3502/ontology-explorer는 :3503으로 리다이렉트되므로 옛 주소도 살아 있다. 회의 안건에서 제외 — F3은 완료.

드리프트 4
결정 번호 충돌 — D6이 두 개다

백엔드 app/ontology/DECISIONS.md의 D1~D7과 우리 결정장부 D1~D8은 번호 체계가 겹친다 (예: 백엔드 D6 = yaml 사상 확정, 우리 D6 = 테넌트 유형 필드). 회의·문서에서 "D6"이 모호해진다.

표기 규약은 선언해 뒀다 (2026-08-18) — 문서·회의에서는 MD-(모델 정의) / AD-(API 실행) 접두로 부른다. 양쪽 소유 문서(ontology/decisions.json · app/ontology/DECISIONS.md)가 자기 접두를 머리에 적고 서로를 링크한다. 데이터 키(A1~D8)는 그대로 뒀다 — catalog·초안·회의록 4종이 이미 이 키를 쓰고 있어 리넘버는 지난 회의록까지 건드린다. 남은 결정: 키까지 리넘버할 것인가 (기본안: 하지 않는다).

제안 — 대원칙 하나, 후속은 기술 작업

회의에서 합의할 것은 이 한 문장뿐이다. 이게 서면 §3의 4건은 전부 소유권이 정해진 기술 후속이 된다.

대원칙 (합의 대상)

루트 ontology/가 개념·축·어휘의 정의 정본이고, apps/api/app/ontology/는 그것을 소비하는 실행 표면이다. 개념·기관 유형·어휘를 새로 만들거나 바꾸는 결정은 정의 정본에서 하고, 실행 표면은 따라간다.

#후속 작업내용주 담당
F1축 값 통일yaml 좌표·AXES가 profiles/index.json의 id를 쓴다 (counseling→center 또는 역방향 — 방향만 회의에서). shelter 좌표 등재 시점도 함께.백엔드 + 우리
F2개념 대응표catalog 개념 id ↔ API concept 명사 매핑을 ontology/catalog.json에 등재. 신규 concept은 여기부터.우리
F3탐색기 역할 분리완료 (2026-08-18) — 호칭 분리 대신 한 셸로 통합. 모델 탐색기가 /api-map을 읽어 온톨로지 표면을 호출하고 응답을 그래프로 그린다(장기안 선반영).—
F4결정 번호 접두표기 규약 선언 완료 (2026-08-18) — MD-/AD- 접두 + 양쪽 문서 상호 링크. 데이터 키 리넘버 여부만 회의 판단.각자
F5검증 연결 (장기)yaml의 축·좌표를 catalog/bindings와 대조하는 감사(로드 검사 5번째 축) — 정본이 기계적으로 하나가 되는 종착점.백엔드

F1의 방향 논거: 프로필 id는 이미 web(terms.ts)·explorer·문서가 소비 중이고, 백엔드 쪽은 컬럼 미생성 + 좌표 1개 (counseling) + 값집합 튜플 1곳이 전부라 지금이 가장 싼 시점. 단 "counseling이 용도(코어 루프, A6)로는 더 정확하다"는 반론이 가능 — 회의에서 결정. 우리 D6이 이미 "테넌트 유형 필드 = 프로필 포인터"를 확정해 둔 것이 이 합의의 근거 조항.
