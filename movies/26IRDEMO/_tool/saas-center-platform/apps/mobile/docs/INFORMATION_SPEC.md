## 1. 용어 정의

| 용어 | 정의 |
|------|------|
| 세션 (상담) | 상담 자체. 여러 회기로 구성되는 단위. 예: "홍길동의 놀이치료 상담" |
| 회기 | 세션 내의 개별 만남. 날짜로 식별. |
| 일정 | 날짜 기준으로 회기를 보여주는 뷰 |
| 프로그램 | 상담 종류. `[치료프로그램명]-[개인/그룹]` 형식. 예: 놀이치료-개인, 미술치료-그룹 |

### ❌ 사용하지 않는 것
- **회기 번호 / N회차 표기** → 날짜로 대체
  - **예외 (2026-07-21 재판정)**: 회기 단위 화면(일정 타임라인 카드·회기 상세)의 케이스 캡션 `{case_code}의 N회기`는 허용 — 같은 날 복수 회기·케이스 내 진행 위치 식별 보조(날짜는 별도 표시 전제). 목록·요약 카드의 회기 번호 표기 금지는 유지.

## 2. 화면 구조 및 연결 관계

```
앱 메뉴 (하단 탭)
├── 홈
├── 일정
│   ├── 상담 일정 카드
│   │   └── 일정 상세 (회기) ──→ 상담 상세 (세션)
│   │       └── 내담자 카드 탭 ──→ 상담일지 바텀시트
│   └── 검사 일정 카드
│       └── 검사 일정 상세 ──→ 검사 상세 (세션)
├── 내담자
│   └── 내담자 상세
├── 필드노트
└── 내정보
    ├── 상담 현황
    │   └── 상담 리스트 ──→ 상담 상세 (세션)
    ├── 검사 현황
    │   └── 검사 리스트 ──→ 검사 상세 (세션)
    ├── 청구 현황
    │   └── 청구 리스트 ──→ 청구 상세 바텀시트
    └── 상담일지 ⚠️
        └── 상담일지 리스트 (작성/미작성/전체) ──→ 상담일지 바텀시트

상담 상세 (세션)
├── 내담자 클릭 ──→ 내담자 상세
└── 회기 클릭 ──→ 회기 바텀시트
    └── 내담자 카드 탭 ──→ 상담일지 바텀시트 (바텀시트 내 페이지 이동)

검사 상세 (세션)
├── 내담자 클릭 ──→ 내담자 상세
└── 검사 항목 결과보기 ──→ 결과 바텀시트
```

### 3-1. 일정 (회기 기반)

#### 일정 카드 (목록 뷰)

> 상담 / 검사 카드 공통 포맷. 날짜/시간은 현재 타임라인 좌측에 표시되나, 레이아웃에 따라 카드 내부로 이동 가능.

| 항목 | 상태 | 비고 |
|------|------|------|
| 내담자 이름 | ✅ | |
| 날짜 / 시간 | ✅ | 현재 타임라인 좌측 표시 |
| 장소 | ✅ | |
| 프로그램 | ✅ | |
| 일정 상태 | ✅ | 예정 / 완료 / 취소 / 노쇼 (4가지) |

#### 일정 상태와 내담자 출결 상태의 관계

- **일정 상태** (4가지): 예정 / 완료 / 취소 / 노쇼
- **내담자 출결 상태** (3가지, §3-2): 참석 / 불참 / 노쇼
- 두 레이어는 **derived 관계** — 일정 노쇼는 "모든 참여 내담자가 노쇼"인 경우 자동 처리. 일부만 노쇼면 일정은 완료(회기는 일어남), 그 사람만 출결 노쇼로 기록.
- 의미: 일정 노쇼 = 사실상 회기가 일어나지 않음. 일정 완료 = 회기는 일어남(일부 노쇼 포함 가능).

**케이스 예시**
- 1:1 케이스에서 내담자가 안 옴 → 1명=모두 → **일정 노쇼**
- 그룹 3명 중 1명만 노쇼 → 회기는 진행됨 → **일정 완료**, 내담자C 출결=노쇼
- 그룹 3명 모두 노쇼 → 사실상 회기 X → **일정 노쇼**, 전원 출결=노쇼
- 사전 취소 (회기 자체 무효) → **일정 취소**, 출결 영역 숨김

#### 일정 상태 변경 시 동작

| 상태 | 출결 자동 처리 | 사유 입력 |
|------|---------------|-----------|
| 예정 | (기본값) | — |
| 완료 | 전원 참석 default (이후 개별 출결 수정 가능) | — |
| 노쇼 | 전원 노쇼 default (derive: 모든 참여자 노쇼이면 자동) | — ("이유 없이 안 온 것"이 정의) |
| 취소 | **출결 영역 숨김** (일정 자체가 무효) | enum + 비고 (필수) |

**일정 취소 사유 enum**: `내담자 사정` / `상담사 사정` / `시설·환경` / `기타`

#### 일정 상세 뷰

**상단 카드**

| 항목 | 상태 | 비고 |
|------|------|------|
| 프로그램 | ✅ | `[치료프로그램명]-[개인/그룹]` |
| 날짜 / 시간 | ✅ | |
| 장소 | ✅ | |

**최근 회기 요약 (hero — 약속 카드 직하)**

> "굳이 상담 상세에 안 들어가도 이번 회기 직전 컨텍스트를 잡을 수 있게" 의도. 가벼운 1줄 brief로 마찰 해소.
> 같은 케이스에 완료된 이전 회기가 1건 이상 있을 때만 노출. 첫 회기는 hero 숨김.

| 항목 | 상태 | 비고 |
|------|------|------|
| 직전 회기 날짜 + 상태 | ✅ | 예: `직전 회기 5/15 (수) · 완료` |
| 직전 회기 요약 1줄 | ✅ | 일지 모델의 `summary` 필드를 그대로 노출 (자연 문장). summary 비어있으면 요약 영역 숨김 |
| 다음 회기 일자 | ✅ | 예: `다음 회기 5/22 (목) 14:00` |

> **도메인 경계**: hero는 임상 정보 묶음(키워드 칩·출석 패턴·사전기록지 등)을 끌어오지 않는다. **직전 1줄 요약 + 다음 일자만** — 가벼운 brief에 한정. 자세한 임상 컨텍스트가 필요하면 상담 상세(§3-2) · 내담자 상세(§3-3)로 이동.

**하단 영역**

| 항목 | 조건 | 상태 |
|------|------|------|
| 참여 내담자 | 일정 상태 ≠ 취소일 때 표시 | ✅ |
| 필드노트 | 항상 표시 (연결 여부) | ✅ |
| 취소 사유 | 취소 상태일 때만 (enum + 비고 노출) | ✅ |
| 메모 | 항상 표시 | ⚠️ 상담사 검증 필요 — 메모의 용도(운영 vs 회기 준비) 명확화 필요 |

**네비게이션**: 일정 상세 → 상담 상세(세션)

### 3-2. 상담 상세 (세션)

#### 상담 현황 리스트 카드

> 진입: 내정보 → 상담 현황. 케이스 단위 카드 리스트.

| 항목 | 상태 | 비고 |
|------|------|------|
| 상담 코드 | ✅ | `case_code` (예: C00041). 카드 **최상단 caption** — `label-01`, text/caption/default(gray-500). 위계 최약(식별 보조). 회기 번호(N회기)는 붙이지 않음(§1 ❌, 케이스 단위라 단일 회기 없음) |
| 내담자 이름 + "외 N명" | ✅ | 첫 번째 내담자 기준. 그룹 케이스는 `홍길동 외 2명` |
| 성별 / 나이 | ✅ | 첫 번째 내담자 기준 |
| 프로그램명 | ✅ | `[치료프로그램명]-[개인/그룹]` 형식 |
| 케이스 상태 | ✅ | 진행중 / 예정 / 완료 / 취소 |
| 연장필요 보조 라벨 | ✅ | 진행중 + 회기 모두 소화(completed_sessions ≥ total_sessions) 조건. 상태 뱃지 아래 작게 표시 |
| 다음 상담일 | ✅ | 미지정 시 `-` |
| 회기 진행도 | ✅ | progress bar + `N/M` 표기 |

#### 요약 카드

| 항목 | 상태 | 비고 |
|------|------|------|
| 상담 코드 | ✅ | `case_code` (예: C00041). 상단 카드 **최상단 caption** — `label-01`, text/caption/default(gray-500). 회기 번호 미포함(§1 ❌) |
| 상담 프로그램명 | ✅ | |
| 시작 일정 | ✅ | |
| 완료일 | ✅ | 미완료 시 `-` 표시 |
| 회기 진행도 | ✅ | |
| 케이스 상태 | ✅ | 진행중 / 완료 / 취소 — 우상단 뱃지 |
| 담당 상담사 | ❌ | 모바일은 상담사 전용 앱이라 본인 정보. 노출 안 함 |
| 참석률 | ❌ | 진행 회기 표기(`5/10회`)로 출석 신호 충족. 별도 행 노출하지 않음 |
| 일지작성률 | ❌ | 제거 (상담사 피드백) |
| 주호소 | ❌ | 상담 케이스 상세에는 표시하지 않음. 내담자 도메인 속성이므로 §3-3 내담자 상세에서 노출 |

#### 내담자 목록

| 항목 | 상태 | 비고 |
|------|------|------|
| 이름 / 성별 / 나이 | ✅ | 기본 식별 정보 한 줄로 표기 |
| 생년월일 | ❌ | 식별 디테일은 §3-3 내담자 상세에서만 확인. compact 카드에선 표시 안 함 |
| 출결 횟수 | ✅ | 한 내담자의 누적 진행 회기 (참석 회기 / 케이스 전체 회기). 예: `5/10회`. 화면 라벨은 "진행 회기" |
| 출석 주의 배지 | ❌ | 도메인 경계상 내담자 메뉴(§3-3 캐러셀·상세 출석 패턴 시각화) 영역. 케이스 상세에는 노출하지 않음 |

#### 내담자 출결 상태

| 상태 | 코드 | 사유 입력 | 비고 |
|------|------|----------|------|
| 참석 | `attended` | — | |
| 불참 | `absent` | enum + 비고 (필수) | 사전 통보 결석 |
| 노쇼 | `no_show` | — | "이유 없이 안 온 것"이 정의 — 사유 입력·표시 없음. 회기 차감 여부(`is_consumed`)만 운영상 별도 결정 |

**출결 사유 enum (불참 전용)**
- 불참: `질병` / `가족 사정` / `학교·외부 일정` / `기타`

**일정 완료 시 일괄 처리 동작** (§3-1 참조)
- 일정 상태가 `완료`로 변경되면 모든 참여 내담자가 default `참석` 처리
- 이후 내담자 카드 탭 → 개별 출결 변경 가능 (불참·노쇼)
- **불참** 선택 시: 사유 enum + 비고 입력 폼(BottomSheet) 노출
- **노쇼** 선택 시: 사유 입력 없음. 회기 차감 여부만 확인

#### 청구 (세션 단건 / 패키지 선결제) ⚠️

> web counselor 시점과 통일. **발행·납부·패키지 선결제만 모바일 가능**, 환불·삭제는 비범위(관리자 web). counselor `write:billing`(본인 담당) 기준.

| 진입 | 단위 | 동작 | 상태 |
|------|------|------|------|
| 회기 바텀시트 → 내담자별 `청구하기` | 세션 × 내담자 1건 | 세션 단건 청구 발행 시트 (단가표 prefill) | ⚠️ |
| 내담자 목록 카드 → `패키지 선결제` | 케이스 × 내담자 (전 회기 묶음) | 패키지 선결제 시트 | ⚠️ |
| 청구 상태 배지 탭 → 청구 상세 시트 | 청구서 1건 | 항목·금액·납부기록 조회 + `납부 등록` | ⚠️ |

- **상태 표현** (web BillingActionButton 통일): `none`=청구하기 / `pending`=청구 확인(미완납 조회) / `completed`=청구 완료(또는 선결제 완료)
- **세션 ↔ 패키지 상호배제**: 한 내담자에 세션 개별 청구가 있으면 패키지 선결제 비활성, 반대도 동일 (web 정책과 동일)
- **0원·완납 자동 처리**, 미수금 초과 납부 차단 등 검증은 백엔드 공통 (web과 동일 API)

| 항목 | 상태 | 비고 |

| 내담자 이름 | ✅ | |

**AI 감지 기준**
- 출석 주의: 최근 3회기 중 2회 이상 결석
- 노쇼 후 미재예약: 노쇼 발생 후 재예약 없음

> **출석 주의 감지 기준**: 가장 최근 3회기 기준. 과거 결석이 아닌 현재 진행 중인 결석 패턴만 감지.
> 예: `● ○ ○ ● ● ●` → 최근 3회기(4,5,6) 전부 출석 → 경고 없음

### 3-4. 필드노트 — ❓ 정의 예정 (일부 확정)

> 화면 전반은 정의 예정. 단 **AI 분석 탭(§3-4-1)**·**연결 단위(§3-4-2)**·**목록 카드/필터(§3-4-4)**는 아래로 확정한다.

#### 3-4-1. 상세 — AI 분석 탭 (구조화 분석)

> 진입: 필드노트 상세 → 분석 완료(`summary_status=completed`) → "AI 분석" 탭.
> 데이터: 요약 스텝(LLM)이 녹취록+메모를 분석해 구조화 JSON 생성 → `field_note.analysis`에 저장, `FieldNoteDetailResponse.analysis`로 노출. **데이터 있는 섹션만 렌더**, 없으면 평문 `summary` 폴백(구버전 노트).

| 항목 | 상태 | 비고 |
|------|------|------|
| 요약 | ✅ | `analysis.summary` (없으면 `summary` 평문). 100–200자 요약체 |
| 키워드 | ✅ | `analysis.keywords` — 칩. 회기 대표 명사구 3–7개 |
| 주요 이슈·호소 | ✅ | `analysis.issues` — 불릿. 0–5개 |
| 정서 흐름 | ✅ | `analysis.mood` — 관찰 기반 한 줄. 정보 부족 시 숨김 |
| 하이라이트 | ✅ | `analysis.highlights[{t(초), text}]` — 탭 시 그 지점부터 **재생 점프**(전사 싱크와 동일 seek) |
| 상담일지 초안 만들기 / 다시 분석 | ✅ | 기존 유지 |

> **경계**: 분석 탭은 **회기 이해용 경량 세트**로 한정한다. 개입·진전·과제·다음목표 등 깊은 임상 구조는 상담일지(§3-5, counseling_note)로 보낸다. 살펴볼 신호·후속 액션은 향후 agentic(§4)와 함께 검토.
>
> ⚠️ 본 절은 화면 구현과 함께 추가됨 — 본래 스펙 변경은 별도 작업 권장(CLAUDE.md). 커밋 분리가 필요하면 이 절만 떼어내도 됨.

#### 3-4-2. 연결 단위 — 상담은 회기, 검사는 항목(task) ✅

> 필드노트가 "무엇에 묶이는가"는 도메인별로 다르다. 서버 모델 `field_notes` 의 연결 컬럼(`schedule_id`·`task_id`)이 이 정책의 source of truth.

| 도메인 | 연결 단위 | 개수 | 비고 |
|--------|----------|------|------|
| 상담 | **회기(session = 일정)** | 회기당 1개 | `field_notes.schedule_id`로 연결 |
| 검사 | **개별 검사(task)** | 검사 항목당 1개 | `field_notes.task_id`로 연결. 한 검사 일정(세션) 안에 검사 4개면 검사별로 따로(각 1개) |

**왜 검사는 task 단위인가** — 투사검사(HTP·SCT·Rorschach·TAT 등)는 내담자의 언어 반응·연상과 검사자 inquiry **자체가 임상 데이터**다. 회기 대화에 필드노트가 붙는 것과 같은 논리로, 검사별 녹음·전사·분석이 의미가 있다. 풀배터리 한 일정을 한 녹음으로 뭉치면 "이건 HTP inquiry, 이건 SCT"를 가를 수 없다.

**1:1 강제 (회기·검사 공통)** ✅ — 한 회기/검사에 **필드노트는 1개만** 연결된다. 회기·검사 모두 동일.
- DB: `field_notes.schedule_id`·`task_id`에 **partial unique index**(`... IS NOT NULL AND deleted_at IS NULL`) — soft delete 된 노트는 제외하므로 **삭제 후 같은 회기/검사에 새 노트 재연결 가능**.
- 앱: 생성(`create_field_note`)·연결(`link_schedule`/`link_task`) 모두 중복 시 `ConflictException`(409).
- 마이그레이션 `d9b3f6a2c811` — 기존 중복(검사 1:N 허용 시절 잔재)은 **최신 1개만 남기고 soft delete**.

> ⚠️ **변경 이력 (2026-06-15)**: 검사 task를 **1:N → 1:1**로 변경. 직전 안은 "재실시 등 task 1 ↔ field_note N"을 허용했으나, 한 회기/검사에 노트가 여럿 붙는 혼란을 막기 위해 1:1로 통일(사용자 결정). 재실시 등 추가 기록이 필요하면 §3-4-5 흐름대로 기존 노트를 삭제(soft delete)하고 새 노트를 붙인다.

**적용 경계**
- 검사 항목마다 **필요한 것만** 연결한다 (인지/객관 검사 BGT·K-WISC는 보통 미연결, 투사검사 위주).
- **온라인 검사(`execution_method=online`)**: 검사자가 현장에 없어 녹음 N/A. onsite 검사만 대상.
- **AI 산출물 분기**: 검사 task 필드노트의 분석은 상담일지(counseling_note)가 아니라 **검사 소견(`task.opinion`)** 방향으로 소비한다. note 서식 타입(soap/dap 등)은 상담 전용 — 검사엔 적용하지 않는다.

> **아키텍처 가드레일** (CLAUDE.md 모듈 경계): field_note ↔ assessment 연동은 **AssessmentFacade 경유**로만 한다. `AssessmentTask` 모델·Repository 직접 import 금지(기존 `ScheduleRepository` 직접 접근 같은 위반을 반복하지 않는다). `field_notes.task_id`는 `schedule_id`와 동일하게 **FK 제약 없는 UUID 참조**(application-level 관리).
>
> ⚠️ 본 절은 검사 필드노트 구현과 함께 추가됨(2026-06). 구현 전 스펙 확정 원칙(CLAUDE.md) 준수.

#### 3-4-3. 검사 필드노트 분석 — 검사 렌즈 (상담과 다름) ⚠️

> task 연결 필드노트(§3-4-2)는 §3-4-1 상담 분석을 **그대로 쓰지 않는다.** 검사·특히 투사검사는 **verbatim(있는 그대로의 반응)이 임상 데이터**라, 분석의 1순위는 AI 요약이 아니라 **전사 싱크**다.

**핵심 원칙**

1. **전사 싱크가 1순위** — 정확한 verbatim 전사 + 화자분리(검사자↔내담자) + **탭→그 지점 재생**(§3-4-1 highlights seek와 동일 인프라 재사용). 검사 노트 상세는 이걸 **전면**에 둔다(상담식 요약에 가리지 않게).
2. **AI는 해석하지 않고 "정리·위치 찾기"만** — 검사 맥락에서 정서·진단 등 해석성 출력은 임상 판단을 오염시킬 위험이 있어 **금지**. AI는 검사자가 소견 쓸 raw material을 모아주는 역할에 한정.
3. **소견 초안으로 연결** — 분석은 **검사 소견(`task.opinion`) 초안**으로 소비. 단 **자동 저장 금지** — 소견 시트에 prefill하고 검사자가 검토 후 저장(기존 `updateTaskOpinion`). 상담의 "일지 초안"에 대응.

**검사 렌즈 추출 항목** (task 노트일 때 `analysis` JSON에 채움 — 상담의 `mood`/`issues` 대신)

| 항목 | 상태 | 비고 |
|------|------|------|
| 전사 싱크(verbatim+화자+seek) | ✅ | 1순위. 인프라 재사용 |
| 질문↔반응 쌍 | ⚠️ | 검사자 inquiry와 내담자 반응을 타임스탬프로 묶음 (`responses[{t, prompt, response}]`) |
| 관찰 지점 | ⚠️ | 긴 침묵·거부·정서 변화 등 **관찰 가능한 사실** 지점 (`observations[{t, text}]`) — 해석 아님 |
| 소견 인용 후보 | ⚠️ | 소견에 그대로 넣을 만한 verbatim 인용 (`quotes[{t, text}]`) |
| 요약 1줄 | ⚠️ | 회기 식별용 사실 요약(누가 어떤 검사). **해석·정서 평가 금지** |

**금지 (검사 렌즈에서 빼는 것)**

- ❌ 정서/기분 평가(`mood`), 임상적 이슈 해석(`issues`) — 상담 전용. 검사자 판단 영역 침범
- ❌ 진단적 추론, 점수 해석 (채점·해석은 web 전용 §3-6)
- ❌ 상담일지(counseling_note)·서식 타입(soap/dap) 생성

> **구현 경계** (CLAUDE.md): 분석 렌즈 분기는 **field_note 내부에서 `task_id` 유무로** 결정(cross-module 의존 없음). `analysis`는 JSON 컬럼이라 검사 필드 추가는 **마이그레이션 불필요**(additive). 소견 prefill은 **클라이언트**가 분석을 읽어 시트에 채움 — 서버 cross-module write 없음(정 필요시 AssessmentFacade 경유). ⚠️ 본 절은 구현 전 합의용 — `responses/observations/quotes` 추출 품질은 프롬프트 튜닝·검사자 검증 후 ✅ 격상.

| 프로그램·검사명 | ✅ | 2행. 상담=`program_name`(예: `놀이치료 - 개인`) / 검사=검사명(예: `풀배터리검사-HTP`). 검사 세트면 앞에 `세트` 뱃지. **장소(상담실)는 목록 API 미제공 → 생략** |
| 미리보기 2줄 | ✅ | `summary` > `refined_transcript`(전사) 순, 실제 내용 있을 때만. 실패=빨강 한 줄, 분석중=`AI가 분석하고 있어요` 폴백 |
| play 아이콘 | ❌ | 제거. 카드 전체 탭=상세 진입이라 "탭하면 재생" 오해 |

**미지정 노트 카드 (CTA)** ✅

- 연결 안 된 노트(녹음/일시정지 제외)는 일반 카드 대신 **CTA 카드**로: 제목 `회기 미지정` + 안내 `어떤 상담·검사에 대한 기록인가요?` + 아웃라인 `선택하기` 버튼(탭=상세 진입해 회기 연결).

**필터 = 연결 축 (+ 카운트) + 검색** ✅

| 필터 | 의미 |
|------|------|
| 전체 | 모든 필드노트 |
| 연결 | 회기/검사에 붙은 노트 (`schedule_id` 또는 `task_id` 있음) |
| 미연결 | 어디에도 안 붙은 노트 (`schedule_id` & `task_id` 둘 다 null) |

- **칩 = 라이트 채움 pill**(active). 각 칩에 **카운트 인라인**(전체·연결·미연결).
- **검색바**: 내담자명·프로그램·검사명 부분일치(클라이언트측).
- **날짜 그룹**: `오늘`/`어제`/`M월 d일 (요일)` 헤더(카운트 없이).

**검사(task) 노트 표시** ✅

- 블루 dot + 2행 검사명. **세트 뱃지** = 같은 case 안에 검사 노트가 둘 이상일 때(`task.case_id` 중복). 데이터: 목록 응답 **task brief**(`task.client_name`·`assessment_kor_name`·`case_id`), `isLinked = schedule_id || task_id`.

> **트레이드오프 (직전 안 대비 — 인지 부담 인정)**:
> - **분석 가시성 ↓**: 분석중/완료를 카드 전면 신호에서 뺐다(미리보기 폴백 텍스트로만 약하게). "이 노트 분석됐나"를 한눈에 보긴 어려움 — 시안 우선의 의도적 트레이드오프.
> - **용어 혼재**: 직전 안은 `미연결`(DB 관계어)을 ❌ 처리하고 `회기 미지정`을 썼으나, 시안 채택으로 **필터 라벨은 `미연결`**, 카드 본문/CTA 제목은 `회기 미지정` 유지. 정리 여지 ⚠️.
> - **검사 1급화 약화**: 도메인 필터(상담/검사 분리)를 연결축으로 되돌려, 검사 노트를 필터로 가르지 않는다(연결로만 묶임).

> **구현 경계** (2026-06-12): 검색·필터·카운트·세트 판정은 모두 **클라이언트 파생** — 목록을 **단일 unfiltered 쿼리(size 50)**로 받아 처리(연결/미연결 카운트를 동시에 보이려면 단일 소스 필요). 50건 초과 정밀도는 추후 페이지네이션 시 보강. 녹음 중 `MM:SS`는 전역 `recordingStore.elapsed` 구독. 장소(상담실)는 목록 응답에 없어 미표시 — 필요 시 `FieldNoteScheduleBrief`에 `room` 추가 후속.

#### 3-4-5. 이어녹음(resume) 경계 — AI 분석 후 차단 ✅

> 한 필드노트에 녹음을 더 붙이는 **이어녹음(resume)**은 **AI 분석 전까지만** 가능하다. **AI 분석이 실행된 노트에는 이어녹음을 막는다.**

**규칙**

| 노트 상태 | 이어녹음 | 비고 |
|----------|---------|------|
| 녹음 중 / 일시정지 | ✅ 가능 | 현행 — 같은 노트에 이어서 녹음 |
| 정지(저장) · 전사 완료 · 화자분리 완료 | ✅ 가능 | 전사·화자분리만으로는 차단하지 않음. 같은 노트에 이어녹음 진입점 유지 |
| **AI 분석 실행 후 (분석중 · 분석 완료)** | ❌ **차단** | AI 분석(`field_note.analysis` 생성 / `summary_status != none`)이 한 번이라도 돌면 이어녹음 진입점 제거 |

- **기준은 AI 분석.** 전사·화자분리(기반, §3-4-1 fallback 평문 포함)는 이어녹음을 막지 않는다. 무거운 AI 분석(요약·일지/소견 초안)이 실행된 순간부터 차단한다.
- **이유**: AI 분석은 그 시점의 녹취록·메모를 입력으로 산출된 결과물이다. 이후 오디오를 덧붙이면 이미 만들어진 분석과 어긋나 신뢰를 깬다. 분석된 노트는 "닫힌 회기 산출물"로 둔다.
- **추가 기록이 필요하면 새 필드노트로.** 분석된 노트에서는 이어녹음 대신 §3-4-2 연결 단위(회기/검사 task)에 맞춰 **새 노트**를 만든다(목록 "추가 녹음" 흐름). 기존 분석은 보존된다.
- **표현**: 분석된 노트 상세에서 이어녹음 버튼/진입점을 **노출하지 않는다**(비활성이 아니라 숨김). 사용자가 굳이 찾지 않도록 한다.

> **구현 경계**: 차단 판단은 **클라이언트 파생** — 노트 상세의 `analysis`/`summary_status` 유무로 이어녹음 진입점을 가린다. 서버는 방어적으로 이미 분석된 노트에 대한 오디오 청크·resume 요청을 거절(`InvalidOperationException` → 400)할 수 있다(이중 안전망, ⚠️ 추후). AI 분석은 §3-4-1(상담)·§3-4-3(검사 렌즈) 산출물 모두 포함.

| 항목 | 상태 | 비고 |
|------|------|------|
| 검사 항목별 필드노트 상태 | ⚠️ | 검사 항목 카드에 표시 — 미연결 / 녹음중 / 분석중 / 완료 |
| "녹음 연결" 진입 | ⚠️ | 항목 카드에서 필드노트 녹음 시작·연결. `field_notes.task_id` 세팅 |
| 필드노트 상세 진입 | ⚠️ | 연결된 항목 → 필드노트 상세(전사·AI 분석). §3-4-1 분석 탭 재사용 |
| 온라인 검사 | ❌ | `execution_method=online` 은 녹음 대상 아님 — 진입점 숨김 |

> **분석 렌즈**: 검사 필드노트 분석은 상담과 다르다 — **전사 싱크 1순위 + 비해석 정리(질문↔반응·관찰 지점·인용 후보)**. 상세 정의는 **§3-4-3**. 정서/진단 등 해석성 출력은 금지.
> **소견과의 관계**: 분석은 해당 항목의 **검사 소견(`task.opinion`) 초안**으로 이어진다(상담 일지 초안 대응). 단 자동 저장 금지 — 소견 시트에 prefill 후 검사자 검토·저장.
> **연결 단위·아키텍처 제약은 §3-4-2**, 분석 렌즈·구현 경계는 **§3-4-3** 을 따른다.

**검사 청구** ⚠️

| 항목 | 상태 | 비고 |
|------|------|------|
| 청구 상태/액션 | ⚠️ | **세션 단건 청구만** (검사는 패키지 선결제 없음 — web과 동일). `none`=청구하기 / `pending`=청구 확인 / `completed`=청구 완료 |
| 청구 상세 시트 | ⚠️ | 항목·금액·납부기록 조회 + `납부 등록` |

> 발행·납부만 모바일 가능. 환불·삭제는 관리자 web. §3-2 "청구" 소섹션과 상태 표현 통일.

### 3-9. 청구 현황

> 진입: 내정보 → 업무 바로가기 "청구 현황".
> 본인 담당 케이스의 청구서를 모아 보는 리스트. web `/billing` 페이지의 counselor(`access_level=own`) 범위 축소 버전.
> web의 청구 기능을 **환불·삭제만 빼고** 가져온다 (CLAUDE.md 원칙).
> 센터 전체 매출 대시보드·단가표 관리는 관리자 web 전용 — 모바일 비범위.

#### 필터 (Segment)

| 필터 | 의미 | 비고 |
|------|------|------|
| 전체 | 발행 + 완납 모두 | 기본 탭 |
| 발행 | `issued` — 미완납 청구서 | 미수금 있는 건 |
| 완납 | `paid` — 납부 완료 | |

> `draft`(임시)는 모바일에서 노출하지 않음 — 발행 전 단계는 web에서 관리.
> `overdue`(연체)는 Phase 4 이후 검토. 현재는 `issued`에 포함.

#### 정렬

| 정렬 | 기준 |
|------|------|
| 최신순 (기본) | 발행일(`issued_at`) 내림차순 |

#### 검색

| 검색 | 기준 |
|------|------|
| 내담자 이름 | 클라이언트 측 필터 |

#### 리스트 카드 항목

| 항목 | 상태 | 비고 |
|------|------|------|
| 내담자 이름 | ✅ | |
| 항목 요약 | ✅ | `item_summary`. 예: `놀이치료-개인 외 1건` |
| 청구 금액 | ✅ | `total_amount`. 원 단위 포맷 |
| 미수금 | ✅ | `unpaid_amount`. 미완납(`issued`) 상태에서만 표시. 0원이면 숨김 |
| 청구 상태 | ✅ | 발행(blue) / 완납(green). web `BILLABLE_STATUS_COLORS`와 통일 |
| 발행일 | ✅ | `issued_at`. 짧은 날짜 (`M월 d일`) |
| 패키지 뱃지 | ✅ | `is_package=true`이면 `패키지` 뱃지 표시 |

#### 카드 탭 동작

청구 상세 바텀시트 진입. §3-2 "청구 상태 배지 탭 → 청구 상세 시트"와 **동일한 바텀시트 재사용**.

| 항목 | 상태 | 비고 |
|------|------|------|
| 청구 항목 리스트 | ✅ | `BillableItem` 목록 (품명·수량·단가·금액) |
| 금액 요약 | ✅ | 소계·할인·총액·납부액·미수금 |
| 납부 기록 | ✅ | `Payment` 목록 (금액·수단·일자) |
| 납부 등록 버튼 | ✅ | 미완납(`issued`) 상태에서만 활성. web `PaymentModal`과 동일 플로우 |

#### 모바일 비범위 (web 위임)

| 기능 | 사유 |
|------|------|
| 청구서 삭제 | counselor에 `delete:billing` 없음 |
| 환불 | 관리자 web 전용 (Phase 4) |
| 단가표 관리 | 관리자 web 전용 (`/billing/price-list`) |
| 센터 전체 매출 조회 | 관리자 대시보드 영역 |
| 청구서 신규 생성 | 리스트에서 직접 생성 불가 — §3-2 회기 바텀시트·패키지 선결제 등 **맥락 진입만** 허용 |

> **신규 생성 제한 이유**: 모바일에서 청구 발행은 "회기 완료 후 바로 청구" 플로우가 자연스럽다. 리스트에서 맥락 없이 생성하면 내담자·케이스·세션 선택 UX가 복잡해지고, 잘못된 청구 발생 위험이 높아진다. 필요시 상담/검사 상세에서 발행 후 리스트에서 확인·납부하는 흐름을 유지한다.

## 4. Agentic 신호 기준

> 두 위치에서 노출.
> - **홈 화면**: 횡단 발견 (여러 내담자에 걸친 상담사의 오늘 업무)
> - **내담자 상세 Attention 카드**: 단일 인물 컨텍스트 안에서의 처리
> 같은 신호가 두 곳에 표시될 수 있되, 라벨링·시각 weight는 다르게 (홈=발견, 상세=처리).
> 내담자 상태 기반 신호(출석 주의, 노쇼)는 내담자 탭 캐러셀에서도 처리.

| 우선순위 | 신호 | 감지 기준 | 상태 | 액션 |
|----------|------|-----------|------|------|
| 1 | 오늘 예정 세션 | 당일 일정 존재 | ✅ | 회기 시트 열기 |
| 2 | 상담일지 미작성 | 완료된 회기 중 상담일지 미작성 | ✅ | 일지 작성 시트 열기 |
| 3 | 상담 종결/연장 결정 필요 | 마지막 예정 회기 7일 이내 | ⚠️ Q5 인터뷰 후 임계값 확정. 후보: "마지막 회기 후 N일 무재예약" | 다음 회기 추가 / 종결 처리 |
| 4 | 검사 결과 미공유 | 검사 완료 후 결과 미공유 | ✅ | 결과 공유 트리거 |
| 5 | 청구 미수 | 본인 담당 케이스 중 미수금 발생 (access_level=`own`) | ⚠️ A2 데이터 + Q2 인터뷰 후 ✅ | 청구 상세 열기 → 납부 등록 (모바일) / 환불은 web |

**Mobile에서의 액션 범위** (CLAUDE.md 권한 룰과 연계):
- **청구(신호 5)**: 발행·납부 등록·패키지 선결제까지 모바일 처리 가능 (counselor `write:billing`, 본인 담당). 환불·삭제만 web. → §3-2 "청구" 소섹션
- **그 외 운영자 액션**(결과 보고서 작성·사전기록지 폼 발송): 인지(read) + 1차 트리거(메시지 전송·시트 열기)까지. 처리는 web 위임

> **신호 2 ↔ 상담일지 리스트 연계** ⚠️: 신호 2 "상담일지 미작성"과 상담일지 리스트(§3-5-1)의 `미작성` 필터는 동일 데이터 소스(`find_unlogged_completed_sessions_by_counselor`)를 사용한다. 홈은 발견(요약), 리스트는 처리(작성 진입)로 라벨링·시각 weight를 다르게 한다.
