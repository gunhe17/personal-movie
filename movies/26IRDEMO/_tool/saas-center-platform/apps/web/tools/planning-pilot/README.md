# 기획 워크스페이스

여러 화면의 기획을 같은 UI에서 만들고 검토하는 로컬 전용 SvelteKit 5 · TypeScript 도구. 제품 API·DB·로그인 없이 실행되며, 후보 준비와 기획 정리는 로그인된 Codex·Claude Code CLI 또는 연결된 Codex 대화로 수행한다.

## 실행

Node **20.19 이상**(또는 22.12 이상). 별도 의존성 설치 없이 부모 `apps/web`의 설치된 SvelteKit·Vite·TypeScript·Vitest를 사용한다. 이 하위 도구는 별도 pnpm 워크스페이스 패키지가 아니다.

저장소 루트에서:

```sh
pnpm dev:planning                      # 자동 연결
pnpm dev:planning --ai=codex           # Codex CLI 독립 실행
pnpm dev:planning --ai=claude          # Claude Code CLI 독립 실행
pnpm dev:planning --ai=off             # AI 없이 조회·편집·저장
```

또는 `apps/web`에서:

```sh
npm run planning:dev
npm run planning:check
npm run planning:test
```

<http://127.0.0.1:4318>은 기획 목록, `/plans/ai-case-analysis`는 기존 AI 경과 분석이다. `server.mjs`는 AI 연결을 확인하고 Vite를 실행하며, UI와 업무·저장 로직은 `src/`의 Svelte·TypeScript로 구현한다. `svelte.config.js`는 SvelteKit 설정 파일이다.

- `PLANNING_AI_PROVIDER`: `auto`(기본), `codex`, `claude`, `codex-thread`, `off`. 실행 옵션 `--ai`가 우선한다.
- `PLANNING_AI_MODEL`: 선택한 CLI에 전달할 모델 ID. `--model=<모델 ID>`가 우선하고 미지정 시 각 CLI 기본 설정을 사용한다. 기존 대화 연결에서는 해당 대화의 모델을 유지하므로 `--model`은 독립 실행에서만 지원한다.
- `CODEX_THREAD_ID`: 현재 Codex 대화 연결용. 자동 모드에서 `codex queue --thread`가 지원되면 우선 사용한다. `--ai=codex/claude/off`를 지정하면 이 값보다 명시적 선택을 우선한다.
- `PLANNING_PILOT_PORT`: 기본 4318.
- `PLANNING_DATA_DIR`: 검증용 데이터 루트 지정. 일반 사용에서는 지정하지 않는다.
- 루프백 개발 서버 전용이다. 프로덕션 빌드는 검증할 수 있지만 운영 모드에서는 요청을 404로 거절한다. CLI 실행 기능을 제품 서버에 배포하지 않는다.

## 팀원별 AI 연결

각자 사용할 CLI를 설치하고 **한 번 로그인**한 뒤 위 명령으로 실행한다. Codex는 `codex login`, Claude Code는 `claude auth login`을 사용한다. 로그인 정보는 각 CLI가 관리하며 팀원 간 공유하지 않는다. 초기 의존성이 없다면 저장소 루트에서 `pnpm install`이 필요하다.

자동 연결 순서: 전달받은 Codex 대화 → 로그인된 Codex CLI → 로그인된 Claude Code CLI → AI 없이 실행. 명시적으로 지정한 CLI가 설치/로그인되지 않았으면 시작 시 이유를 알리고 종료한다. 자동 선택은 설치·로그인 상태 기준이며 실제 모델 접근/사용량은 요청 시 확인된다. 실행만으로 모델을 호출하지 않는다.

개인 기본값은 이 도구 폴더의 `.env.local`에 설정할 수 있다(커밋하지 않음):

```dotenv
PLANNING_AI_PROVIDER=claude
# PLANNING_AI_MODEL=사용할-모델-ID
```

독립 실행은 **요청마다 새 CLI 작업**을 만들고 저장된 기획·선택·결정과 관련 코드를 읽는다. Codex/Claude의 기존 대화 이력을 공유하거나 자동으로 재개하지 않는다. 대신 동일한 `plans/`와 `records/`를 사용하므로 공급자를 바꿔도 기획 맥락을 이어간다. 팀원끼리 다른 컴퓨터에서 같은 기획을 보려면 기획 파일 가져오기 등으로 자료를 전달해야 하며 실시간 공동 편집 서버는 아니다.

- Codex: `codex exec --sandbox read-only`, Claude: `claude -p`와 `Read,Glob,Grep` 도구로 조사한다. AI는 JSON 결과를 반환하고 서버가 Plan·후속 질문 스키마를 검증한 뒤 정해진 기획 파일만 저장한다. 원본 선택 기록은 보존한다.
- 후보 준비 완료 시 초안이 갱신되고, 기획 정리 완료 시 결과 문서가 표시된다. 실행 중에는 요청 버튼이 비활성화되며 제한 시간은 10분이다. 기존 대화 모드는 전달 후 별도 대화에서 처리하고 수동 새로고침한다.
- 응답 해석·스키마 검증 실패는 오류로 표시한다. AI 실행 중 기획 파일이 달라지면 후보를 덮어쓰지 않는다. CLI별 권한/로그인 오류를 다른 제공자로 자동 재시도하지 않는다.
- 실행 중인 서버에서 제공자를 바꾸려면 `Ctrl+C` 후 다른 `--ai` 값으로 다시 실행한다. 계정과 모델 설정은 각자 관리한다.

공식 CLI 참고: [Codex 비대화형 실행](https://developers.openai.com/codex/noninteractive/), [Claude Code 프로그램 실행](https://code.claude.com/docs/en/headless).

## 다른 화면의 기획 시작하기

1. 목록의 **새 프로젝트**에서 이름, 대상 화면 또는 코드 경로, 해결할 문제를 입력한다.
2. **AI에 후보 준비 요청**을 누르면 현재 목적·의견을 저장하고 선택한 AI로 조사 요청을 보낸다.
3. AI가 관련 구현·문서를 조사해 해당 `plans/<id>.json`을 작성한다.
4. 독립 CLI 모드는 완료 후 자동 반영된다. 기존 대화 모드는 **초안 새로고침**을 눌러 사용자 흐름과 후보를 검토한다.
5. 범위·동작·의견을 결정하고 **기획 정리**에서 요약을 확인한 뒤 요청한다.
6. 요청 후 오른쪽 **문서** 패널이 열린다. 완성된 결과가 이 패널에 자동으로 표시된다. 이전 결과 선택 및 수동 새로고침도 가능하다. 현재 선택이나 후보가 달라졌다면 이전 기준의 결과임을 표시한다.

기획 정리 결과는 반드시 원본 선택 기록과 같은 디렉터리의 `<recordId>-review.md`에 저장한다. 자동 생성되는 `<recordId>.md`는 선택 내역이지 AI의 완료 결과가 아니다. 원본 JSON은 수정하지 않는다. 워크스페이스는 화면이 보이는 동안 5초마다 결과를 확인하며, 큐 전달 상태만으로 완료를 표시하지 않는다. 결과 문서는 제목·문단·목록·강조·인라인 코드를 표시하고 HTML은 실행하지 않는다. 기획 결과는 디자인 승인과 별개다.

AI가 이미 조사해 작성한 파일은 **기획 파일 가져오기**로 추가할 수 있다. 같은 ID는 덮어쓰지 않는다. 저장소의 `plans/`에 파일을 직접 추가해도 목록 새로고침으로 반영된다. 새 화면을 추가할 때 라우트·컴포넌트·서버 코드를 수정할 필요가 없다.

이 도구가 자체적으로 모델 API 키를 받아 호출하는 것은 아니다. 독립 실행은 각 CLI의 로그인·모델 설정을 사용하며, 기존 대화 연결은 `codex queue`로 전달한다. 전달 여부와 결과 문서 완성 여부는 구분한다.

## 결과에서 다음 결정으로 이어가기

- 기획 결과의 **후속 질문**에서 필요한 항목을 **남은 결정에 추가**하거나 **이번 범위에서 제외**한다. 적용은 현재 초안에 기록되며 임시 저장으로 파일에 보관한다. 같은 질문 ID를 다시 가져와도 기존 답변을 덮어쓰지 않는다.
- **남은 결정**에서 직접 질문을 추가하고 관련 기능, 담당(함께·개발자·디자이너·운영), 구현 전 답변 필요 여부와 답변을 정한다. 담당별로 볼 수 있고 결정·제외한 질문은 기본적으로 접어 둔다.
- **결정함**에는 답변이 필요하다. 답변을 수정하면 다시 답변 필요 상태가 되어 재확인한다. 보류한 선행 질문은 계속 구현 전 질문 수에 포함한다. 관련 기능 자체가 보류·제외되면 그 기능의 질문은 현재 구현 전 질문 수에서 뺀다.
- **동작 미정**과 **구현 전 답변 필요**는 별도 집계다. 후속 질문이 남아 있어도 기획 정리 요청은 가능하며, 질문 0개를 구현·디자인 승인으로 해석하지 않는다.
- 답변을 작성한 후 **기획 정리**로 다시 검토하거나 **기획 보완 → 현재 의견으로 후보 보완 요청**을 사용한다. 후보 보완 후에는 초안 새로고침으로 갱신하고 기존 선택을 이어간다.
- 예전 Markdown 결과에는 **이 결과에서 질문 정리 요청**을 사용할 수 있다. 원본 선택 기록과 Markdown은 보존한다. AI 연결 없이도 직접 질문 추가·답변·저장은 가능하다.

AI는 새 기획 정리 시 `<recordId>-review.md`와 함께 `<recordId>-review.json`을 저장한다. JSON 형식:

```json
{
  "followUps": [
    {
      "id": "approval-owner",
      "question": "누가 변경 요청을 승인하나요?",
      "context": "승인 방식은 선택했지만 담당자는 아직 정하지 않았습니다.",
      "featureId": "",
      "owner": "operator",
      "blocking": true
    }
  ]
}
```

`featureId`는 원본 선택 기록의 후보 ID 또는 새 요구/전체 기획이면 빈 문자열이다. `owner`는 `together | developer | designer | operator`. 한 항목은 질문 하나이며, 동일한 질문은 다음 검토에서도 ID를 유지한다. 최대 60개, 없으면 빈 배열이다. 담당·선행 여부는 제안이며 사용자가 변경할 수 있다. JSON이 없거나 손상돼도 기존 Markdown을 계속 표시한다. 범위·동작·후보가 다른 결과의 질문은 최신 기준으로 다시 정리한 후 가져온다.

선택 기록의 선택적 `decisions` 배열에는 위 필드와 `status: open | resolved | later | excluded`, `answer`, `origin`(출처 결과 기록 ID 또는 직접 작성이면 빈 문자열)을 저장한다. 이전 기록은 빈 결정 목록으로 읽는다. 원래 후보가 사라져도 질문과 답변은 보존하고 관련 항목을 재확인하도록 표시한다.

## AI가 작성할 공통 데이터 계약

정확한 타입: `src/lib/types.ts`의 `Plan`. 런타임 검증: `src/lib/schema.ts`의 `parsePlan`. 실제 사례: `plans/ai-case-analysis.json`.

문서 최상위 필드:

- `id`: 파일명과 같은 영문 소문자·숫자·하이픈 ID. 다른 화면이나 문서에 재사용하지 않는다.
- `title`, `screen`, `goal`: 기획 이름, 대상 경로, 사용자 문제.
- `reviewedAt`, `baseline`: 조사 날짜와 실제 확인한 코드 기준. 조사 전에는 빈 문자열.
- `notice`: 조사 범위와 확인하지 못한 점.
- `existing`: 확인된 기존 구현의 `title/detail/source` 목록.
- `features`: 검토 후보 목록. 조사 전에는 빈 배열을 허용한다.

## 항목별 내용 검토와 화면 전환

- **내용 채택 / 수정 요청 / 판단 보류**로 검토한다. 수정 요청에는 의견이 필요하다. 처리하면 다음 미검토·재검토 항목으로 이동하고, 마지막 검토를 되돌릴 수 있다. 필터는 현재 검토 항목 찾기에 쓰며, 처리 후에는 전체 미검토 순서로 이어간다.
- 내용 채택은 기능 포함·정책 확정·디자인 승인·구현 테스트 완료를 뜻하지 않는다. 미작성 내용이나 미결정 정책을 자동으로 채우지 않는다. 미결정 질문은 별도로 **남은 결정에 등록**한다.
- `Selection.contentReviews`에 항목 종류/ID, 검토 상태, 당시 내용 스냅샷, 의견, 시각을 보관한다. 검토한 기록은 브라우저 초안·임시 저장·복원·기획 정리 요청에 포함된다. 버튼을 누르기 전 작성 중인 의견은 현재 화면에서만 유지된다.
- 현재 내용이 스냅샷과 다른 항목은 **재검토**로 표시하고 변경된 필드의 이전/현재 내용을 보여준다. 삭제된 항목의 기록은 보존하되 현재 항목 수에는 세지 않는다. 내용 검토 기록만 바뀌어도 기존 구현 비교의 기준을 바뀐 것으로 처리하지 않는다.
- 기본 화면은 중앙 기획서다. 문서 항목 검토 후 다음 문서로 스크롤하고, 요구사항 다음의 기능 검토부터 구조도로 이어진다. 구조도는 기능과 흐름을 탐색하고 명시적으로 내용 검토를 누르면 상세 패널이 열리며, 좁은 화면에서는 캔버스 위에 겹쳐 열린다. 하단 검토 바는 독립 스크롤 아래에 고정된다.
- 탭 전환, 구조도 항목 등장, 상세 항목 교체, 진행률과 검토 안내에 짧은 애니메이션을 적용한다. 다음 항목의 위치로 부드럽게 이동하며 `prefers-reduced-motion: reduce`에서는 애니메이션·전환·부드러운 스크롤을 끈다.

## 흐름을 중심으로 검토하기

프로젝트 목록은 좌측 탐색과 카드 그리드로 표시한다. 편집기는 뷰포트 높이에 맞춰 **접을 수 있는 왼쪽 요청 패널 / 상단 작업 탭 / 중앙 문서·캔버스 / 오른쪽 도구 레일**로 나뉜다. 큰 제목과 요약 대시보드는 제거하고, 현재 기획의 목적·포함 기능·시나리오 수를 왼쪽에 둔다.

- **기획**: 기본 탭. **기획서 / 구조도 / 기능·동작** 보기로 전환한다. 기획서는 개요·요구사항을 문서 카드로, 구조도는 처음에 기능 묶음만 표시한다. 기능 → 연결된 정상 흐름 하나 → 진행 단계 순서로 좁혀가며, 예외 경로와 상세 사례는 접힌 상태에서 필요할 때 펼친다. 전체 관계선·축소 노드는 사용하지 않는다. 내용 검토와 범위·동작 편집은 별도다.
- **시나리오**: 정상 단계는 실선, 발생 단계에서 갈라지는 예외는 점선으로 연결한다. 단계별 처리·상태 변화·복구 방법을 확인한다.
- **영향·누락 점검**: 요구 연결, 기존 동작 영향, 모든 단계 × 9개 관점과 상세 사례를 확인한다. 미기록은 미조사다.
- **구현 비교**: 기획과 실제 화면·실행 근거를 비교한다.
- 오른쪽 **결정 / 문서 / 기록 / 설정**은 공통 도구다. 결정과 문서 패널을 열어도 중앙 탭은 유지되고 문서 결과 확인도 계속된다. 저장 기록을 복원하거나 목적·관련 구현 정보를 편집할 수 있다.
- 왼쪽 **보완 요청**은 기존 후보 보완 API를 사용해 목적·추가 의견·현재 선택을 연결된 대화로 전달한다. 실제 채팅 이력을 흉내 내지 않으며, 요청 결과를 안내하고 조사 완료 후 수동 새로고침한다. 빠른 제안은 입력에 추가할 뿐 자동 전송하지 않는다.

탭·공통 도구를 전환해도 초안과 작성 내용은 보존한다. 탭은 방향키·Home·End로 이동하며 지도 노드도 키보드로 선택할 수 있다. 좁은 화면에서는 왼쪽 패널이 기본적으로 접혀 있고 버튼으로 열 수 있다. 저장·기획 정리는 상단 또는 작은 화면의 왼쪽 패널에서 접근한다. 레이아웃·패널·검토 이동에 짧은 애니메이션을 사용하며 움직임 줄이기 설정을 존중한다.

예외는 정상 경로의 분기 이전 단계만 공유하며 실패한 단계의 정상 성공 상태를 적용하지 않는다. 상세 패널에서 예외 내부 단계, 최종 결과와 복구·다음 행동을 확인하고 **정상 경로**로 돌아갈 수 있다.

시나리오는 실제 실행·테스트가 아닌 기획 초안이다. 현재 범위·동작과 맞지 않는 연결은 경고하고 적용되지 않는 행동의 상태 변화는 표시하지 않는다. 상태·영향은 단계가 연결한 기존 `effects`에서 읽어 사용자 편집을 반영한다. 정상 경로에 거절·실패 행동을 단순 나열하지 않는다. 데이터가 없는 기존 기획에는 시나리오를 임의 추정하지 않고 후보 보완 요청을 제공한다.

`Plan.scenarios`는 최대 16개이며 다음 형식을 쓴다. ID는 기존 계약과 같은 영문 소문자·숫자·하이픈/밑줄이다.

```json
{
  "id": "approval-conflict",
  "title": "승인 중 일정 충돌",
  "kind": "exception",
  "precondition": "센터 승인 방식을 검토하는 초안",
  "trigger": "승인 전에 희망 시간에 충돌이 생김",
  "branch": {
    "scenarioId": "schedule-happy-path",
    "stepId": "approve-request"
  },
  "steps": [
    {
      "id": "recheck",
      "title": "최신 일정으로 재검토",
      "actor": "승인 담당자",
      "description": "충돌 상태에서 일정을 확정하지 않는다.",
      "expected": "승인 완료로 표시하지 않고 재검토한다.",
      "featureId": "schedule-change",
      "effectId": ""
    }
  ],
  "outcome": "일정 변경이 확정되지 않음. 요청 유지 상태는 미정.",
  "recovery": "재검토 후 승인·거절·재요청 기준을 결정해야 함.",
  "unresolved": "충돌 시 대기로 유지할까요, 거절할까요?"
}
```

- `kind`: `normal | exception`. 정상 시나리오는 `branch`를 생략한다. 예외는 별도 진입 상황이면 `branch`를 생략할 수 있다.
- `branch`: 존재하는 정상 시나리오의 단계에만 연결한다. 예외끼리 연결하거나 순환시키지 않는다. 분기는 해당 단계의 **처리 도중, 정상 성공 이전**을 뜻한다.
- `steps`: 1~16개. `featureId`는 기존 기능 ID 또는 빈 문자열, `effectId`는 해당 기능의 `effects` ID 또는 빈 문자열이다. 실패 단계에 정상 성공 행동을 연결하지 않는다.
- 미정인 기대 결과·복구 정책은 문구로 명시한다. `unresolved`는 남은 결정에 추가할 수 있다. 필요한 예외만 작성하며 예외가 모두 검증됐다고 표현하지 않는다.
- 새 AI 후보 준비 요청에서 시나리오도 생성한다. 보완할 내용을 전체 의견·남은 결정에 작성하고 후보 보완을 요청하면 갱신한다. 수동 그래프 편집기는 제공하지 않는다.
- 저장 기록에는 시나리오 원본도 함께 보관한다. 선택 Markdown과 AI 기획 정리 요청에는 정상·예외 순서와 분기, 최종 결과, 복구를 포함한다. 기존 저장 기록은 시나리오 없이 계속 읽으며 시나리오 변경 시 이전 결과 표시가 나타난다.

각 후보의 필드:

- `id/group/title/kind`: 고정 ID, 사용자 흐름 단계, 사용자 행동으로 표현한 질문, 기존 개선·신규 제안 등의 구분.
- `why/question/recommendation/acceptance/source`: 필요 이유, 결정 질문, 제안, 완료 조건 제안, 코드·문서 근거.
- `current`: 코드에서 확인한 현재 흐름의 짧은 문구 배열. 실제 화면 캡처로 표현하지 않는다.
- `options`: 동작 대안의 `id/title/description`. 선택적으로 `layout: stack | split`과 `panels`로 구조를 설명한다.
- `dependencies`: 함께 포함해야 하는 후보 ID 배열.
- `requirements`: 선택적 `featureId/optionId/message` 배열. 선행 후보의 특정 동작이 필요한 경우에만 사용한다.
- `effects`: 선택적 행동별 영향·상태 변화 초안. 아래 계약을 따른다. 기능 간 `dependencies`와 별개다.

## 범위·기존 영향·엣지케이스 점검

후보 준비·보완과 기획 정리 모두 `src/lib/server/audit-prompt.ts`의 점검 절차를 사용한다. **영향·누락 점검** 탭과 흐름 지도의 요약에 흐름 미작성, 요구 연결 누락, 영향 미확인, 전체 단계 관점 미조사, 정책 미정을 표시한다. **점검 보완 요청**에서 기획 보완 창을 열어 추가 의견을 적고 후보 보완을 요청한다. 조사 결과는 `Plan.audit`로 작성하고 초안 새로고침으로 읽는다. UI에서 질문을 남은 결정으로 가져올 수 있다.

- 사용자의 목적·메모·답변을 요구사항으로 추적한다. 범위가 포함/미정인 기능이 정상 흐름에 없으면 경고하며 제외·보류한 기능은 범위 누락 집계에서 뺀다. 정책 미정은 흐름 제외 사유가 아니다. 정상 경로 연결은 형식 점검이므로 실제 요구를 충분히 표현했는지 별도 검토한다.
- 기능별 이전/이후 동작, 유지 조건, 같은 데이터·권한·상태를 사용하는 기존 화면·업무에 대한 영향과 출처를 기록한다. 확인되지 않은 연계는 영향 미확인으로 남긴다.
- 정상·예외의 **모든 단계 × 9개 관점**을 표시한다. 미기록 셀은 미조사다. `cases`는 사례를 발견했다는 뜻이며 관점 전체를 검토했다거나 실행 검증을 끝냈다는 뜻이 아니다. 제외 기능이 포함된 경로도 전체 초안 점검표에 남으며 현재 선택과의 불일치를 표시한다.
- 지도에는 최대 16개의 대표 시나리오를 표시하고 상세 사례는 별도 목록으로 최대 256개 보관한다. 중요한 복합 조건을 포함하고, 처리·복구를 정하지 못한 사례는 빈 필드와 구체적 질문을 남긴다. 무리하게 모든 사례를 정상/예외 지도 노드로 바꾸지 않는다.
- 기존 계획에 `audit`가 없으면 조사가 끝난 것으로 추정하지 않는다. 원본 기획 변경 시 기존 사용자 선택·질문은 유지하고 이전 결과와 구현 비교의 기준 차이를 표시한다. 기획 기록 JSON/Markdown에 점검 기준을 보관한다. 구현 비교에도 저장 당시 단계에 연결된 상세 사례와 검증 기준을 표시한다. 개별 사례의 실행 판정을 자동 집계하지 않는다.

정확한 타입·검증: `src/lib/audit.ts`. `Plan.audit`의 네 배열은 필수이며 빈 배열도 허용한다.

```ts
{
  requirements: [{ // 최대 80개. 사용자 요구와 출처, 기능·정상 시나리오 연결
    id, text, source, featureIds: [], scenarioIds: []
  }],
  impacts: [{ // 기능당 1개, 최대 60개
    featureId, status: 'mapped' | 'na' | 'unknown',
    before, after, invariants: [],
    targets: [{ target, change, source }], reason, source
  }],
  cases: [{ // 최대 256개. 현재 시나리오·단계에 연결
    id, title, scenarioId, stepId, axes: [],
    condition, invariant, expected, feedback, recovery, verification,
    source, priority: 'high' | 'medium' | 'low', rationale, question
  }],
  checks: [{ // 단계당 관점별 1개, 최대 2,304개
    scenarioId, stepId, axis,
    status: 'cases' | 'na' | 'policy' | 'unknown', reason, caseIds: []
  }]
}
```

- `axis`/`axes` 값: `access` 권한·주체, `state` 상태·완료, `input` 입력·경계, `time` 시간·만료, `concurrency` 동시 처리, `failure` 부분 실패, `recovery` 재시도·중단, `propagation` 다른 화면·업무, `experience` 안내·사용 경험.
- requirements의 출처는 필수다. 아직 기능·흐름을 정의하지 못한 요구는 빈 연결로 보존한다. 없는 기능/시나리오 ID를 만들거나 예외 경로만 연결해 정상 흐름을 충족했다고 표시할 수 없다.
- `mapped` 영향은 이전·이후, 유지 조건, 영향 대상과 근거가 필요하다. `na` 영향은 이유와 조사 근거가 필요하다. `unknown`은 조사하지 못한 부분과 가설을 구분해 적는다. invariants와 targets는 각각 최대 12개.
- 사례 발견 셀에는 같은 단계·관점의 상세 사례를 연결한다. 해당 없음/정책 미정에는 이유가 필수다. 연결 사례가 있는 관점을 해당 없음으로 표시할 수 없다. 사례 자체가 있다고 누락된 점검 셀을 검토한 것으로 채우지 않는다.
- 사례는 제목·발생 조건·관점·출처·우선순위 이유가 필수다. 유지 조건·처리 후 상태·안내·복구·검증 방법이 비어 있으면 UI에 미정으로 표시한다. 우선순위는 빈도와 함께 손실·노출·영향 범위·복구 난이도·사용자 오해를 고려한다. 일반 문장 최대 2,000자, 출처·질문·우선순위 근거 최대 1,000자, 사례 제목 최대 300자.

## 기획과 구현 비교

**구현 비교** 탭에서 **새 기준으로 비교**를 시작한다. 실제 화면 주소(선택), 구현 버전/빌드 기준, 환경·데이터 조건, 확인 역할을 입력한다. 시작 시 서버에 있는 기획 원본과 현재 선택(영향·상태 편집 포함)을 스냅샷으로 고정한다. 시나리오가 없는 기획은 후보 보완을 먼저 요청한다.

1. **실제 화면 열기**로 확인할 구현에 접근한다. 흐름 지도에서 단계를 고르면 기획의 조건·예상 결과·상태 변화와 실제 관찰 기록을 나란히 볼 수 있다. 기획 당시 첨부한 참고 이미지도 함께 표시한다.
2. **화면** 판정에는 관찰 근거를 작성한다. 실제 캡처는 단계당 최대 3개, PNG/JPG 각 4MB다. 캡처를 크게 열어 확인하고 설명을 남길 수 있다.
3. **동작** 판정에는 실제 실행한 절차/예외 재현 조건과 관찰한 결과를 모두 적는다. 화면과 동작 각각 `확인 전 / 일치 / 차이 있음 / 미구현`으로 판정하며, 둘 다 일치일 때만 단계가 일치로 표시된다. 캡처만으로 동작을 확인 처리하지 않는다. 관찰 내용·재현 조건을 수정하면 관련 판정은 확인 전으로 돌아간다.
4. 차이를 **구현 수정 작업** 또는 **기획 질문**으로 남긴다. 후속 처리 목록에서 미완료 항목을 훑고 해당 단계로 이동할 수 있다. 처리 완료는 비교 판정을 자동 변경하지 않는다. 비교를 저장한 뒤 질문을 **남은 결정에 추가**할 수 있으며 같은 비교 기준의 같은 질문은 중복으로 추가하지 않는다. 가져온 질문은 기획 초안의 **임시 저장**으로 보관한다.
5. **비교 기록 저장**은 기획의 임시 저장과 별도다. 매번 새 비교 기록으로 저장하고 이전 기록을 보존한다. 기록 선택기로 과거 결과를 다시 볼 수 있다. 미저장 입력은 기획·비교 기록별로 브라우저에 보관한다.

현재 기획·선택이 고정한 기준과 달라지면 이전 기준의 결과임을 표시한다. 이전 기록에 관찰을 더 남길 수 있으나 기준은 바꾸지 않는다. 구현 빌드/역할/환경이 바뀌면 **새 기준으로 비교**를 시작해 이전 판정을 가져오지 않는다. 입력한 구현 버전은 사용자가 명시한 기준이며 실제 배포 버전을 자동 조회하지 않는다.

현재 비교는 사람이 화면을 열고 관찰·실행 결과를 기록하는 방식이다. 자동 브라우저 탐색·캡처·시나리오 실행·자동 판정은 수행하지 않는다. 실제로 실행하지 못한 예외는 확인 전으로 남긴다. 기획 자체가 미정이거나 범위·행동 연결이 맞지 않는 경우 기준 패널에 확인할 점을 표시한다.

- 저장: `records/<planId>/comparisons/compare-<uuid>.json`. 원본 기획·선택 스냅샷, 구현 기준, 단계별 판정·관찰·캡처·후속 처리, 원본 비교 ID(`runId`)와 직전 기록 ID(`parentId`)를 포함한다. 기존 파일은 덮어쓰지 않는다.
- API: `GET /api/plans/<planId>/comparisons`(목록), `GET ...?id=<recordId>`(상세), `POST ...`의 `action: start | save`. start는 서버가 기준을 캡처하며 save는 저장된 기준에서 관찰 기록만 새 버전으로 저장한다. 수정 클라이언트에서 기준 기획이나 구현 버전을 덮어쓸 수 없다.
- 정확한 계약: `src/lib/comparison.ts`, 저장: `src/lib/server/comparisons.ts`. 다른 기획의 기록·캡처를 연결할 수 없고 중복/누락 단계, 근거 없는 판정, 잘못된 URL을 거절한다. 깨진 비교 파일은 목록에서 경고하며 정상 기록은 유지한다.

## 행동의 영향과 상태 변화

각 후보에서 **행동의 영향과 상태 변화**를 확인하고 **내용 편집** 또는 **행동 추가**로 보완한다. 한 행동에서 변경 요청·실제 예약 등 여러 대상의 상태를 분리해서 적는다. 바뀌지 않는 상태도 명시한다. 빈칸은 미정이며, 해당하지 않는 경우에는 그 이유를 적는다. 남은 질문은 **남은 결정에 질문 추가**로 담당·답변 관리에 연결한다.

후보의 `effects`와 사용자 선택 항목의 선택적 `effects`는 같은 형식이다. 사용자 편집본이 있으면 후보보다 우선한다. 빈 배열도 사용자가 비운 내용으로 보존하며 후보 보완·기록 불러오기에서 자동으로 채우지 않는다. 동작을 바꿔도 이전 대안의 작성 내용은 유지하고 **다른 동작용도 보기**로 확인한다. 저장 요약과 Markdown에는 공통 행동 및 현재 선택한 동작의 행동만 표시한다. JSON 기록에는 다른 대안도 보관된다.

```json
{
  "id": "submit-change",
  "optionId": "approval",
  "actor": "요청한 사용자",
  "action": "희망 일정 제출",
  "condition": "예약 변경 권한 필요. 마감 정책은 미정.",
  "transitions": [
    { "target": "변경 요청", "before": "요청 없음", "after": "승인 대기" },
    { "target": "실제 예약", "before": "기존 일정", "after": "기존 일정 유지" }
  ],
  "impacts": [
    {
      "target": "승인 담당자",
      "change": "처리할 요청이 생김. 확인 위치는 미정."
    }
  ],
  "failure": "저장 실패 시 기존 예약 유지. 중복 요청 처리 정책은 미정.",
  "cancellation": "승인 대기 중 철회 가능 여부 미정.",
  "unresolved": "누가 변경 요청을 승인하나요?"
}
```

- `id`는 안정적인 행동 ID, `optionId`는 해당 후보의 선택지 ID 또는 모든 대안에 공통이면 빈 문자열이다. 사용자 편집본에서는 `other`도 가능하다. 없어진 선택지의 편집본은 지우지 않고 이전 동작으로 표시한다.
- 후보당 최대 12개 행동, 행동당 상태 대상·영향 대상 각각 최대 8개다. 초안 입력 중인 빈 문자열도 저장할 수 있다. 조건·실패·취소·미결정은 각각 최대 1,000자다.
- 새로운 AI 후보 준비에는 `effects` 작성을 요청한다. 기획 정리에는 사용자 편집본과 현재 선택 동작을 우선하고, 기능별 영향·상태 변화 절을 포함하도록 요청한다. 원본 선택 Markdown에도 동일한 구조가 포함된다.
- 기존 기획과 기록에는 필드가 없어도 정상적으로 동작한다. 기존 AI 결과 문서는 수정하지 않으며 최신 선택으로 정리를 요청하면 새 문서에 반영된다.

항목·선택지 ID는 영문 소문자·숫자·하이픈·밑줄을 사용한다. `other`, `undecided`는 도구가 제공하는 예약 선택지다. 없는 선행 후보·선택지, 순환 의존성, 중복 ID는 거절한다. 최대 60개 후보·후보당 8개 동작을 허용하지만 필요한 범위만 작게 작성한다.

기존 파일을 갱신할 때 같은 의미의 항목 ID는 유지한다. 새로운 의미에 옛 ID를 재사용하지 않는다. 사용자 동의 없이 후보를 확정하거나 제품 코드를 구현하지 않는다. 사실은 실제 근거를 확인하고, 제안과 미결정 사항을 분리한다.

## 결정과 기록

- 기능 범위(`choice`)와 동작 선택(`behavior`)은 별개다. 미정과 다른 안도 보존한다.
- `reviewed`는 참고 내용 확인이며, `designApproval: not_requested`는 디자인 승인과 구분한다.
- 현재 화면과 제안 이미지를 구분해 PNG·JPG를 첨부한다. 각 4MB, 후보당 3개. 실제 캡처 자동 수집은 지원하지 않는다.
- 초안은 기획 ID별 localStorage에 보관한다. **임시 저장**은 `records/<planId>/<timestamp>-<id>.json`과 같은 이름의 Markdown 문서를 생성한다.
- 이미지는 `records/<planId>/attachments/`에 저장한다. 다른 기획에서 해당 ID를 사용할 수 없다.
- 저장 기록을 선택해 불러올 수 있다. 불러오기 전 초안을 브라우저에 백업하고 복원 버튼을 제공한다.
- 초안 파일이 바뀌면 저장 요청을 거절해 오래된 후보로 덮어쓰는 일을 방지한다. 새로고침하면 같은 ID의 선택·메모를 이어받고 없어진 선택지는 미정으로 표시한다.
- `plans/`는 공유 가능한 기획 원본이다. `records/`는 Git에서 제외하는 로컬 기록이다. 실시간 공동 편집·계정별 승인 관리는 제공하지 않는다.

## 이전 실험의 자료 보존

기존 `records/*.json`과 `records/attachments/`는 이동하거나 삭제하지 않는다. AI 경과 분석에서만 예전 기록·이미지를 읽는 호환 경로를 제공한다.

같은 브라우저·포트에서 AI 경과 분석을 처음 열면 기존 `planning-pilot:<baseline>:<thread>` 초안을 새 기획별 키로 복원한다. 기존 키는 삭제하지 않는다. 다른 세션의 초안은 저장 기록을 통해 불러올 수 있다.

### 구조도에서 길을 잃지 않도록

- 첫 화면에는 기능 묶음과 범위·연결된 흐름 수만 표시한다. 중복되지 않는 기존 그룹명을 짧은 제목으로 쓰고 원래 질문은 아래에 보존한다.
- 한 기능에서 정상 흐름 하나를 선택하면 진행 단계를 세로로 읽는다. 해당 흐름 전체의 예외는 별도로 펼치며, 발생 단계·복구 행동·상세 사례를 이어서 본다. 이 연결은 탐색 맥락이며 새로운 기능 의존성을 추가하지 않는다.
- 상단 경로에서 전체 기능 또는 선택한 기능으로 돌아간다. 단계 탐색만으로 검토 항목을 채택하지 않으며, 내용 검토 패널을 열었을 때만 하단 검토 버튼을 표시한다.
- 요구사항과 연결되지 않은 요구·흐름, 별도 진입 예외를 삭제하거나 숨겨서 없애지 않는다. 각각 접을 수 있는 목록으로 보존하며 전체 검색·상태 필터로 모든 검토 항목에 접근할 수 있다.
- 검토 큐나 검색으로 예외/상세 사례를 열면 해당 기능·정상 흐름·예외의 위치를 찾아 펼친다. 관계가 없는 흐름은 연결 미작성 목록에서 검토한다.
