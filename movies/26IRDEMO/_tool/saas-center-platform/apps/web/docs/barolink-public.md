# 바로링크 공개 화면

`src/routes/verify-link/+page.svelte`는 SvelteKit 공개 라우트다. 직원용 `AssessmentFlowHeader`는 직원 조회·로그인 스토어에 의존하므로 공개 화면에 직접 재사용하지 않는다.

## UI 구성

- `Button`, `Typography`, 기존 아이콘과 `app.css`의 색상·입력 토큰을 사용한다.
- `VerificationCodeInput`은 네 자리 입력, 전체 코드 붙여넣기/자동완성, 앞자리 0, 키보드 이동을 담당하는 공통 컴포넌트다.
- `LinkVerification`은 인증 요청과 입력→확인→성공 전환을 담당한다. 요청 중 추가 전송을 막으며 실패 시 자동 반복 요청하지 않고 사용자가 재시도할 수 있다.
- 성공 표시는 서버 응답 후에만 나온다. 모션 감소 설정에서는 이동·확대 효과와 성공 대기를 생략한다.
- 문항을 처음 답하면 같은 페이지의 다음 미응답 문항으로 스크롤한다. 기존 답 수정 시에는 이동하지 않으며, 마지막 응답 뒤에는 다음/제출 버튼으로 이동한다. 페이지 넘김과 제출은 사용자가 직접 실행한다.
- 검사 헤더는 검사명·페이지 표시만 남기고 긴 제목은 줄바꿈한다. 센터명은 목록에만 표시한다. 선택지는 360px 미만에서 1열, 일반 모바일에서 2열로 배치한다. 모바일 스크롤 막대는 숨기되 스크롤 자체는 유지한다. 문항 전환 효과는 모션 감소 설정을 따른다.

## 이동과 세션

SvelteKit shallow routing의 `pushState`/`replaceState`로 목록·검사·문항 페이지를 기록한다. 브라우저 뒤로가기는 이전 문항/목록으로 이동한다. 목록 버튼은 방문 기록을 여러 단계 되감지 않고 현재 화면을 목록으로 교체해 메모리의 인증을 유지한다. 제출된 검사는 과거 기록으로 돌아가도 다시 응시하지 않는다. 초기 기록 설정은 라우터 초기화 이후에 실행한다.

인증 토큰·인증번호·응답은 방문 기록에 저장하지 않는다. 인증 토큰은 링크별 경로에 제한된 HttpOnly·SameSite=Strict 쿠키로 보관하며 HTTPS에서는 Secure를 적용한다. `/api/barolink/<linkId>/session`이 서버의 토큰 유효성·링크 만료/폐기를 재확인해 새로고침 후 목록을 복원한다. 복원은 쿠키/토큰 수명을 연장하지 않는다(최대 2시간). 인증번호는 저장하지 않고 직원 로그인 쿠키와 바로링크 쿠키는 분리한다. 쿠키가 없거나 만료되면 다시 인증한다. 응답 임시 저장은 링크/검사별 sessionStorage 정책을 유지한다.

## 결과 열람

목록은 제출 완료·검사 완료·결과 준비/공개 대기를 구분한다. `completed`는 자동 채점 처리에서도 설정되므로 사람의 검수 완료를 뜻하지 않는다. 링크 범위 내 task가 `completed`이고 `is_report_visible_to_guardian`이 참이며 보고서 파일이 있을 때만 결과 보기가 활성화된다. 다운로드 시에도 링크 유효성·task 소속·센터·공개 상태를 재검증한다. 성공한 접근은 guest 감사 이벤트를 기록하고 60초 유효 서명 URL로 새 탭을 연다. 공개 철회 후 새 URL 발급은 차단되지만 이미 발급된 URL은 남은 60초 이내에 유효할 수 있다. 일반 공개 task 상세에서는 보고서 원본 payload·문서 ID·내부 소견을 반환하지 않는다.

제출 응답의 완료·보고서 공개 상태를 목록에 반영하며, 상단의 목록 새로고침으로 서버 상태를 다시 확인할 수 있다. 자동 PDF 생성과 수신자 공개는 별개다. 현재 공개 플래그는 직원 결과 전송 흐름에서 설정한다. 자동 채점 검사에 한해 PDF 생성 성공 즉시 공개할지는 결정 필요 항목이며, 이번 문구·갱신 보완에서는 공개 권한을 확대하지 않는다.

## 검증 범위

### 기획 대조 보완 (2026-09-08)

기준은 `tools/planning-pilot/plans/plan-42a3a371.json`의 요구·예외 사례와 마지막 저장된 선택 기록 `2026-09-07T07-07-52.267Z-7d80eee6`이다. 후보의 제안·미결정 정책을 확정으로 취급하지 않는다.

- `keyboard-validation`: 미응답 개수와 첫 미응답 문항 이동 버튼을 제공하고 해당 라디오에 초점을 준다.
- `empty-questions`: 서버 상세의 `self_report` 유형과 pending/in_progress 상태가 확인될 때만 문항 입력을 허용한다. 빈 문항·미지원 유형은 센터 문의와 목록 복귀를 안내한다.
- `submit-response-lost`: 매 제출 전에 서버 상태를 다시 조회한다. 이미 제출됐다면 추가 POST 없이 완료를 반영하고 해당 초안을 삭제한다. 조회 실패·통신 실패 시 초안을 유지한다. 이는 서버 트랜잭션 차원의 멱등성 보장이 아니다.
- `cancel-during-exam`, `definition-mismatch`: 제출 직전 상태·유형·문항 정의를 재확인한다. 조회와 제출 사이의 상태 변경은 서버 검증이 필요하다.
- 부분 구현: 인증 응답에 링크 포함 방문 검사의 연결 일정(시작/종료·세션 상태·검사명)을 추가했다. 링크 밖 검사·다른 센터·다른 케이스·내부 메모는 공개하지 않는다. 화면은 한국 시간의 방문 일정과 방문 검사 구분을 표시한다. `collect_link_schedules.py`, `verify_send_link.py`, `send_link/schemas.py` 및 공개 페이지가 근거이며 API 단위 테스트와 모의 브라우저 테스트로 검증한다.
- 미구현: 링크 밖을 포함하는 온라인/방문 전체 목록, 승인형 일정 변경의 바로링크 진입. 발송 단계의 온라인 지원 검사 제한도 아직 남아 있다. 결과 열람은 위 공개 조건에 한해 구현했으며 전체 기획 완료와 구분한다.
- 승인 구조 조사 정정: 직원 대시보드·예약 화면에 이미 일정 변경 승인/반려 흐름이 있다. `schedule_change_request/router.py`는 일정 수정 권한으로 승인을 제한한다. 다만 `request_app_schedule_change.py`는 앱 로그인 사람 ID와 가족·센터 연결을 확인하고 상담 일정만 허용한다. 바로링크는 특정 사람을 식별하지 않으므로 이 핸들러에 수신자 이름/전화번호로 추정한 사람 ID를 넣지 않는다.
- 변경 요청의 다음 결정: 기존 일정 수정 권한을 재사용하고 링크 인증 수신자의 비로그인 요청을 허용할지 사용자에게 확인 요청했다. 허용 시 링크 출처를 기록하는 요청 모델·마이그레이션, 검사 예약 권한/가용성 검증, 직원 목록·승인/반려·알림과 수신자 결과 재조회까지 연결해야 한다. 현재 변경 요청 버튼/API는 구현되지 않았다.
- 선행 결정: 전체 목록의 공개 범위, 일정 변경 승인 담당자·마감·철회·알림, 보고서 공개 대상·시점·만료 정책. 보안 범위를 임의 확대하거나 직원용 API를 공개 화면에 직접 연결하지 않는다.
- 남은 기술 점검: 공개 제출 API의 동시 요청/멱등성, 손상·정의 변경 초안의 폐기 안내, 일정 변경 알림 실패 복구. 특히 직원용 제출 파이프라인은 재제출을 허용하므로 공개 경로의 별도 동시성 통제가 필요하다.

모의 API를 사용한 브라우저 테스트로 입력·붙여넣기·재인증·방문 기록 이동·제출 후 복귀를 검증한다. 실제 문자 발송, 실기기 카카오톡 인앱 브라우저, 운영 데이터 인증은 수행하지 않는다. 실제 재인증 오류는 링크 상태와 해당 요청의 서버 로그를 확인해야 하며 단위 테스트 성공만으로 원인이 해소됐다고 단정하지 않는다.
