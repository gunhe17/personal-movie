## 전제: 전체 구조 한 장 요약

- **로그인 후 기본 진입 = `/schedule/calendar`** (대시보드 아님). `(protected)/+page.ts:1-6`에서 `/` → 302 리다이렉트.
- 메뉴는 **역할 제외(하드코딩) + 권한(OR) 2계층**으로 필터. counselor는 `settings·members·billing·권한설정`이 `ROLE_EXCLUDED_MENUS`로 완전 숨김 (`src/lib/config/sidebar-permissions.ts:43-46`). manager/staff/super_admin은 권한만으로 판단.
- 상담사 데이터 격리는 **백엔드 `owner_scope`/`accessLevel(own/all)` 필터**로 동작하지만, 프론트에서 accessLevel을 쓰는 곳은 대시보드 1곳뿐. 화면에는 "내 담당만 보는 중" 표시가 없다.
- 환경별 숨김: `agent`(프로덕션 숨김), `/schedule/field-notes`(전 환경 숨김), `/center/form-templates`(프로덕션 숨김) — `UnifiedSidebar.svelte:457-463`.

## A. 관리자 시나리오 — 동작 정의

### A1. 센터 개설과 초기 세팅

**실제 동작**: `/signup`(이메일·비번·이름·생년월일·성별·휴대폰·약관) → `/signup/success` → `/welcome`(소속 센터 목록 + 신청 대기 표시 + "새 센터 생성") → `/welcome/register`(센터명·전화·주소·대표자) → 센터 선택 시 `/schedule/calendar` 진입.

- **Q1 (센터 생성 입력)**: 기본 정보만. 운영시간·휴무일·상담실·프로그램·단가는 생성 후 `/center/*`에서 별도 설정 — 어떤 것도 온보딩에서 안내되지 않음.
- **Q2 (멤버 초대)**: `/member/invite`에서 이메일+역할+고용형태로 초대 → 초대자는 `/member`의 "대기" 탭에서 만료일(D-3 등)·재전송 관리 → 피초대자는 메일 링크 `/accept-invitation?token=` → 로그인(또는 가입) → 수락 시 센터 자동 선택 후 `/schedule/calendar`. 흐름 자체는 완결. 엑셀 일괄 초대 버튼은 비활성 상태.
- **Q3 (온보딩 체크리스트)**: **없음.** 센터 생성 직후 빈 캘린더에 떨어진다. 상담실·프로그램·단가 미설정 상태에서는 접수 폼의 드롭다운이 비어 있고, 접수 폼 안에서 "추가하기"(상담실 등 인라인 등록)로 우회하는 구조.

**⚠️ 갭**: 리빙랩 첫 세션에서 "가입은 했는데 다음에 뭘 해야 하는지 모른다"가 나올 확률이 매우 높다. 최소한 빈 캘린더 상태에 세팅 가이드(상담실 → 프로그램 → 멤버 초대 순)가 필요.

### A2. 신규 문의 접수 → 배정 → 첫 일정

**실제 동작 (end-to-end)**:
```
/counseling/status 상단 [상담 접수하기]
→ /counseling/receive (Stepper: 유형(개별/그룹) → 내담자 → 상담사 → 프로그램 → 일정(멀티날짜+장소) → 메모)
→ POST /counseling/intake
→ CounselingCase(active) + 회기 수만큼 Schedule + CounselingSession(scheduled) 생성
→ SMS 알림 발송 → /counseling/status 복귀
```
- **Q4 (접수 진입점)**: 3종이 별개로 존재 — **상담 접수** `/counseling/receive`, **검사 접수** `/assessment/receive`, **운영 일정** `/operation/receive`(회의·블록 등, `schedule_type='operation'`). 사이드바에 "접수" 메뉴는 없고 각 현황 화면·캘린더의 버튼으로 진입. 캘린더의 "스케줄 등록하기"는 운영 일정용 모달이라, **"상담 예약을 캘린더에서 바로 잡는" 동선은 없다** (접수를 거쳐야 함).
- **Q5 (내담자 미등록 시)**: 접수 폼의 ClientMultiSelect에 인라인 등록이 있어 접수 중 등록 가능. 선후관계 문제는 없음.
- **Q6 (배정과 충돌)**: 접수 폼에서 상담사 선택(관리자는 전체, 상담사는 본인만). 충돌 검사는 **장소(room) 기준만** 수행하고(`find_conflicting_schedules`는 room_id 필터만, `apps/api .../schedule/repository.py`), **상담사 이중 배정은 검사하지 않는다**. 즉 홍길동을 같은 시각 상담실 A·B에 동시 배정해도 경고가 없다. 충돌이 있어도 amber 경고만 하고 제출은 차단하지 않음(정책: `docs/RECEIVE_CONFLICT_VALIDATION.md`).
- **Q7 (상태값)**: Case: `active → completed(종결, 되돌리기 가능) | cancelled(복구 불가)`. Session: `scheduled → completed | no_show | cancelled(사유 입력+보충회기 옵션)`. 회기 상태 변경 시 미확정 참석자를 일괄 동기화(완료→attended 등)하는 역방향 동기화 존재(`detail-service.ts:73-160`). 중복 접수는 5분 내 동일 조건 409 차단(상담만 — 검사 접수에는 없음).

**⚠️ 갭**: ① 상담사 이중 배정 무검사 — 리빙랩 실운영에서 가장 먼저 터질 지점. ② 검사 접수는 충돌을 검사해도 응답에 warnings가 없어 사용자가 알 수 없음(상담 접수는 warnings[] 반환). ③ "접수"라는 행위가 상담/검사/운영 3곳으로 흩어져 있는데 신규 문의(아직 상담인지 검사인지 모르는 단계)를 받는 통합 인입점이 없다.

### A3. 하루 시작 — 센터 현황 파악

- **Q8 (첫 화면)**: `/schedule/calendar`. 오늘 전체 일정은 캘린더로 보인다. 그러나 **미처리 접수·미수납·소진 임박 같은 "할 일" 신호는 캘린더에 없다.** 그 신호들은 대시보드(바우처 소진·만료 임박 신호, `dashboard/+page.svelte:51-55`)와 청구 화면(MissingSessionBanner: 미청구 세션 배너), 상담 현황(nextSession kind: `needs_review`(연장/종결 확인)·`unprocessed`(미처리 회기)·`overdue`)에 분산되어 있다.
- **Q9 (대시보드 실데이터/역할)**: 대시보드 위젯(다음 일정 히어로, 바우처 3신호, 공지 4개)은 실데이터. **역할 분기 없음** — 관리자와 상담사가 완전히 같은 화면. `accessLevel` 변수를 선언만 하고(`dashboard/+page.svelte:12-14`) 위젯 구성엔 쓰지 않음. `/dashboard/analytics`는 **전부 더미**("-" 표시 + "차트 준비 중").

**⚠️ 갭**: 관리자의 아침 질문("오늘 누가 오고, 뭐가 밀려 있나")에 답하는 화면이 하나도 없다 — 캘린더(일정만)·대시보드(다음 내 일정 중심)·현황(케이스 목록)·청구(미청구)로 4분할. 리빙랩에서 "어디를 봐야 하나"는 피드백이 예상됨.

### A4. 수납·청구 처리

- **Q10 (billing 범위)**: 내담자 청구 생성(BillableItem: 항목·수량·단가·지원금, 상담/검사/패키지 연계)·납부 기록(Payment: 수단·일시·영수증번호)·미수금 추적·상태 탭(청구 대기→부분결제→완료)까지 구현. 미청구 세션 배너(MissingSessionBanner)로 세션→청구 누락을 잡아준다. **완성도가 상대적으로 높은 도메인.**
- **Q11 (바우처 차감)**: 청구 항목에 `client_voucher_id` 연결, 세션 참가자에 `is_consumed` 필드 존재. 차감 전용 API는 없고 usage 조회만 있음 — 차감은 청구/세션 완료 플로우에 묶여 있다. **`valid_until` 만료 검증이 차감 시점에 없어 만료 바우처도 차감될 수 있음** (voucher/client_voucher 모듈에 검증 부재).
- **Q12 (단가표)**: `/billing/price-list`는 상담/검사/패키지 단가 정의 + 검사·프로그램에서 자동 동기화(synced/manual 구분). 청구 생성 시 참조되는 구조.

**⚠️ 갭**: "billing"이라는 말이 ① 내담자 청구(/billing) ② 서비스 단가(/billing/price-list) ③ SaaS 구독 결제(/settings/billing) 3가지로 쓰인다. 관리자 멘탈 모델에서 ②는 청구가 아니라 센터 설정에 가깝다.

### A5. 검사지 구매·검사 운영

- **Q13 (구매)**: `/assessment/purchase`는 **라우트만 있고 미구현** (+page.svelte 부재). 크레딧/결제 모델이 코드에 없다.
- **Q14 (관리자 vs 상담사 검사 흐름)**: 접수 폼에서 관리자는 담당자 전체 지정+대표(왕관) 지정 가능, 상담사는 본인만. 현황의 담당자 필터는 accessLevel=all(관리자)만 노출. 나머지 흐름(접수→링크 전송→내담자 수행→결과 전송→인증번호 확인)은 동일. 흐름 자체는 SendLink(수행 링크)/SendResult(결과 링크, 4자리 인증번호, 1시간 유효)로 완결돼 있음.

### A6. 멤버·구독 관리

- **Q15 (퇴사 처리)**: 멤버 상태 토글(active/inactive)과 삭제(`delete:member` 권한)는 있다. **퇴사자의 담당 케이스·예정 일정 이관/처리 흐름은 없음** — 비활성화해도 기존 배정이 어떻게 되는지 정의되지 않았다.
- **Q16 (구독 중복)**: `/subscription`과 `/settings/subscription`이 **같은 쿼리·같은 화면의 완전 중복**. `/subscription/ai-usage`와 `/settings/ai-usage`도 동일. 그리고 **두 경로 모두 권한 체크가 없다** — counselor 메뉴에는 없지만 URL 직접 접근을 막는 가드가 없음. (참고: AI/구독 기능은 프로덕션 배포 불가 방침 — 리빙랩 환경이 프로덕션 빌드라면 노출 여부 자체를 확정해야 함.)

## B. 상담사 시나리오 — 동작 정의

### B1. 하루 시작

- **Q17**: 로그인 → `/schedule/calendar`. 캘린더가 "오늘 내 일정"을 보여주므로 상담사에게는 이 기본 진입이 오히려 맞다. 대시보드의 "다음 일정 히어로 + N분 후" 위젯도 상담사 친화적이지만 기본 진입이 아니어서 두 화면의 역할이 겹친다.
- **Q18 (데이터 범위)**: 백엔드가 accessLevel=own으로 자동 필터(캘린더·현황·내담자 목록의 owner_scope). **화면에는 "내 것만 보는 중"이라는 표시가 없어**, 상담사가 센터 전체를 보고 있다고 오해하거나(반대로 관리자가 필터된 줄 모르거나) 할 수 있다. 캘린더에서 상담사가 센터 전체 일정을 볼 수 있는지 여부가 UI로 구분되지 않음.

### B2. 세션 수행 — 사전 확인 → 상담 → 기록

- **Q19 (이동 동선)**: 상담 현황 행 클릭 → `/counseling/status/[id]` (실데이터, 세션 목록+상세 패널+청구 연동). 여기서 내담자 상세로, 세션별 일지로 이동 가능. **주의: `/session/[sessionId]` 라우트는 어디서도 링크되지 않는 고아 라우트이며 mock 데이터(`sessionListMockApis.getSessionDetail('123')`, `session/[sessionId]/+page.svelte:109`)를 쓴다** — 실제 동선이 아니라 레거시. 삭제 대상.
- **Q20 (기록 흐름)**: 일지는 CounselingNote(목표/진행/다음계획/개인메모/소견) 작성 — `/counseling/status/[id]`에서 세션 선택 후 작성. AI 쪽은 필드노트 서비스가 상담 상세에 연결되어 있으나(`createFieldNoteService` 주입) **필드노트 메뉴(/schedule/field-notes)는 전 환경 숨김, AI 에이전트(/agent)는 프로덕션 숨김** — 리빙랩(프로덕션)에서는 수기 일지가 유일한 동선. 기본 동선 = 수기.
- **Q21 (완료 처리)**: 명시적 [완료] 버튼. 미확정 참석자 일괄 처리 모달 → PATCH status. 완료가 청구·바우처 차감으로 자동 연쇄되지는 않고, 미청구 세션은 청구 화면 배너로 사후 잡는 구조(관리자 몫). 상담사 완료 → 관리자 수납이라는 분업은 성립하나 그 인계가 화면에 드러나지 않는다.

### B3. 내담자 등록·관리

- **Q22**: 상담사도 내담자 메뉴 접근·등록 가능(`write:client` 권한 기준, 역할 제외 없음).
- **Q23 (보호자)**: 등록 폼에서 보호자 다중 행 + 관계 선택, 배치 API로 동시 생성·관계 연결(`postBatchCreateClients`). 아동+보호자 시나리오는 커버. 단 **role="both"(내담자이자 보호자)는 API 스키마에만 있고 UI에서 선택 불가** — 성인 내담자가 자기 자녀의 보호자이기도 한 케이스는 표현 못 함. **중복 체크 API(`/duplicate-check`)는 있으나 프론트가 호출하지 않아** 동명이인·재등록 방지 없음.
- **Q24 (담당 개념)**: owner_scope로 존재(백엔드). 목록 화면 표시는 없음(B1과 동일 이슈).

### B4. 검사 의뢰 → 수행 → 결과

- **Q25**: 링크 전송은 SMS/카톡/이메일/QR(바로 링크). 내담자는 `/assessment-flow/login`에서 **검사 전용 계정 로그인 필요** — 링크만으로 바로 검사 시작이 아님(계정 생성 UX는 이번 조사 범위에서 미확인, 리빙랩 전 실전 테스트 필요). 검사 진행 중 토큰 만료 시 복구 흐름 미정의.
- **Q26 (결과 인지)**: `task_submitted`(검사 제출) 인앱 알림이 상담사에게 감(알림 폴링 30초). 결과는 `/assessment/status/[id]`에서 태스크별 확인, 내담자 전달은 SendResult(4자리 인증번호, 다운로드 1시간 유효).
- **Q27 (assessment-case)**: `/assessment-case/[id]`는 배경 이미지 포함 메타 시각화 페이지로 `/assessment/status/[id]`와 역할 중복. 사이드바 레이아웃 숨김 목록에 들어있는 특수 화면. 정리(통합/삭제) 대상.

### B5. 일정 변경·취소

- **Q28**: 세션 취소 시 사유 입력 + "보충 회기 추가" 옵션(SessionCreateModal 연결) — 노쇼(no_show)도 별도 상태로 존재. 반복 규칙은 `session_rule` JSON로 케이스에 저장. 단건 변경은 세션 단위 수정으로 가능. 흐름은 성립. 노쇼→완료 직접 전환 불가 같은 상태 머신 제약은 합리적.

## C. 횡단 질문 답

- **Q29 (메뉴 순서)**: 대시보드→스케줄→내담자→바우처→상담→검사→(구성원→청구→설정)→내정보. 상담사 동선 기준으론 스케줄·상담·내담자가 상단이라 무난. 다만 **"바우처"가 내담자와 상담 사이에 독립 1뎁스**인 것은 실체(바우처 보유 내담자 목록)에 비해 과한 승격 — 내담자 하위 또는 청구 인접이 자연스럽다. 또 바우처 관리(마스터)는 설정>바우처 관리(/settings/vouchers)에 따로 있어 같은 단어가 두 메뉴에 있다.
- **Q30 (접수 중복)**: 사이드바에 "접수" 없음. 상담 접수/검사 접수/운영 일정 등록이 각 화면 버튼으로 분산(§A2). 용어도 "접수하기"(상담·검사) vs "등록하기"(운영·스케줄 모달)로 갈림.
- **Q31 (고아·빈 화면)**: 고아/미완: `/session/[sessionId]`(mock·링크 없음), `/assessment-case`(중복), `/assessment/purchase`(미구현), `/settings/profile`("준비 중"), `/dashboard/analytics`(전부 더미), `/assessment/statistics`(더미 데이터+TODO), `/assessment/quick-links`(**centerId 하드코딩 `'df55ee9f-...'`**, `quick-links/+page.svelte:21`), `/playground`(개발용, ssr=false). 숨김: field-notes(전 환경), agent·form-templates(프로덕션).
- **Q32 (URL 직접 접근)**: 클라이언트 라우트 가드는 인증만 있고 **권한 가드는 페이지별 선택 적용**. counselor가 `/billing` 직접 접근 시 페이지는 뜨고 API가 403으로 막는 구조(액션 버튼은 hasPermission으로 숨김). `/subscription`은 그 API 게이팅조차 확인 안 됨 — 실제 403 여부를 리빙랩 전 확인 필요.
- **Q33 (설정 3곳)**: `/center/*`(센터 운영 설정, 사이드바 "설정") vs `/settings/*`(개인·계정+구독, 진입점 별도) vs `/myInfo`(센터별 내 프로필+근무일정, 그런데 구독 탭이 여기에도 있음 — 관리자 한정). 개인/센터 경계가 3중으로 흐려져 있고 구독이 3곳(myInfo 탭, /subscription, /settings/subscription)에서 접근된다.
- **Q34 (알림)**: 이벤트 종류는 풍부(상담·검사 케이스/회기 생명주기 전체 + 시스템, `notification/constants.ts:19-42`; 백엔드 `notify_members()` 발행). 실시간은 아니고 **30초 폴링**. 채널 기본값: 인앱 ON, 알림톡·푸시 OFF. "알림이 안 와요"보다는 "30초 늦게 와요" 수준이라 리빙랩 치명도는 낮음.

### P1 — 사용성 모호 (리빙랩에서 피드백 왜곡을 막기 위해 사전 정리 권장)

1. **온보딩 부재** — 센터 생성 직후 빈 캘린더. 세팅 순서(상담실→프로그램→단가→멤버) 가이드 필요 (§A1).
2. **관리자 아침 화면 부재** — 할 일 신호(미처리 접수·미청구·소진 임박)가 대시보드/현황/청구에 4분할 (§A3). 대시보드에 역할 분기(manager용 운영 신호)를 넣는 것이 최소 수정.
3. **데이터 범위 미표시** — 상담사 "내 담당만" / 관리자 "전체" 를 목록 헤더에 명시 (§B1·B3).
4. **접수 진입점·용어 분산** — 상담/검사/운영 접수 3곳 + "접수/등록" 혼용, 캘린더에서 상담 예약 불가 (§A2, Q30).
5. **검사 링크 용어** — "링크 전송"(수행)과 "결과 전송"(다운로드)이 UI에서 구분 안 됨 → "검사 링크"/"결과 링크"로 라벨 분리 (§B4).
6. **중복 체크 미사용** — duplicate-check API 연결로 재등록/동명이인 방지 (§B3).
7. **구독·설정 3중 진입** — /subscription 계열 중복 제거, myInfo의 구독 탭 제거 (§A6, Q33).
8. **바우처 메뉴 이원화** — 1뎁스 "바우처"(내담자 현황)와 설정>바우처 관리(마스터)의 관계 명확화, 바우처 수정 UI 부재 (§C Q29).
9. **퇴사 처리 흐름** — 멤버 비활성화 시 담당 케이스·일정 처리 정의 (§A6).
10. **assessment-flow 내담자 로그인 UX** — 검사 전용 계정 생성·만료 복구를 리빙랩 전 실전 리허설 필수 (§B4).
